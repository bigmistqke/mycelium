A rule carries its own check, and its examples are that check's tests draft 2026-07-31

The language family holds fourteen rules. Eight of them declare language-checkable as yes. No check exists for any of them. Nothing reads a rule, nothing enforces one, and a rule marked yes produces exactly the same result as a rule marked no.

That is not a gap waiting to be filled by the obvious next commit. It is the same shape as validate reported failures and exited zero: a mechanism that reads as enforcement while enforcing nothing. The field states an intention in the grammar of a capability.

We also declared the value wrong within two hours. say-harness-when-you-mean-harness was marked no, when the truth is that a machine cannot decide it but can flag every candidate. The repair proposed at the time was a third value, gate|flag|none, which keeps the shape that failed: still hand-written, still a claim about a capability rather than the capability, still able to disagree with what exists.

What the ruleset should be

Limited, and ours. An external style guide has more rules than this project will ever write by hand, but importing three hundred of them produces a hand-maintained copy of somebody else's list, which is precisely the failure a readers treat a hand-copied command list as the whole tool records. A small ruleset authored here has no upstream and therefore cannot drift from one.

That argument does not extend to implementations. If a published library already detects passive voice, writing a worse detector by hand is not ownership, it is duplication. So the design has to let a rule reach a library without making every rule depend on one.

Delete language-checkable. A language-rule may instead carry a <script> exporting check(text).

A rule with a script is enforced. A rule without one is guidance. Enforceability stops being described and becomes observable, so it cannot be wrong.

A check takes text, not documents

A rule and an audit ask different kinds of question, and the distinction decides the whole shape. An audit asks something about a set of documents: is every outcome linked to, is anything an orphan. A rule about writing asks something about a string.

Giving a rule check(documents) and a data-audits marker makes it an audit, and that is what makes reaching comments in src/ and messages in git look hard: the checker has to go and find text wherever it lives. Inverted, the problem is not there. The rule receives the text. A commit message arrives on stdin, an audit extracts corpus prose and brings it, and nothing has to reach outside docs/ because nothing is reaching at all.

One function, three callers, none of them a family

language.template.html exports the function that runs every rule against a string, the way knowledge.template.html already exports extractGraph by id for its own generate command to import. mycelium run language lint is a thin wrapper over it.

  1. language lint - reads stdin. Commit messages, drafts, anything.
  2. An audit extracts corpus prose and calls the same function, so the graph is checked by the same rules as everything else.
  3. A commit-msg hook, once the rules are worth blocking on.

Nothing calls it from inside another family. Wiring it into knowledge add would be the first cross-family import in the system; the decision against it has the test that settles it and the reason the cost is only immediacy. The coupling belongs in a skill or a hook, which already compose commands.

A general mycelium lint with a script type the engine recognises would let any family contribute rules. Deferred with a condition: a second family wanting to contribute, because a protocol with one participant coordinates nothing.

The two examples are the check's tests, directly

language-pass and language-fail are required on every rule, for a human reason: readers read a rule stated abstractly differently. They are also strings, and a check takes a string, so running a rule against its own examples needs no fixture and no simulated corpus.

lint verifies every rule against its own two examples as part of its own run. A check that does not flag its failing example fails the test. A check that flags its passing example fails the test. We catch both before they reach the corpus.

Protected text belongs to the caller

No rule may be applied to a code block, the boilerplate quoting a plan's environment, a rule's own failing example, or a knowledge-prompt. That last is a record of what somebody typed, and editing one to satisfy a style rule would make the record false. Cleaning the corpus established this: of 59 occurrences found, 27 sat in protected contexts and 2 of those were inside recorded user messages.

Because a check takes a string, this is not a rule's problem at all. The caller that knows what a document is does the extraction; a commit message needs none. That keeps the logic in one place per caller instead of one place per rule.

Reaching a library stays a per-rule choice

A probe confirmed that a script inside a document resolves a bare npm specifier, through the virtual-module hook described in virtual module script imports. So a rule wanting retext-passive imports it, and a rule we implement ourselves imports nothing. Same file shape, and the project never has to adopt a linter wholesale.

Title length is absent because it is no longer a candidate. It is a pattern on the field, which is where a check goes when the schema can already express it.

Sentence length is the one number this spec does not fix. A cap of 25 words, which is what ASD-STE100 uses, flags 519 sentences, a quarter of the corpus. At 40 words it flags 168 and at 50 it flags 68.

The standard chose its number for aircraft maintenance procedures read by non-native speakers, and this corpus is expository prose about software. The number is a judgment about how much rewriting is worth it, and we leave it open below.

Two questions this spec previously left open are now answered. A check receives text, not documents. And a rule's own examples test it directly, with no fixture.

  1. What a violation is. A message alone is enough to report. An offset and an excerpt let a caller point at the place, which matters for a long detail field and matters less for a commit message. The cheaper shape is hard to widen later without touching every rule.
  2. Whether lint exits non-zero. A linter that only reports is ignored; one that blocks on 464 known violations is turned off. Related to the next question, and probably answered together.
  3. Whether corpus linting joins validate immediately. Gating across 277 existing documents fails on the first run. Gate on node shape, not on logging rate is the nearest precedent and suggests gating only what we write after now, but "newly written" needs a definition that does not depend on git, which a reader of the graph cannot follow.
  4. The sentence cap. 40 words flags 168 sentences, 50 flags 68. Not a technical question.
  5. Whether a rule without a check needs any marking. Absence is already the signal, and adding a field to say so reintroduces what this spec deletes. But a reader scanning a list cannot see absence, so list may need to show it even though no document stores it.
  6. Rules whose check needs configuration. A length cap has a number in it. In the script, changing it edits code inside a document. In a field, the field can disagree with the script. The same problem this spec solves for enforceability, one level down.
