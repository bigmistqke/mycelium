Deciduous as an HTML template series, plus v4's first dogfooded knowledge nodes implemented 2026-07-23

DESIGN.html proposed reimplementing deciduous's six node types and six edge labels as a template series, then building real knowledge nodes from v4's own history on top of it, as the proof case for the whole document-as-canonical-store thesis (see DESIGN.html's "What's next" item 1). This spec fixes the shape of that template series and scopes the first real instances. The crawler, mycelium run, and any cross-file validation stay explicitly out of scope, per DESIGN.html's own roadmap ordering — everything here is provable by opening a single document in a browser, nothing requires fetching across files.

File naming convention: a template file is named after the tag family it defines (spec.template.html for the spec-* family, knowledge.template.html for the knowledge-* family), not after any single type within it — the same file can hold several related <template> entries, addressed by fragment, the way DESIGN.html's own worked example already does. Documents that conform to spec-doc end in .spec.html; knowledge instances end in their specific type instead — .goal.html, .decision.html, .action.html, .outcome.html — since knowledge-* has six types where spec-* only ever had one, and a shared .knowledge.html wouldn't say which. Not applied with full rigor (the strict form would be .knowledge-action.html, matching the tag exactly, and .spec.html would arguably become .spec-doc.html for the same reason) — good enough for now beats a consistency pass nobody asked for. The descriptive part of the filename also drops the now-redundant type word: write-design-html.action.html, not action-write-design-html.action.html.

Tag vocabulary: hyphenated, family-prefixed

Each node type is a real element, not a <div data-node="goal">, and fields are child elements, not data-field attributes — templates are exactly where this project's vocabulary gets invented, so it should read as itself. Every invented tag is hyphenated, though: the Custom Elements API rejects unhyphenated names outright, and an earlier, unhyphenated version of this vocabulary already collided twice — once for real (<title>, a real element with its own parsing rules, worked around with a CSS reset before this fix) and once waiting to happen (option, one of the six deciduous types, is a real, heavily special-cased HTML element).

The hyphen prefix names a family, not a brand (not v4-title): spec-* for design-document types, knowledge-* for the six deciduous node types — knowledge, not graph, because "graph" only names the shape (and most of this project is graph-shaped, given every document links to others), while "knowledge" names what these six types actually are: captured reasoning, not structure for its own sake. Mirrors the project's own knowledge/ directory of instances. A root type is <family>-<type>; its fields share only the family prefix, since fields belong to the family, not to one type within it — every knowledge-* type shares knowledge-title, the same way every spec-* type shares spec-title: 

<template id="knowledge-goal">
  <knowledge-goal>
    <knowledge-title></knowledge-title>
    <knowledge-confidence></knowledge-confidence>
    <knowledge-status></knowledge-status>
    <knowledge-prompt></knowledge-prompt>
  </knowledge-goal>
</template>

Instance:

<knowledge-goal data-conforms-to="../templates/knowledge.template.html#knowledge-goal">
  <knowledge-title>Build v4: knowledge graph as hypermedia</knowledge-title>
  <knowledge-confidence>85</knowledge-confidence>
  <knowledge-status>pending</knowledge-status>
  <knowledge-prompt>we are playing around with mycelium…</knowledge-prompt>
</knowledge-goal>

Validators query by tag instead of attribute: root.querySelector('knowledge-title'), root.querySelector('knowledge-confidence'), and so on, the same pure-check(root) shape DESIGN.html's live demo already established.

Styling: shared theme, one stylesheet per template family

Every document up to this point carried an identical inline <style> block, so a change to the shared look (colors, fonts, how code/pre/table render) meant editing every file separately. That duplication is now two real stylesheets, linked normally, not generated by any tool: theme.css, the base look shared by every document in experiments/v4/ regardless of type, and templates/spec.template.css, sibling to spec.template.html, holding only the spec-* family's own rendering rules. A future knowledge.template.css would sit next to knowledge.template.html the same way. A document links both: this one pulls in ../theme.css and ../templates/spec.template.css; if it later embeds an inline knowledge-decision, it links that family's stylesheet too, the same way data-conforms-to already composes.

This doesn't weaken the self-containment DESIGN.html argues for — that thesis is about the data never living somewhere else, not about zero external resources, and DESIGN.html itself already pulls in an external script to render its mermaid diagram. A missing stylesheet degrades to unstyled-but-fully-readable-and-queryable HTML, not missing content.

Per-type fields

Deciduous's flat schema bolted status onto every node type and then had to fake its absence for option/outcome/observation with a nodeTypeSupportsStatus() helper — the exact problem DESIGN.html names as the reason templates exist. Field vs. link: not every need becomes a field

The correction earlier in this document (see "Shape" in spec.template.html) was that a spec's real content can't sit entirely outside any tag — that's what made the first three-field version unqueryable. It would be a mistake to read that as "therefore anything worth keeping needs its own field." The distinction that actually matters isn't structured vs. unstructured, it's uniform vs. ad hoc: a field earns its place when the same question should be askable across every instance of a type without opening each one by hand — every spec's problem statement, every decision's confidence. A plain link earns its place when the connection is genuinely one-off: this spec happens to reference a runnable experiment, a scratch calculation, a tangential elaboration, worth reaching from here but not something every future spec should be expected to have a slot for, filled in or explicitly omitted.

Neither path is less queryable than the other, just queryable differently. document.querySelectorAll('spec-problem') finds every field of that kind across the corpus; document.querySelectorAll('[data-rel]') finds every asserted relationship regardless of what's on the other end. A field promises uniformity the schema enforces; a link asserts one relationship without promising every other document has (or lacks) the same one.

This is also what the original framing in DESIGN.html already asked for — "co-locating knowledge, documentation, experiments, tests, implementation code (or not)" — and it only works if structure stays optional per-connection, not mandatory per-type. Content outside a template's structured element, or inside one of its free-form sections without being promoted to a field of its own, is not a gap to close; it's the same honest default DESIGN.html already names for links themselves: a document that asserts nothing about some tangent contributes nothing queryable about that tangent specifically, and that's fine, not a degraded case. Apply the same instinct when knowledge.template.html gets built: resist adding a field for something a link would serve just as well.

Conformance: on the element, not the document

DESIGN.html's own example declares conformance with a <link rel="conforms-to"> in <head> — a claim about the document as a whole, one slot, exactly one type. That doesn't compose: it can't sit next to a <knowledge-decision> nested inside this very document's <spec-design> section, declaring conformance for just that one embedded element (see the open question below about inline <knowledge-decision>/ <knowledge-observation> instances). So this document (and spec.template.html) instead declare conformance as a data-conforms-to attribute directly on the element making the claim — this document's own <spec-doc> tag carries it. A document can then have exactly one typed root and any number of typed elements nested inside it, each independently found via document.querySelectorAll('[data-conforms-to]').

Edges

The six data-rel labels carry over unchanged: depends_on, blocks, supports, contradicts, alternative_to, leads_to, used exactly as DESIGN.html's <a data-rel="verifies" href="…"> example already shows. knowledge-option → parent knowledge-decision uses depends_on, the closest existing label; the dogfood chain below uses leads_to for its forward narrative. New labels get minted the same way DESIGN.html describes: as a project needs them, not from a fixed enum — this document mints specifies for the spec → action link below, and elaborates for the link to DESIGN.html above.

Audits live with their family

First built as a separate audits/knowledge-integrity.html, then folded into knowledge.template.html itself once the reasoning for separating it didn't hold up: "different scope" (checking one instance vs. checking the whole graph) argues for a different kind of script, not a different file, and both audits below only ever concern relationships between knowledge-* types — a family already bundled in one file on purpose. An audit that spans two families (say, confirming a spec-doc's specifies edge resolves to a real knowledge-action) would still earn its own file, since neither family's template file could host it without redeclaring the other's types. Neither audit here is that, so there is no audits/ directory.

The convention: data-validates="#id" marks a script checking one instance against one template (check(root), existing convention); data-audits="name" marks a script checking the whole graph (check(nodes, edges), new), with data-touches listing which types it concerns — queryable the same way data-rel makes an edge queryable, rather than left as prose only a reader would know.

  • orphans-except-goal — every non-knowledge-goal node must have at least one edge (CLAUDE.md: "Root goal nodes are the ONLY valid orphans").
  • dangling-outcome — every knowledge-outcome must have an edge back to what it resolves (CLAUDE.md: "does every outcome link back to what caused it?"), deliberately stricter than orphan-checking: an outcome with only an outgoing edge already passes orphans-except-goal but is still exactly the dangling case CLAUDE.md means.

Both are pure functions over {nodes: [{id, type}], edges: [{from, to, rel}]} — deliberately the shape a future crawler would emit by parsing knowledge/*.html. Proven live, but not against a hand-typed fixture and not against the real knowledge/ files either: knowledge.template.html's own sample instances (one per type, already there to prove each per-instance validator) are wired together with real data-rel edges, and the audit demo extracts nodes/edges straight out of that markup — even the six type names come from document.querySelectorAll('template[id^="knowledge-"]'), not a retyped list. That's a closer preview of the eventual crawler than a JS array fixture would be, short of actually fetching across files, which stays deferred. The five real instance docs get conforms-to links and hand-verified-correct structure, not yet mechanically checked.

The six dogfood nodes

v4's own decision trail so far, as knowledge nodes instead of deciduous rows:

  1. build-v4.goal.html — a knowledge-goal, "Build v4: knowledge graph as hypermedia," with knowledge-prompt set to the verbatim message that opened this session.
  2. html-as-store.decision.html — a knowledge-decision, "HTML documents as canonical store, not DB + Markdown," summarizing DESIGN.html's core thesis.
  3. write-design-html.action.html — a knowledge-action, writing DESIGN.html.
  4. design-html-committed.outcome.html — a knowledge-outcome, committed as 9794442, with knowledge-commit set accordingly.
  5. write-template-series.action.html — a knowledge-action: the template series plus this spec.
  6. template-series-built.outcome.html — a knowledge-outcome, added once the action above actually landed rather than written speculatively ahead of it, per CLAUDE.md's before/after logging rule.

Chained knowledge-goal →leads_to→ knowledge-decision →leads_to→ knowledge-action →leads_to→ knowledge-outcome →leads_to→ knowledge-action →leads_to→ knowledge-outcome. This document's specifies edge points at node 5: the action that wrote this template series.

Spec docs are graph nodes too

This document is the concrete answer to a meta-question the brainstorming skill leaves open for every project: where does an approved design go? v4's answer is templates/spec.template.html's spec-doc type: a required identity (spec-title, spec-status, spec-date) plus required spec-problem and spec-design sections, and optional spec-out-of-scope / spec-open-questions sections — each free to hold whatever content the design needs, but addressable by tag name across every spec in the corpus. spec-status tracks the skill's own lifecycle: draft while under discussion, approved at the point this document reached (sign-off, before writing code), implemented once this design has shipped.

  • No mycelium run. Deferred by DESIGN.html's own roadmap.
  • No crawler/index. Same deferral; nothing here fetches across documents.
  • No live validation of the real instance docs. The audits prove out against knowledge.template.html's own sample markup, not the real knowledge/ files, which don't exist yet. The five dogfood nodes below, once written, are correct by hand-inspection, not mechanically checked against the audits. That mechanical check — the audits running for real, against real files — is exactly what the crawler gives later.
  • Once knowledge.template.html exists, should specific claims inside a spec's <spec-design> (like the two callouts above) be marked up as inline <knowledge-decision>/<knowledge-observation> instances, rather than plain paragraphs? Left open rather than done here, since it can't properly conform to a template that doesn't exist yet.
