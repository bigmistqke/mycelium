Virtual ES modules extracted from template-embedded script blocks draft 2026-07-25

Two knowledge-decision nodes from this session settled the shape of a mechanism — extract embedded scripts into virtual ES modules rather than concatenate and address them via #id fragments — without specifying it fully enough to build. This doc is that specification.

Today, a template-embedded <script type="mycelium/command"> or <script data-validates> block is loaded as a single self-contained blob (a data: URL, per spec.template.html's own comment on the subject). A data: URL has no hierarchical base, so a relative import inside one has nothing to resolve against — which is why every family's script duplicates whatever logic it needs instead of sharing it. That's a deliberate, already-made choice at small scale: duplicate-not-share-loadcheck chose to duplicate a five-line function across two call sites rather than build sharing machinery for it. But once more than a function or two needs sharing — a slugify helper, a Markdown parser, another family's own validator delegated to for a nested foreign type — duplication stops being viable, and nothing about the data: URL model can simply be relaxed without losing the property that a template's script stays a single, self-contained, inspectable blob: no build step, nothing to keep in sync, no persisted artifact that can drift from its source.

Extraction

Every <script> block embedded in a .template.html file — a type="mycelium/command" block, a data-validates block, any future kind — is extracted at load time into its own real ES module. Extraction is not a build step and produces no file on disk: the mechanism below reads the real .template.html file, finds the script's text via the project's existing HTML parser (not a regex — attributes and nested markup make a hand-rolled pattern fragile), and hands that text to Node's module system as the source for a synthetic URL. Nothing is cached across invocations; every run re-extracts from the real file, the same "derive fresh, never persist" discipline this project already applies to backlinks.

Addressing: only an explicit id is importable

A script block becomes importable only if its <script> tag carries an explicit id attribute — distinct from any data-validates="#type-id" it might also carry, since "what type this script checks" and "what name you call this script by" are different questions and a type could plausibly have more than one addressable script. An id'd script is imported the same way anything else in this project is already cross-referenced — a fragment on a path: 

import { slugify } from "../format-utils.html#slugify"
import { check as checkKnowledgeDecision } from "../knowledge.template.html#knowledge-decision-validate"

A script with no id is simply not part of the import address space. That's not a gap needing a fallback name — it's the correct boundary: only scripts that opt in by declaring an id are addressable from outside their own file. The module system still needs some identity to hand the JS engine when it evaluates an un-id'd script (engines want a module URL for stack traces regardless of whether anyone imports it), but that identity is derived deterministically from the script's file path and its position among that file's <script> tags — never assigned randomly. A random identity would need to be remembered to reproduce, which is exactly the kind of persisted derived-state this design avoids everywhere else; a positional identity is recomputed identically every time, from nothing but the file that's already there.

Resolution: Node's own module-customization hooks, not a data: URL

Confirmed working by direct prototype, not inferred: a data: URL module in Node cannot resolve anything requiring a hierarchical base — not a relative path, not even an absolute filesystem path, not a package.json subpath import. Only a fully self-sufficient URL works from inside one (a file:// URL, a node: builtin, or another data: URL used directly as a specifier). That ruled out extending today's loadModule (a plain import("data:text/javascript,…"), per utils.ts) by rewriting specifier text alone.

Node's real extension point for this is node:module's register(), which installs a pair of hooks — resolve(specifier, context, nextResolve) and load(url, context, nextLoad) — that every module resolution and load in the process passes through:

  • resolve recognizes a specifier matching <path>#<id> — using the URL spec's own native fragment syntax (new URL(specifier, parentURL) splits path from id for free, no custom string parsing) — and mints a synthetic file:// URL that sits in the same real directory as the referenced HTML file, marked so load can recognize it (confirmed pattern: file://<dir>/<basename>.__mycelium_virtual__.<id>.mjs). Anything else is passed to nextResolve, unmodified.
  • load recognizes that synthetic URL, reads the real HTML file, extracts the script text for that id, and returns it as the module's source ({ format: "module", source, shortCircuit: true }). Anything else is passed to nextLoad, unmodified — including every one of today's existing data:text/javascript,… calls, which never match this pattern and keep working exactly as they do now.

Because the synthetic URL is a real, hierarchical file:// URL living beside the real file, a plain relative import written inside the extracted script — import { slugify } from "./format-utils.mjs" — needs no special handling at all: it resolves against that synthetic URL's directory using Node's completely ordinary default resolution, which is the real file's real directory. Both hooks fall through for it via nextResolve/nextLoad, and Node loads the real file normally. This was prototyped end-to-end — a fake template file with an embedded script importing a real neighboring .mjs helper, resolved and executed with no rewriting of the inner import at all.

Integration is additive: register() is called once, early, in run.ts's and validate.ts's main(). Nothing about today's loadModule/loadCheck in utils.ts needs to change.

What this unlocks

  • Shared helpers — a slugify, a generic "require these tags present" validator helper, a Markdown or TypeScript parser — can live once and be imported by any family's script, real ES import/export, no scope collisions, no hand-copied duplicate logic.
  • Cross-family validator delegation — a family whose content can nest another family's type (a spec-design section containing a <knowledge-decision>, say) can import that other type's own validator and delegate to it, instead of either re-implementing a check for content it doesn't own or silently trusting it's well-formed.
  • Cross-family command reuse — a command that needs to resolve and confirm another family's id is valid (not just that the string is present) can call into that family's own resolution logic directly.

This is the same underlying question duplicate-not-share-loadcheck already answered once, just at a different scale: sharing machinery wasn't worth it for one five-line function used in two places; it becomes worth it once the target is "any family, sharing with any other family, indefinitely" rather than two known call sites inside the engine itself.

  • Non-HTML target formats for a family's own validator (Markdown, TypeScript) — a separate, larger question, tracked as its own observation rather than specified here.
  • A render() hook so a non-HTML citer shows up in a generated cross-reference view — named as a gap elsewhere, not addressed by this mechanism.
  • A template.template.html that validates template files themselves.
  • Whether a command script should be allowed to import a validator script and vice versa, as opposed to just "any script may import any id'd script" — this doc specifies the mechanism, not a permission policy on top of it.

Re-parsing is simpler and keeps "always derive fresh" uniform; caching is the obvious performance answer if a file is imported from many times in one run. Unresolved.

Does the loader need its own collision check independent of the DOM's, or is "don't reuse an id across element kinds in one file" left as an authoring discipline?
  3. Only static import/export … from declarations are addressed here. A dynamic import("…") expression using the same <path>#<id> form would go through the same hooks and likely just work, but that hasn't been prototyped — noted as untested, not assumed.
