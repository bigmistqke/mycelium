spec.template.html's authoring commands, and date-prefixed filenames for both families approved 2026-07-24

CLAUDE.md's own tracked gap: spec.template.html has no type="mycelium/command" script, so every spec doc in this project — including this one — is still hand-authored through Write/Edit, the exact workflow the original authoring-commands spec built add/link/update to eliminate for knowledge-*. spec-doc is a different shape than any knowledge-* type, though, in ways that don't just fall out of copying the existing commands:

  • One type, not six — no <type> positional needed.
  • Cross-references live inside the rich-content fields (<a data-rel> nested in spec-design, etc.), never as direct children of <spec-doc> itself — so there's no edge-attaching operation for a link command to perform.
  • Two of its five required fields, spec-problem and spec-design, are both rich content (real markup, not a one-line value) and both mandatory from the moment a spec is created — unlike knowledge-detail, which is optional everywhere and could always be filled in by a later update call, a spec's own validator rejects it as incomplete without both, so add itself has to accept rich content for more than one field in the same call.
  • Filenames encode a date (<date>-<topic>.spec.html), which no knowledge-* file has ever needed.

add and update only — no link, no list yet

No <type> positional: spec.template.html defines exactly one type, so add takes only flags. No link: since every cross-reference already lives inside a rich-content field's own markup, authoring one is just part of writing that field's content (see "Rich content: one --body flag" below) — there's no separate "attach an edge to this node" operation the way knowledge-* has. No list, for now: a spec's filename already encodes its date and topic, so the only genuinely hidden field is spec-status; the corpus is small enough that this doesn't yet earn a command the way knowledge list did for a fast-growing, opaquely-named directory. Can be added later, the same way knowledge list itself was added after add/link/update already existed.

Filenames: no --date flag anywhere

add computes today's date itself — local calendar day, zero-padded YYYY-MM-DD, via a small local helper (not a shared export; see "Duplicated, not shared" below): 

function todayDate() {
  const d = new Date()
  const pad = n => String(n).padStart(2, '0')
  return `${d.getFullYear()}-${pad(d.getMonth() + 1)}-${pad(d.getDate())}`
}

No override flag: every spec written this session used the date it was actually written on, never a backdated or future one, so there's no real use case an explicit --date would serve that "today" doesn't already cover — one less argument to document, remember, or misuse. For spec-doc specifically, the same computed value fills two places: the filename prefix (<date>-<file>.spec.html) and the required <spec-date> field's content, so they can never drift apart the way a hand-typed date in each spot could.

knowledge-* filenames get the same date prefix, separately

Not a new field, not a schema or validator change, not retroactive: existing knowledge/*.html files keep their current names untouched. This only changes how knowledge.template.html's own add constructs a new file's path, from knowledge/${args.file}.${type}.html to knowledge/${todayDate()}-${args.file}.${type}.html — the exact same todayDate() shape as spec-doc's, duplicated into knowledge.template.html's own command script rather than imported from anywhere. No other command needs to change: update/link both take an existing file's exact current name as an argument, never construct one, so this is fully contained inside add's one line of path-building logic.

Duplicated, not shared

todayDate() lives once in each family's own type="mycelium/command" script (knowledge.template.html's and spec.template.html's), not in utils.ts as a shared export. Same reasoning already applied to loadModule/loadCheck: a data: URL-loaded command script can't do a relative import anyway (a data: URL has no hierarchical base to resolve ./utils.ts against), and each family's command script stays self-contained by design — requireArgs already lives only in knowledge.template.html, not shared with a family that didn't exist yet when someone wrote it. spec.template.html's own command script gets its own requireArgs, too, not a copy imported from knowledge.template.html.

Rich content: one --body flag, not one flag per field

Real options considered and rejected, in the order they came up:

  • A flag per rich field (--problem, --design, --out-of-scope, --open-questions), each independently literal-or---for-stdin. Breaks the moment more than one needs stdin in the same call: stdin is one stream, and a second readStdin() call finds it already drained, silently returning an empty section instead of an error.
  • A curl-style @-prefix per field (--problem @file, --problem @-). Doesn't actually solve the collision above — that's fixed by reading from files instead of stdin, which works identically whether it's spelled with an @ or a second flag. The @ was purely a flag-count question, confusing to present as if it were the fix.
  • A file per rich field (--problem-file, --design-file, one real file each). Genuinely solves the collision — unlike stdin, the command can read each file independently — but at the cost of needing a separate temp file per field just to write one spec, real friction for what's usually a single sitting of authoring.
  • Defer problem/design to a later update call, so add only ever handles single-line fields. Doesn't work at all: spec-problem/spec-design are both required, so add's own cli.validate() call rejects the node before it's ever written — there's nothing left for update to fill in afterward.

Landed on: one flag, --body, same literal-or---for-stdin shape --detail already has. Its value is a small blob of markup using the field names as their own delimiters — nothing new to invent, since an author already has to know spec-problem/spec-design/spec-out-of-scope/spec-open-questions by name regardless: 

mycelium run spec add --title "…" --status draft --file remove-x --body - <<'EOF'
<spec-problem>
  <p>Whatever's motivating this.</p>
</spec-problem>
<spec-design>
  <p>The approach, with a real code block:</p>
  <pre><code>const x = 1</code></pre>
</spec-design>
EOF

One flag, one stdin stream (or one literal string, for a trivial case), no collision possible — because the command only ever reads one thing, which can carry as many or as few of the four sections as the call actually needs. Not present in the blob at all: the command leaves that field alone.

Parsing reuses the exact mechanism already used for knowledge-detail's own real-markup insertion, wrapped and queried by tag name: 

function extractSections(cli, bodyMarkup) {
  const { document } = cli.parseHTML(`<div>${bodyMarkup}</div>`)
  const wrapper = document.querySelector('div')
  const sections = {}
  for (const tag of ['spec-problem', 'spec-design', 'spec-out-of-scope', 'spec-open-questions']) {
    const el = wrapper.querySelector(tag)
    if (el) sections[tag] = el.innerHTML
  }
  return sections
}

This needs cli to expose parseHTML (already in utils.ts, alongside validate/readStdin) as a fourth capability, since the command script itself can't import it directly. A typo'd or malformed tag inside the blob needs no special handling: it just fails to match any expected tag name, that field silently stays unset, and cli.validate() catches the resulting "missing spec-problem" the normal way — the same safety net every other malformed-input case in this project already falls back on, not a new failure mode to design around.

update: the existing per-field convention, applied per tag found

update's established rule for every optional field — omitted leaves it untouched, an explicit empty value removes it, anything else upserts it — maps directly onto --body's contents, just checked per tag instead of per flag: a tag absent from the blob means that field isn't touched by this call at all; a tag present but empty (<spec-design></spec-design>) removes the field; a tag with real content upserts it, matching knowledge-detail's own upsert logic (overwrite via innerHTML if the field already exists, create and append if not).

  • No list command for specs. Named directly above as deferred, not rejected — the corpus and the "what's hidden" surface are both small enough right now that ls docs/specs/ plus opening a file covers most of what it would add.
  • No retroactive renaming of existing knowledge/*.html files. The date prefix only applies to files add creates from here forward. Renaming existing files would also mean rewriting every <a href> that currently points at them by their un-prefixed name across the whole graph — a much bigger, more error-prone operation than this spec's actual scope, and not something asked for.
  • No per-field rich-content flags. Considered and rejected above, alongside the @-prefix and per-field-file alternatives — --body covers the single-field case fine (a blob containing only one tag), so keeping both would just be two ways to do the same thing.
  • No --date override flag. Considered and rejected above — nothing in this project's actual usage has ever needed a spec dated other than the day someone wrote it.
