Cardinality in the template schema: the repeatable declaration draft 2026-08-06

The schema vocabulary in template.template.html has three words. required says a field must carry text, pattern constrains that text, and enum closes it to a fixed list. None of them says how many times a child may appear.

So every placeholder means at most one, and the validator acts on that by finding each field with Array.from(el.children).find(…). A second child of the same tag never reaches a check.

Two things follow. A duplicate field passes: add a second <plan-title> to a step and validation stays clean, leaving one title live and the other as content that no field holds and no query reaches. That is the failure nothing-outside-the-type guards against at the level of the document body, one level down and unguarded.

And a genuinely repeated child cannot declare itself. plan-doc holds many plan-task children and figure-graph holds many figure-node children, but each template can only write the placeholder once, where it reads as a single optional field. The prose in plan.template.html already says optional (repeatable) plan-task children, so the word exists in the documentation and nowhere in the schema.

A third problem sits next to these and this spec does not solve it. No figure-graph in the corpus carries data-conforms-to, so no figure has ever met the generic validator at all. Cardinality changes nothing there until a figure declares conformance. See the observation about an instance living inside a host document.

Add one word. repeatable on a placeholder says the child may appear more than once. Its absence makes a second one an error rather than silence.

<plan-title required>           exactly one
<plan-status enum="rejected">   at most one
<plan-task repeatable>          zero or more
<figure-node required repeatable>  one or more

The order of the placeholders is the content model, and it always binds. There is no word to relax it. A document that does not match its declared shape is as wrong as one missing a required field, and the project has no reason to negotiate about that.

Two orders, and only one of them is structure

Order between placeholders is structure. A title comes before a status, which comes before the run of tasks, because the template says so.

Order within a run is content. Which task comes second is whatever the author chose. The schema says nothing about it, and it needs no word to stay silent, because nothing in the project sorts a run.

That split is what keeps the vocabulary at one word. An earlier draft carried a second word saying whether a tool could sort a run, on the theory that a figure's nodes form a set and a plan's steps form a sequence. The distinction is real and it belongs nowhere in a schema, since the only thing it could gate is a rewrite that no command performs.

The walk

One pass over the instance's children, with a cursor into the placeholder list. Every placeholder names a distinct tag, so a tag identifies its slot and nothing backtracks.

validate(shape, instance):
    slots = [{tag, required, repeatable, seen: 0} for placeholder in shape]
    at    = 0

    for child in instance.children where tag starts with the family prefix:
        if child.tag != slots[at].tag:
            ahead = find child.tag in slots after at
            if not ahead:
                error (child.tag in slots before at) ? "out of declared order"
                                                     : "unexpected <child.tag>"
                continue
            for skipped in slots[at+1 .. ahead-1]:
                if skipped.required and skipped.seen == 0: error "missing"
            at = ahead

        slots[at].seen += 1
        if slots[at].seen > 1 and not slots[at].repeatable:
            error "<tag> appears twice; the template declares one"
        checkText(child, slots[at]); checkAttributes(child, slots[at])

    for slot in slots[at ..]:
        if slot.required and slot.seen == 0: error "missing <slot.tag>"

The cursor stays on a slot after matching it, which is what lets a run accumulate. It never moves backwards, so a run cannot have another tag in the middle of it. Contiguity costs no extra code.

Every member of a run meets checkText and checkAttributes, so a figure with twelve nodes checks twelve data-at values rather than one.

What the corpus says about turning this on

A probe over all 903 instances maps each one's family-prefixed children onto its template's placeholder sequence. Two results, and they point opposite ways.

Not one instance has a run that another tag interrupts. The repeat half therefore lands with nothing in the corpus to repair.

31 instances sit out of their template's field order. All 31 are knowledge nodes and the disorder is always in the tail, because field() in knowledge update ends in root.appendChild(el). A field that a later update adds lands last, so a node's field order records which flag arrived when.

The order of work

Three steps, and the sequence matters.

First, repeatable and duplicate detection. This stands alone, closes the duplicate gap across every family, and needs no repair pass.

Second, field() inserts at the position its template declares instead of appending. This means knowledge update has to resolve the data-conforms-to it already writes into every node, which it does not do today.

Third, repair the 31 and turn the order half on. Doing this before the second step only postpones the drift to the next update. Doing it before the first step gains nothing.

The repair belongs in a command beside the gate rather than inside it, the way comments check and comments autofix already split. A gate that repairs what it measures stops reporting.

A wrapper element such as <template-list>. template.template.html commits to turning the existing skeleton into a schema without adding any new wrapper elements, and cardinality belongs to a placeholder rather than to a container around it.

A word saying whether a tool may sort a run. It would gate autofix and nothing else, and no command sorts a run.

Uniqueness within a run. A figure with two nodes sharing an id stays valid here. That is a job for an audit, which can see the whole document, rather than for a placeholder.

Conformance for a figure. Nothing in this spec reaches a figure until a figure-graph declares data-conforms-to, and the question of how an instance lives inside a host document is its own piece of work.

A compositor that lets placeholders appear in any order relative to each other, the way XML Schema's xs:all sits beside its xs:sequence. The case for it is a figure that narrates its graph, a node and then the edge leaving it and then the node that edge arrives at, which strict sequence rejects. Every figure in the corpus groups its nodes before its edges, so nothing needs it yet.

Links sit outside the schema entirely. The unexpected-child check only looks at tags carrying the family prefix, so an <a data-rel> edge inside a knowledge node meets no placeholder and no constraint. A template cannot say that a node may carry edges, how many, or which relations, and this work makes that absence easier to see rather than closing it.

Whether required on a repeatable placeholder reads clearly as one or more. It composes correctly and it may still mislead someone scanning the template, since required everywhere else means exactly one.
