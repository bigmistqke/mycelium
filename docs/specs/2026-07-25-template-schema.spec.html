template.template.html: schema-via-attributes for template files, replacing hand-written validators implemented 2026-07-25

Every type declared in knowledge.template.html (six types) and spec.template.html (one type) states its own shape three times over, in three places that can silently drift apart:

  • Prose ("Fields: title, confidence, status, optional detail…")
  • A <template id="…"> skeleton of empty placeholder tags, for documentation/copy-paste
  • A hand-written <script data-validates> check() function re-encoding the same required/pattern/enum rules in JS — ~20–30 near-identical lines per type, ~180 lines total across all seven

Nothing machine-readable ties these together. A tool wanting to answer "what fields does knowledge-goal require, and what values does knowledge-status allow?" has no structured place to read that from today — it would have to scrape prose or parse validator JS. This is what blocks the LLM-context overview command from showing field-level detail. It's also why this work was promoted from a deferred idea to a prerequisite — it had already been named as explicitly out of scope in the virtual-module-imports spec.

The schema lives on the existing <template>, not in new elements

No new wrapper elements (no <template-type>, no <template-field>). The field placeholders already sitting inside each type's <template id="…"> gain three optional attributes directly: 

<template id="knowledge-goal">
  <knowledge-goal>
    <knowledge-title required></knowledge-title>
    <knowledge-confidence required pattern="^\d+$"></knowledge-confidence>
    <knowledge-status required enum="pending active completed rejected"></knowledge-status>
    <knowledge-prompt></knowledge-prompt>
    <knowledge-detail></knowledge-detail>
  </knowledge-goal>
</template>
  • required — boolean attribute; the field must be present with non-empty text.
  • pattern — a JS regex source, tested against the field's trimmed text.
  • enum — a whitespace-separated list of the only exact values the field's trimmed text may take.
  • A field with none of the three is optional and free-form — any content, or omitted entirely — but if present, still can't be empty (the existing uniform "present but empty — omit it instead" rule).
  • The full set of field tags declared inside a type's <template> is its allowed set — any instance field not among them is rejected, same as every hand-written validator's current "unexpected <tag>" check.

Full rationale and the happy-dom verification behind this shape: a <template>'s children live in .content, a separate inert DocumentFragment — reading a field's attributes means tpl.content.querySelector(…), not tpl.querySelector(…) directly, and required needs hasAttribute rather than a truthy getAttribute check (present-but-boolean reads back as '').

template.template.html: vocabulary + one generic validator, not a new instantiable type

template.template.html does not declare a <template id="…"> of its own, and no data-conforms-to is added to any other file's <template> elements to mark them as conforming to it. Unlike the growing docs/knowledge/*.html instance corpus, there are only ever a handful of *.template.html files, hand-authored, never mixed — the .template.html filename suffix is already sufficient signal that a file follows this convention, the same way it already signals "this file is a template family" today. Nothing here needs crawler enforcement.

What the file does hold: prose documenting the required/pattern/enum vocabulary above, and one generic validator function, exported the same id-addressable way knowledge.template.html's own extractGraph already is (#extract-graph), for real cross-file import under Node. Given a type's <template> element and a real instance element, it performs exactly the four checks above — required, pattern, enum, unexpected/empty-optional-field — generically, for any type, from its own markup alone.

Full replace: the seven hand-written validators are deleted

Checked against all seven existing check() functions (the six knowledge-* types plus spec-doc): every rule any of them encode — required fields, confidence's 0–100 range, status's enum, the empty-optional-field rule, the unexpected-tag check — is already expressible in the vocabulary above. So this migration adds the attributes to all seven <template> skeletons and deletes all seven <script data-validates> blocks; the crawler falls back to the generic validator whenever a template has no hand-written one. The engine's checking order is schema-first: the generic check always runs, and a hand-written data-validates script — still fully supported, for any future type whose validation genuinely can't be expressed as required/pattern/enum — runs afterward as additional validation on top of it, never as a replacement for it.

This is a real behavior change to the crawler (validate.ts/utils.ts), not just a new file: template discovery currently treats a template with no paired data-validates script as a hard failure ("no template found"); it needs a fallback path to the generic validator instead, used both by validate.ts's whole-corpus pass and by utils.ts's validateInstance() (the single-element path run.ts's add/update commands call).

  • Reverse-DNS-style filename inference for docs/knowledge/*.html instance files (inferring data-conforms-to from a slug.type.family.html naming convention instead of declaring it) — a separate, bigger change to the crawler's "protocol-only, doesn't know about filenames" contract, touching the whole existing instance corpus. Logged as its own deferred observation.
  • template.template.html being self-conforming (a "template of templates") — it isn't a node type with real instances, so there's nothing for self-conformance to actually check.
