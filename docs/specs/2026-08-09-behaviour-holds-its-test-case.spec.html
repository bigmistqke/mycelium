A behaviour holds the case that proves it draft 2026-08-09

A behaviour states a claim in one sentence and nothing in its own document can falsify it. The case that checks it sits in another directory, in another family, reached by an edge. Two audits exist to police that edge, and a third pair of audits describes properties of the document holding the case.

The corpus says the two are one thing already. The canon documents declare 80 behaviours, the test documents declare 80 cases, and every case carries exactly one depends_on. That bijection came partly out of retrofitting, so it is evidence about fit rather than a rule anybody wrote.

A test document also repeats what the specification above it already declares. test-subject names the file a document exercises, and the specification names that same file with specifies. One of the two is a second copy, and this project treats a second copy as drift waiting to happen.

The drawing shows the third symptom. It lays out axioms, behaviours, cases and declarations as four columns, and the canon template's own prose calls that a chain running axiom, then behaviour, then test, then implementation. No edge ever ran from a case to a declaration, so every wire out of the last column doubles back over the case column to reach a behaviour two columns away.

Both citations point at the behaviour because both answer to it. A declaration does not answer to a test, and a case and a declaration sit at the same height, so an edge between them would have no up to point at. The layout is wrong about the shape, and the shape is worth changing.

The shape

A case becomes a declared child of the behaviour it checks:

<canon-behaviour id="exits-non-zero-on-any-failure">
  <canon-title>validate exits non-zero when any check fails.</canon-title>
  <a data-rel="depends_on" href="./root.canon.html#a-gate-people-ignore">…</a>
  <test-case id="one-failing-instance-fails-the-run">
    <test-name>a corpus with one bad instance exits non-zero</test-name>
    <test-status>PENDING</test-status>
    <test-fixture>…</test-fixture>
    <script type="mycelium/test">…</script>
  </test-case>
</canon-behaviour>

The child is required and repeatable. Required is the whole point: a claim nothing can falsify is prose, and the template says so rather than an audit finding out later. Repeatable keeps the door open for several cases per behaviour, which nothing forbids today and which the flat count hides.

test-case keeps its name, its id, its name field, its PENDING status, its optional message, its fixture and its script. It loses the depends_on edge, since the element holding it is the answer that edge used to give.

test-doc goes, and test-title and test-subject go with it. The specification names the subsystem and each behaviour names its claim, so the document layer carries nothing the two ends do not already say.

What the audits become

Two die outright. exhaustive asked whether every behaviour has a case, which a required child answers in the schema. cited asked whether every case names a behaviour, which containment makes unaskable — a case has nowhere else to live.

That follows the axiom that a declaration carries the whole contract. A cardinality an audit enforces is a cardinality the template failed to state.

test-cases-carry-a-script becomes the required attribute the placeholder already carries, so it dies too. test-documents-pick-one-runner and test-documents-load-the-runner survive, reworded, and now describe a canon document. Both hold: all four figure test documents cite figure.canon.html and carry browser cases, and every other document carries node cases, so one runner covers each canon today.

Three worked examples in canon.template.html go with the audits that used them: sample-untested-behaviour, sample-uncited-case, and whichever half of sample-freelancing-behaviour the surviving grounded does not need.

Where a run walks

test run lists tests today, in two places. It lists canon instead, and finds cases through canon-behaviour rather than through test-doc. The node-first ordering stays, so a run with no browser cases still never starts Chrome.

A browser canon document loads test.element.js and reports itself. Opening figure.canon.html then shows the subsystem's claims turning green one at a time, which is the strongest form of what this change argues: prose becomes a promise once something in the same document can falsify it.

PENDING stays the only verdict a file may hold, and the schema keeps enforcing it. A run belongs to a run.

Reading a canon document

This is the cost, and it needs a decision rather than a discovery. The comments canon holds 21 behaviours; folding puts 21 fixtures and 21 scripts between them, and the figure fixtures carry real markup. A document whose job is to list what a subsystem promises would turn into mostly test code.

canon.template.css collapses each case behind a <details>, closed, so the default reading stays one line per claim. A reader who wants the proof opens it, the same gesture the chain page already uses for a declaration's comment and code.

canon generate chain gains nothing here and loses a rank, which the next section covers. For a plain enumeration, test list keeps working and prints claims with their cases beneath them.

What the drawing loses

The chain drops to three ranks: axioms, behaviours, implementation. Every edge then crosses exactly one rank, nothing doubles back, and the sentence calling the chain a sequence becomes true.

A behaviour box carries its case count, since the cases no longer have a column of their own. A behaviour with four cases and a behaviour with one look different, which is the same question the reach numbers already answer one rung up.

The migration

Eleven documents hold 80 cases, and each case moves into the behaviour its edge already names. The edge names it unambiguously, so a script can do the move: read the citation, find the behaviour, cut the element, drop the anchor.

Every href inside a moved case shifts by one directory, since docs/tests/ and docs/canon/ sit at the same depth but a fixture path written from one does not resolve from the other. The every-link-resolves audit catches whatever the move gets wrong, which is the check earning its place.

The order of arrival matters. The template change lands first, then the migration, then the audit removals, then the drawing. A run that goes red between two of those steps teaches people to skip the gate, and this project has watched that happen.

A case still has no add command, and should not get one. Its substance is a fixture and a script, neither of which fits on a flag, so hand-authoring stays right for this one thing.

A code citation keeps pointing at the behaviour. It does not move to the case, and a case does not gain a citation to code. Both answer to the claim, and which cases cover a declaration stays a join through the behaviour rather than a stored edge.

Nothing here changes what a behaviour may claim or how it names its axiom. The upward edge, the id pattern and the one-line title all stay as they are.

Where the eleven test titles go. They group cases inside one subsystem — validate fails the build and says why covers a subset of validate's behaviours — and a flat list of 19 behaviours loses that. Dropping them is the cheap answer, and a grouping element inside a specification is the honest one, at the cost of a new type.

What happens to the fixture canon documents the chain tests build. Those cases construct sample canons in a sandbox, and after this change a canon document holds the source for canon documents. Nothing breaks, since a fixture sits inside a script as a string, but a reader meets it in a surprising place.

Whether one runner per canon should stay a rule or become a rule about one runner per behaviour. Today the split falls along subsystem lines by accident, and a subsystem that genuinely needs both would have to split its canon.

How much a stylesheet may hide before a document stops being honest. A closed <details> keeps the claims scannable, and it also makes a behaviour with no real assertion in it easy to miss.
