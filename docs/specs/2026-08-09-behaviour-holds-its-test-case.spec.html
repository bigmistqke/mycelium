A behaviour holds the case that proves it draft 2026-08-09

A behaviour states a claim in one sentence and nothing in its own document can falsify it. The case that checks it sits in another directory, in another family, reached by an edge. Two audits exist to police that edge, and two more describe properties of the document holding the case.

The corpus says the two are one thing already. The canon documents declare 80 behaviours, the test documents declare 80 cases, and every case carries exactly one depends_on. That bijection came partly out of retrofitting, so it is evidence about fit rather than a rule anybody wrote.

A test document also repeats what the specification above it already declares. test-subject names the file a document exercises, and the specification names that same file with specifies. One of the two is a second copy, and this project treats a second copy as drift waiting to happen.

The eleven test titles carry something the canon does not. validate fails the build and says why groups five of validate's nineteen behaviours, and nothing checks it, because a document title is prose. The grouping is real and the canon has no way to hold it.

The drawing shows the next symptom. It lays out axioms, behaviours, cases and declarations as four columns, and the canon template's own prose calls that a chain running axiom, then behaviour, then test, then implementation. No edge ever ran from a case to a declaration, so every wire out of the last column doubles back over the case column.

Both citations point at the behaviour because both answer to it. A declaration does not answer to a test, and a case and a declaration sit at the same height, so an edge between them would have no up to point at. The layout is wrong about the shape, and the shape is worth changing.

One more constraint turns out to belong to the command rather than to the corpus. A test document's cases must all run in the same place, because the command reads one kind per file and opens the whole file one way. The script type on each case already says which runtime hosts it.

The shape

A case becomes a declared child of the behaviour it checks:

<canon-behaviour id="exits-non-zero-on-any-failure">
  <canon-title>validate exits non-zero when any check fails.</canon-title>
  <test-case id="one-failing-instance-fails-the-run">
    <test-name>a corpus with one bad instance exits non-zero</test-name>
    <test-status>PENDING</test-status>
    <test-fixture>…</test-fixture>
    <script type="mycelium/test">…</script>
  </test-case>
</canon-behaviour>

test-case keeps its name, its id, its name field, its PENDING status, its optional message, its fixture and its script. It loses the depends_on edge, since the element holding it is the answer that edge used to give.

test-doc goes, and test-title and test-subject go with it. The specification names the subsystem, so the subject repeats it; the title becomes a behaviour, which the next section covers.

A behaviour narrows a behaviour

A behaviour gains itself as a declared child, so a broad claim holds the narrower ones that make it up:

<canon-behaviour id="the-gate-fails-and-says-why">
  <canon-title>validate fails the build and says why.</canon-title>
  <canon-behaviour id="exits-non-zero-on-any-failure">…</canon-behaviour>
  <canon-behaviour id="prints-every-failure-before-exiting">…</canon-behaviour>
</canon-behaviour>

This needs no new type, because an axiom already narrows an axiom and reach through a narrower axiom counts. A behaviour narrowing a behaviour is that same shape one rung down, and the walk that finds an axiom beneath an axiom finds this too.

A child names no axiom of its own. Its parent names one, and the reach walk goes as far as it needs, so the citation sits where the claim genuinely narrows.

Containment carries the parent rather than an edge, since the grouping earns its place by showing up when somebody reads the document. Containment gives a tree, and every claim in the corpus has exactly one parent today — 91 with one citation and 5 with none. The depends_on edge stays declared beside the nesting, so a behaviour narrowing two others still has somewhere to say so.

What proves a behaviour

A behaviour carries at least one case or at least one child behaviour. A leaf claim earns a case, and a claim made of narrower claims takes its proof from them.

The schema states the pair and the grounded walk needs no change to see it. That replaces the audit asking whether every behaviour has a case, which is cardinality the declaration can hold — the axiom that a declaration carries the whole contract says to put it there.

Which runtime runs a case

A case's script type picks its runtime, and nothing larger picks anything. mycelium/test means a sandbox on disk, and text/mycelium-test means a page in a browser. The run groups every case in the corpus by that label and makes one pass per runtime.

So the audit demanding one runner per document goes. The first subsystem needing both is the one this change lands in: the chain canon holds three checks a sandbox settles and two drawing claims only a page can, since the disclosure the drawing builds exists once the page runs.

A browser page then meets cases it cannot host. It has to leave them alone and show that it did, rather than letting a node case read as still working — PENDING that never resolves looks exactly like a page still thinking.

A fixture is not a claim

A browser case writes its fixture as real markup, and after this change that markup sits inside a canon document. A figure fixture holds figure elements and nothing notices. A chain fixture holds canon elements, and readCanon would count them as claims the project makes.

That reaches further than the drawing. readCanon feeds grounded, so a fixture axiom would arrive as a real axiom nothing derives from, and the gate would fail on a claim nobody made.

Every reader of the canon skips anything inside a test-fixture. The drawing already skips a template's worked examples by asking whether the document declares a template, and this is the same exemption one level in.

What the audits become

Four go. exhaustive and cited both police the joint that containment makes unbreakable, since a case now has nowhere else to live. test-cases-carry-a-script becomes the required attribute the placeholder already carries. test-documents-pick-one-runner goes with the constraint it enforced.

test-documents-load-the-runner survives, reworded. A canon document holding any browser case loads test.element.js, or its cases render as a list that reads PENDING and always will.

Three worked examples in canon.template.html go with the audits that used them: sample-untested-behaviour, sample-uncited-case, and whichever half of sample-freelancing-behaviour the surviving grounded does not need.

Where a run walks

test run lists tests today, in two places. It lists canon instead, and finds cases through canon-behaviour at any depth rather than through test-doc. Node cases still run first and alone, so a run with no browser case never starts Chrome.

PENDING stays the only verdict a file may hold, and the schema keeps enforcing it. A result belongs to a run.

Reading a canon document

This is the cost, and it needs a decision rather than a discovery. The comments canon holds 21 behaviours; folding puts 21 fixtures and 21 scripts between them, and the figure fixtures carry real markup. A document whose job is to list what a subsystem promises would turn into mostly test code.

canon.template.css collapses each case behind a closed <details>, so the default reading stays one line per claim. A reader who wants the proof opens it, the same gesture the chain page already uses for a declaration's comment and code.

Nesting helps here rather than hurting. A canon document that used to list 19 flat behaviours lists 5 broad ones, each opening onto its own, which is the structure the eleven titles were carrying informally.

What the drawing gains

The chain drops to three ranks: axioms, behaviours, implementation. Every edge then crosses exactly one rank, nothing doubles back, and the sentence calling the chain a sequence becomes true.

Behaviours rank by depth the way axioms already do, so a narrowing behaviour sits one column right of the one it narrows. A behaviour box carries its case count, since the cases lose their column, and a behaviour with four cases looks different from one with one.

The migration, in order

Eleven documents hold 80 cases, and each case moves into the behaviour its edge already names. The edge names it unambiguously, so a script can do the move: read the citation, find the behaviour, cut the element, drop the anchor.

Every href inside a moved case shifts by one directory, since docs/tests/ and docs/canon/ sit at the same depth but a fixture path written from one does not resolve from the other. The every-link-resolves audit catches whatever the move gets wrong.

The template change lands first, then the migration, then the eleven titles as parent behaviours, then the audit removals, then the drawing. A run that goes red between two steps teaches people to skip the gate, and this project has watched that happen.

A case still has no add command, and should not get one. Its substance is a fixture and a script, neither of which fits on a flag, so hand-authoring stays right for this one thing.

A code citation keeps pointing at the behaviour. It does not move to the case, and a case does not gain a citation to code. Both answer to the claim, and which cases cover a declaration stays a join through the behaviour rather than a stored edge.

Nothing here changes how an axiom works. The axiom rank, its own nesting and its detail field all stay as they are, and a behaviour still reaches an axiom rather than replacing one.

A case keeps the script type it carries today. mycelium/test and text/mycelium-test name one idea two ways, which is a concept this project pays for on every reading, and a separate decision weighs the candidates. It waits because this change already rewrites eighty tags and moving the same eighty twice buys nothing.

Whether all eleven titles survive becoming claims. A parent behaviour has to be falsifiable like any other, and What validate hands an audit, and which tree it reads names a topic rather than making an assertion. Some will reword cleanly and some may turn out to be table of contents entries with nothing to say.

Whether a parent behaviour may also carry its own case. Allowing both costs nothing in the schema and gives a broad claim an end-to-end check above its parts. Forbidding it keeps one clean rule about where proof lives.

How a page shows a case it cannot host. Hiding a node case understates what the document claims, and showing it greyed asks a reader to know why. Neither answer is obvious and the page is the only report a browser case has.

Whether behaviour depth should rank into columns or nest inside one box. Columns reuse what the axiom rank already does and spread a deep subsystem across the page. Nesting keeps a subsystem together and makes the rank's widths uneven.
