A behaviour holds the check that proves it implemented 2026-08-09

A behaviour states a claim in one sentence and nothing in its own document can falsify it. The check that settles it sat in another directory, in another family, reached by an edge. Two audits existed to police that edge, and two more described properties of the document holding the check.

The corpus said the two were one thing already. The canon documents declared 80 behaviours, the test documents declared 80 cases, and every case carried exactly one depends_on. That bijection came partly out of retrofitting, so it was evidence about fit rather than a rule anybody wrote.

A case also had nothing of its own to say. Counted before deciding: 61 of the 80 case names repeated their behaviour's title word for word, 12 overlapped substantially, and the 7 that read differently said the same thing in scenario voice. That last group is the worst kind of second copy, because it reads like new information.

Fifteen test titles carried something the canon could not hold. validate fails the build and says why groups five of validate's nineteen behaviours, and nothing checked it, because a document title is prose.

The drawing showed the last symptom. It laid out axioms, behaviours, cases and declarations as four columns, and called that a chain running axiom, then behaviour, then test, then implementation. No edge ever ran from a case to a declaration, so every wire out of the last column doubled back over the case column.

One further constraint turned out to belong to the command rather than to the corpus. A test document's cases all had to run in the same place, because the command read one kind per file and opened the whole file one way.

The shape

A leaf behaviour carries the check that falsifies it, with no wrapper around it:

<canon-behaviour id="exits-non-zero-on-any-failure">
  <canon-title>validate exits non-zero when any instance or audit fails.</canon-title>
  <a data-rel="depends_on" href="./root.canon.html#a-gate-people-ignore">…</a>
  <canon-verdict>PENDING</canon-verdict>
  <canon-fixture>…</canon-fixture>
  <script type="mycelium/test">…</script>
</canon-behaviour>

There is no case element and no case title, because the measurement said a case name restates the claim above it. The behaviour is the test. Its id is the one id, its title is the one title, and canon-verdict holds the PENDING that a run replaces in the page.

One check per claim therefore holds by construction rather than by count. A claim wanting two checks is two claims, which is the decomposition a broad claim already gets.

A behaviour narrows a behaviour

A behaviour holds the narrower behaviours that make it up, so the grouping fifteen document titles carried informally becomes a claim the canon states and the children prove.

This needed no new type, because an axiom already narrows an axiom and reach through a narrower axiom counts. The walk that finds an axiom beneath an axiom finds this too.

Containment carries the parent rather than an edge, since a grouping earns its place by showing up when somebody reads the document. Containment gives a tree, and every claim in the corpus has exactly one parent — 91 with one citation and 5 with none. The depends_on edge stays declared beside the nesting for the claim that eventually narrows two.

What proves a behaviour

A behaviour carries a check, or child behaviours, and exactly one of the two. A leaf earns a check, and a claim made of narrower claims takes its proof from them.

A hand-written validator holds this, because the schema states cardinality and has no word for a choice. Neither side of the rule is a gap the schema can see: a claim with no check and no children is unproved, and a claim with both has two kinds of proof and no rule saying which answers for what.

canon add behaviour requires --check, reading the script from stdin the way --detail already does. That is the same argument as an axiom's required reasoning, one rung down, and it is what keeps a claim from ever arriving unproved — the command creating it is the last place able to insist.

Which runtime runs a check

A check's script type picks its runtime and nothing larger picks anything. mycelium/test means a sandbox on disk and text/mycelium-test means a page in a browser. The run groups every check by that label and makes one pass per runtime.

So the audit demanding one runner per document went with it. The chain canon needs both already: three checks a sandbox settles, and two drawing claims only a page can, since the disclosure the drawing builds exists once the page runs.

A fixture is not a claim

A browser check writes its fixture as real markup, and that markup now sits inside a canon document. A figure fixture holds figure elements and nothing notices. A chain fixture holds canon elements, and the canon reader would count them as claims the project makes.

That reaches further than the drawing, since the same reader feeds grounded: a fixture axiom would arrive as a real axiom nothing derives from, and the gate would fail on a claim nobody made. Every reader of the canon skips anything inside a canon-fixture.

What the audits become

Four go. Every behaviour has a case and every case cites a behaviour both police a joint that containment makes unbreakable. Every case carries a script becomes the schema's own required. And one runner per document goes with the constraint it enforced.

One survives, reworded: a canon document holding any browser check loads test.element.js, or its checks render as a list reading PENDING that always will.

Where the runner lives

The runner is mycelium canon test, merged into the canon command host. It queries canon-behaviour, canon-verdict and canon-fixture directly, and a check lives with its vocabulary settles where that belongs.

An earlier draft put it beside validate, reasoning from a resemblance: both exit non-zero and both are what a build runs. The resemblance is real and the axiom is better evidence, since validate is generic over every template and knows no family's tags at all.

test.template.html declared no types once its family dissolved, so it went too. Every link naming it now reaches the file holding what it described, which is what move already does for a claim.

What the drawing gains

The chain drops to three ranks: axioms, behaviours, implementation. Every edge crosses exactly one rank, nothing doubles back, and the sentence calling the chain a sequence is true.

Behaviours rank by depth into columns, the way axioms already do, so a narrowing behaviour sits one column right of the one it narrows. The header sticks at the left edge, since the number of columns stopped being fixed at four. A behaviour box carries whether it holds a check.

The migration

Fifteen documents held 80 checks, and each moved into the behaviour its edge already named. The five helper modules those checks import moved with them, and nothing remains under docs/tests/.

The move ran through a parser. An early attempt used indentation to decide which tag was a field and which was a string inside a script, and it renamed opening tags while leaving their closing tags behind, across six documents. The rewrite asks parse5 which elements are children and asks source ranges where to cut, so every script survived byte for byte.

The template change, the migration and the audit removals are one commit rather than three. The gate is red between any two of them, since a check that has left its document but not yet reached its claim satisfies nothing.

A check still has no add of its own beyond --check on the behaviour. Its substance is a fixture and a script, and a fixture does not fit on a flag, so a browser check stays hand-authored after the claim exists.

A code citation keeps pointing at the behaviour. Both a check and a declaration answer to the claim, and which checks cover a declaration stays a join through the behaviour rather than a stored edge.

Nothing here changes how an axiom works. The axiom rank, its own nesting and its detail field all stay as they are.

A check keeps the script type it carries today. mycelium/test and text/mycelium-test name one idea two ways, and a separate decision weighs the candidates for a follow-up.

Nothing creates a grouping. canon add behaviour makes a leaf and requires a check, and turning existing leaves into children of a new parent moves elements rather than adding one. The eleven parents the fifteen titles become need either a command or a hand edit, and this project prefers the command.

How a page shows a check it cannot host. Hiding a node check understates what the document claims, and showing it greyed asks a reader to know why. The page is the only report a browser check has, so guessing at this is worse than waiting.

Whether the two rewritten parents hold together. The scope title and the knowledge add title each cover one child that does not narrow them, and both fixes rest on reading four claims and three claims carefully.
