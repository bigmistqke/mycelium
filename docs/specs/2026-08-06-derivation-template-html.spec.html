derivation.template.html: axioms, specifications, and a chain a checker can walk draft 2026-08-06

This project can say what shape a document takes and whether its prose obeys the rules. It cannot say why the system took the shape it has, nor whether the code answers to anything.

Three gaps sit under that. The graph has held options and decisions since January without ever holding the criterion that settles them, so a rationale lives in prose inside a decision or it lives nowhere. No document states what the system does in a form a test can cite, so nothing connects a running test to a claim about behaviour. And with nowhere for a principle to live, nothing can show that one subsystem assumes one thing while another assumes something incompatible: each part stays internally consistent, neither part is a bug, and the disagreement never surfaces.

A methodology already exists for this, and another project applied it by hand: a chain running from an axiom, to a specification of behaviour, to a test, to an implementation. That project also found that an agent does not hold to such a discipline on trust, and made the citations structured text so a checker could answer whether the protocol held. The observation recording that is what this design responds to.

The chain runs in both directions, and that is the methodology rather than a property of it. Implementation flows down: an axiom settles what a specification should say, a specification says what a test should check, a test says what an implementation should do.

Findings flow up. A problem the chain did not predict is not faulty code by default, because it means either that no behaviour speaks to the case, or that two behaviours want different things and someone had to pick one. So a fix has an altitude, and patching the code alone leaves the hole that produced it. The observation recording that carries the argument.

The upward direction is also how this reaches a project already running. A codebase carries principles nobody wrote down, sitting in its maintainers' habits and sometimes visible in how the project describes itself. Reading those out of the code is the same operation, run the other way.

Two types in one family file

docs/templates/derivation.template.html declares derivation-axiom and derivation-specification, with derivation-behaviour nested inside the second. One file, because the types only mean anything together, which is the same reason six knowledge types and four plan types each share a file. The decision recording this carries the alternatives it beat.

The name is not new. Tests cite, they are not nodes refers to a hypothetical derivation-* family, so the family had a name in July and gets a file now.

Instances carry no date

Both types describe what holds now. An axiom that stops being true gets revised or retired, and a specification that no longer matches the system is a bug in one of the two. Neither belongs to the exploration that produced it, which is the argument language.template.html already made when it dropped the date prefix its siblings carry.

So docs/derivation/axioms/<slug>.axiom.html and docs/derivation/specifications/<slug>.specification.html, and add takes no --date flag.

What an axiom is for

An axiom decides which options are good. It is the standing criterion someone appeals to when two designs both work and one of them is right, which is a job nothing in this corpus does today.

An axiom carries a confidence, the way every knowledge node does. Someone who commits to a principle and someone who infers one by reading a codebase produce the same shape of document, and the second is the likelier misreading. Without the field nothing tells the two apart, which matters most in exactly the case this design wants to serve.

Axioms compose by refinement. A subsystem's axiom links up to the general one it narrows, and that edge is the whole mechanism, with no region names, no scope attribute and no cascade. Asking which axioms govern a subsystem is a walk upward from its own.

What this gives up, and the decision says so: a broad axiom nobody has read down into a given subsystem reaches nothing in it, and no check separates that from an axiom that does not apply there. Writing that reading is the work, and a mechanism that asks for it is a mechanism that gets it written.

What a specification is for

A specification states what one subsystem does, as a list of behaviours that each carry an id. The id is the point. A test cites one behaviour, and a behaviour without an address can only be cited as part of a whole document, which is not enough for anything downstream to count.

A behaviour marks itself as a requirement or as context, the way RFC 2119 keywords do in a standards document. That answers what counts as a behaviour by a word in the prose rather than by anyone's judgement, and a countable list is what exhaustiveness needs before it means anything.

Each specification links up to the axioms it serves. Each behaviour sits inside a specification and inherits that.

Where the rungs live

The chain runs axiom, then specification behaviour, then test, then implementation, and the last two get no document. Tests cite, they are not nodes settled that in July: a test is a citation target read out of real source, the way a commit is a field rather than a re-hosted node.

Real source is not only src/. Eight documents in this corpus hold their own implementation inside a <script type="mycelium/…"> block: each command lives in its .command.html, and each audit lives in the template file whose type it checks. So an implementation rung is a TypeScript file some of the time and a script block inside a document the rest of the time, and the audit reader already parses the second kind.

A citation from a plain source file is an href in a comment, in a file that is not HTML. This corpus already reaches into src/: the audit filesystem is rooted one level above docs/ for exactly this reason, and both the comments command and the prose audit read source today.

The test rung has no home here at all. This repository ships no tests and no test runner, and package.json declares mycelium, typecheck and check-scripts and nothing else. The audits are the nearest thing to tests it has, and they check documents rather than code. That leaves the design intact and says where the work lands: the first specification about this project will cite tests that someone writes first.

The order of work, which the rungs also describe

Read downward the chain says what the system is, at whichever altitude you cut it. Read forward it says what to do next: state the behaviour, stub the implementation so the types check, write tests against that stub and watch every one fail, then fill the implementation in until they pass.

The bottom rung arrives twice, its shape before the tests and its body after. So a gate cannot ask whether the rung above is finished. It asks a narrower question: a signature before a test is the method working, and a body before a test is the method skipped.

What gets checked

Four audits, and the first of them is a repair to something that already exists.

  • Fragments resolve. The current every-link-resolves splits the fragment off before testing a path, so a citation to #behaviour-3 passes whether or not anything carries that id, and a citation carrying nothing but a fragment leaves an empty path that the same function skips outright. Every citation in this chain is a fragment citation, so this audit is the ground the rest stands on. It is two jobs rather than one: the check has to look inside the target document for the id, and it has to see citations in files that are not HTML, which the current pass neither lists nor parses. AuditFs.read takes any path, so the second job needs no new interface.
  • Grounded. Every axiom reaches a behaviour beneath it, and every specification reaches an axiom above it. An axiom with nothing under it is a belief nobody acted on.
  • Exhaustive. Every behaviour marked as a requirement has a test citing it. A behaviour marked as context does not, and that exemption is the only thing the marking does.
  • Cited. Every test cites a behaviour. This is the one that closes the loop: a test citing nothing is a claim about the system that no specification makes, so either a behaviour is missing above it or the test checks something nobody meant to promise.

An earlier form of Grounded also asked that every behaviour reach a test. That duplicated Exhaustive from the other side and quietly overrode it, since Exhaustive exempts a context behaviour and Grounded did not, which left the requirement marking with no effect on any check. Grounded now covers the joint between an axiom and a specification, and Exhaustive and Cited cover the two directions of the joint between a specification and a test. The observation that all three ran one way is where Cited comes from.

None of the four names a rung inside src/. The engine learns the chain by reading this family's own declarations, because a checker that hardcodes its ontology is the divergence already recorded from the way this project works.

An unfinished chain is an ordinary error

A behaviour with no test, an axiom with nothing under it, a test citing nothing: each is a violation, each fails validate, each contributes to a non-zero exit. Nothing marks a chain as in progress, no flag softens a check into advice, and no separate command reports these apart from the rest.

The argument against that ran: non-zero is this family's normal state. You write a chain in order, behaviour then stub then failing tests then an implementation, so every intermediate moment has a gap in it, and an axiom read out of an existing codebase waits a long time before anything sits beneath it. Checks whose expected value is never zero look unlike dangling-outcome, where zero is the answer and anything else means someone slipped.

That difference is real and it is not the checker's business. Everything in this corpus is a declaration, and every audit reports where reality does not match one, so you declared an outcome and nothing causes it and you declared a required behaviour and nothing tests it are the same sentence.

These are type errors: they say the thing does not match what someone declared, and a person can ignore them the way a type error does not stop code from running. A non-zero exit is communication, not permission. The decision records what this rules out.

What follows is that the message carries the weight. Behaviour 3 has no test only scolds. Naming the specification, the axiom that behaviour serves, and what nothing currently checks turns the error into the next thing someone writes.

The entailed check, and finding a conflict

Whether each step follows from the one above it is a judgement, and nothing here runs a model inside an audit. It stays something a person asks for.

The same holds for the conflict this design is partly aimed at. Two axioms that cannot both hold have somewhere to live, since contradicts is already one of the edge labels and knowledge recover prints contested claims, but nothing finds one. Someone reads both and judges.

Coverage as evidence

A citation from an implementation up to a test is a claim someone wrote, and a run could corroborate it. Wiring a coverage report into the chain is a later question.

Folding the design document into the plan family

A spec and its plan state the same design twice, carry two notions of status, and pair only by filename. That migration would free the shorter word, and it is recorded rather than done. Until then this design writes the long word everywhere.

Writing this repository's own axioms

Mycelium's own axioms and specifications are the point of the exercise, and reading them out of the code is the upward direction rather than cleanup after the fact. They still come second, because writing them needs the family to exist and needs somewhere for the test rung to live. Sequence, not priority.

Which keyword vocabulary marks a requirement, and whether the language family should hold those words as terms the way it holds the rest of this project's vocabulary.

What a citation from source looks like exactly, and whether a comment tag or a plain href in a comment carries it.

Whether every test owes a citation, or only a test at some altitude. A unit test of a small helper may have no behaviour above it that anyone would want to write, and Cited as stated makes no room for that.

Whether a behaviour id has to survive an edit to the behaviour's wording, the way a standards body treats an anchor as permanent, and what enforces that here.

Whether one specification maps to one subsystem, and what names a subsystem given that this project refused a topic vocabulary once already.
