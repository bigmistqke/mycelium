derivation.template.html: axioms, specifications, and a chain a checker can walk draft 2026-08-06

This project can say what shape a document takes and whether its prose obeys the rules. It cannot say why the system took the shape it has, nor whether the code answers to anything.

Two gaps sit under that. The graph has held options and decisions since January without ever holding the criterion that settles them, so a rationale lives in prose inside a decision or it lives nowhere. And no document states what the system does in a form a test can cite, so nothing connects a running test to a claim about behaviour.

A methodology already exists for this, and another project applied it by hand: a chain running from an axiom, to a specification of behaviour, to a test, to an implementation. That project also found that an agent does not hold to such a discipline on trust, and made the citations structured text so a checker could answer whether the protocol held. The observation recording that is what this design responds to.

Two types in one family file

docs/templates/derivation.template.html declares derivation-axiom and derivation-specification, with derivation-behaviour nested inside the second. One file, because the types only mean anything together, which is the same reason six knowledge types and four plan types each share a file. The decision recording this carries the alternatives it beat.

The name is not new. Tests cite, they are not nodes refers to a hypothetical derivation-* family, so the family had a name in July and gets a file now.

Instances carry no date

Both types describe what holds now. An axiom that stops being true gets revised or retired, and a specification that no longer matches the system is a bug in one of the two. Neither belongs to the exploration that produced it, which is the argument language.template.html already made when it dropped the date prefix its siblings carry.

So docs/derivation/axioms/<slug>.axiom.html and docs/derivation/specifications/<slug>.specification.html, and add takes no --date flag.

What an axiom is for

An axiom decides which options are good. It is the standing criterion someone appeals to when two designs both work and one of them is right, which is a job nothing in this corpus does today.

Axioms compose by refinement. A subsystem's axiom links up to the general one it narrows, and that edge is the whole mechanism — no region names, no scope attribute, no cascade. Asking which axioms govern a subsystem is a walk upward from its own.

What this gives up, and the decision says so: a broad axiom nobody has read down into a given subsystem reaches nothing in it, and no check separates that from an axiom that does not apply there. Writing that reading is the work, and a mechanism that asks for it is a mechanism that gets it written.

What a specification is for

A specification states what one subsystem does, as a list of behaviours that each carry an id. The id is the point. A test cites one behaviour, and a behaviour without an address can only be cited as part of a whole document, which is not enough for anything downstream to count.

A behaviour marks itself as a requirement or as context, the way RFC 2119 keywords do in a standards document. That answers what counts as a behaviour by a word in the prose rather than by anyone's judgement, and a countable list is what exhaustiveness needs before it means anything.

Each specification links up to the axioms it serves. Each behaviour sits inside a specification and inherits that.

Tests and implementations stay in source

The chain runs axiom, then specification behaviour, then test, then implementation, and the last two get no document. Tests cite, they are not nodes settled that in July: a test is a citation target read out of real source, the way a commit is a field rather than a re-hosted node.

A citation from source is an href in a file that is not HTML, written as a comment. This corpus already reaches into src/ — the audit filesystem is rooted one level above docs/ for exactly this reason, and both the comments command and the prose audit read source today.

The order of work, which the rungs also describe

Read downward the chain says what the system is, at whichever altitude you cut it. Read forward it says what to do next: state the behaviour, stub the implementation so the types check, write tests against that stub and watch every one fail, then fill the implementation in until they pass.

The bottom rung arrives twice, its shape before the tests and its body after. So a gate cannot ask whether the rung above is finished. It asks a narrower question: a signature before a test is the method working, and a body before a test is the method skipped.

What gets checked

Three audits, and the first of them is a repair to something that already exists.

  • Fragments resolve. The current every-link-resolves drops the fragment before testing a path, so a citation to #behaviour-3 passes whether or not anything carries that id. Every citation in this chain is a fragment citation, so this audit is the ground the rest stands on.
  • Grounded. Every axiom reaches a behaviour, and every behaviour reaches a test. An axiom with nothing under it is a belief nobody acted on.
  • Exhaustive. Every behaviour marked as a requirement has a test citing it. This runs opposite to the citations: a link proves one test exists, and the method wants none missing.

None of the three names a rung inside src/. The engine learns the chain by reading this family's own declarations, because a checker that hardcodes its ontology is the divergence already recorded from the way this project works.

The entailed check

Whether each step follows from the one above it is a judgement, and nothing here runs a model inside an audit. It stays something a person asks for.

Coverage as evidence

A citation from an implementation up to a test is a claim someone wrote, and a run could corroborate it. Wiring a coverage report into the chain is a later question.

Folding the design document into the plan family

A spec and its plan state the same design twice, carry two notions of status, and pair only by filename. That migration would free the shorter word, and it is recorded rather than done. Until then this design writes the long word everywhere.
