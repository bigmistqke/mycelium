Readers treat a hand-copied command list as the whole CLI, so its omissions look like absences 90

CLAUDE.md listed three knowledge commands. The CLI exported eight. The two it never mentioned at all, unlink and del, had been committed the day before in 214439e. A session that needed to redirect a mis-aimed edge read the list, found no way to remove one, deleted and rebuilt the node instead, and then reported the missing unlink as the next real gap in that command family — a confident, specific, checkable claim about the tool, produced entirely from a stale copy of its interface and never checked against the tool itself.

The failure mode is not that the list was incomplete. It is that readers treat a list as exhaustive whether or not it says it is. Prose elsewhere in the same file did mention list and recover, but nobody used them either, which is the same finding the harness manufactures the clutter keeps arriving at from different directions: what the harness puts in front of the agent is what the agent does, and prose sitting beside a code block does not compete with the code block.

So the fix is not a more careful edit. Any hand-maintained copy of a generated thing drifts, and this one drifted in the specific direction that hides capability rather than inventing it — the failure is silent, because a command you never learned about cannot produce an error. mycelium run --help now prints every family and every exported command, read off the same command scripts the engine runs, and the SessionStart hook runs it, so the true roster is present without anyone electing to ask for it.
