The complaint about component diagrams is that they go stale, not that nobody wants them 80

A claim in this session that a component diagram is not what anyone actually wants was wrong. People do want one. You can point at it. Two people arguing get a shared set of coordinates.

Spatial memory is real, and a position on a picture outlasts a name. What people object to is that someone drew it once, it went wrong within a month, and it now sits on a wiki as a lie. That argues for deriving the diagram, not for dropping it.

Deriving it adds four things no hand-drawing can have. Grouping that means something, because things a team decided about together belong together even when they scatter across the tree. Edges that carry different meanings, including must not know about, whose whole nature is being absent from the code.

Several diagrams instead of one, because how data flows and what is safe to change are different pictures. And time, so the same diagram can scrub across the project's life to show where the architecture is moving rather than where it currently sits.

It also stops being decoration. A wiki picture cannot be violated, because nothing knows it exists. A derived one is a claim about the code that can re-run and can fail.
