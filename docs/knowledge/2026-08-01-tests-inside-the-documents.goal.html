A document already carries the code it describes. It does not yet carry anything proving that the description still holds. Prose claiming a command rejects a dated slug stays convincing long after the guard goes away, and no reader can tell.

Two places such a test could run, which answer different questions:

  • In the browser, on open. The document renders its own result beside the claim, so whoever reads the page sees the proof at the moment of reading. DESIGN.html already describes a document whose script runs inline and shows its result, and its worked example does a small version of this.
  • In CI, on push. A failing proof breaks the build the way an audit does, so a claim cannot go stale quietly. This gives every document a visible verdict rather than one buried in a log.

Prior art worth reading first: Ezno writes its test cases as markdown, so one file states the behaviour and supplies the case proving it (kaleidawave.blog/ezno/comparison). The interesting difference here is that a document already knows which type it conforms to, so a proof could attach to a field rather than float in the file.

Two questions this has to answer before it becomes a family. A test needs a home in the vocabulary, and tests cite, not modeled as nodes already decided against modelling tests as graph nodes, so this must sit inside a document rather than beside it. And a proof running in two places risks two answers, which is the drift the corpus exists to prevent.
