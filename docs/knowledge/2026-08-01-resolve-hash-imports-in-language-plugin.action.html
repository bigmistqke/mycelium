Resolve #id imports in the language plugin by rewriting them to relative virtual-file paths 85 completed

Fixes the gap that observation found: a bare #locator import, which src/script-hooks.ts already resolves at run time to the sibling <script> with that id, was always "cannot find module" in the editor, because nothing taught TypeScript's own resolver what the specifier means.

Tried the hook the type signature suggests first — resolveLanguageServiceHost, wrapping resolveModuleNameLiterals on the host it hands back — and wired it up before checking further. It did nothing. Reading @volar/typescript's own createProject.js explained why: right after calling every plugin's resolveLanguageServiceHost, it unconditionally reinstalls resolveModuleNameLiterals itself, built from createResolveModuleName — a plain ts.resolveModuleName wrapper for letting a specifier reach a .html file directly, not a general per-specifier hook. Nothing in the plugin surface survives past project creation.

Moved the fix to the one place that does survive: the virtual file's own text. createVirtualCode already reads every block's raw text to split it into per-block virtual files; it now also scans each block for a module specifier shaped like #locator and rewrites it to a real relative path — ./<html file>.<sibling's block index><.ts or .js> — pointing at that sibling's own virtual file, which TypeScript's ordinary relative-path resolution already understands with no custom resolver at all. A locator matching nothing stays untouched, so "cannot find module" still fires — the same failure mode script-hooks.ts's own resolve() has for a dangling reference.

The rewrite changes the virtual file's length where a locator is replaced, so the single whole-block CodeMapping this plugin used before became several segments, using generatedLengths (a mapping segment's generated side may differ in length from its source side) so a diagnostic on an unresolved locator still lands on the original "#locator" text in the HTML file rather than on where the replacement would have been.

Checked three ways. A block with an untyped type="module" sibling: the "cannot find module" error disappears, replaced by ts(7016) ("implicitly has an 'any' type") — correct, expected TypeScript behavior for importing a plain .js file with allowJs off, not a defect in this. Two mycelium/* siblings, one exporting a typed function and the other calling it with a mismatched type: ts(2322) fires with the real return type threaded across the import, at the right line and column in the HTML file — proof the type information, not just the module resolution, crosses the boundary. The full corpus check against every real document (node editor/check.ts, no arguments) came back byte-for-byte identical to its pre-change output: 9 documents, 182 diagnostics, no regressions from the mapping rewrite.
