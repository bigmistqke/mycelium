happy-dom computes no layout, so no audit can reach the figure engine's geometry 95

The open question on this branch was whether the figure layout engine should be tested by an audit collocated in figure.template.html, or by a new mycelium/test script type. A probe settles part of it: neither can measure anything.

validate parses documents with happy-dom (src/utils.ts). happy-dom implements the DOM but not CSS layout. Given a div with position:absolute; top:10px; left:20px; width:120px; height:40px, getBoundingClientRect() returns {top:0, left:0, width:0, height:0}.

Everything the engine decides — which edges share a connected component, how many lanes a gap needs, which lane sits nearest the source, where a back edge's gutter runs — is computed from measured boxes. Under a zero-rect DOM those inputs are all identical, so any check running there passes on every figure and fails on none.

This does not touch the two audits already in the template. Both read the document rather than its rendering: figure-edges-resolve checks that an edge names cells that exist, and figure-edges-run-the-way-they-claim checks a declared back edge against the cell order. Those are corpus claims, and they work. The gap is the engine's own arithmetic, which is not a corpus claim at all.

So the choice is not audit against test. Either the engine gives up its decisions as a function taking boxes and returning lanes, which synthetic boxes can then drive under happy-dom, or a real browser comes in and tests the drawing itself. The first is reachable from here. The second is new machinery, and nothing else in the repository needs it yet.
