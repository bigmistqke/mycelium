Use parse5 alone for HTML source positions, not jsdom or a domutils/css-select facade 80 active

Autofix's HTML leaf-finding needed exact source offsets that happy-dom (the project's existing parser, via cli.parseHTML) does not track at all, so it fell back to searching for each element's serialized outerHTML with an advancing cursor and slicing tag boundaries by hand. Three ways to close that gap were weighed.

jsdom gives real source locations (dom.nodeLocation(element)) on a genuine, spec-compliant DOM, confirmed working in a spike, but pulls in around twenty dependencies for browser features (fetch, cookies, CSS color and layout, XML serialization) this project, a static-document tool, never touches. Swapping the shared cli.parseHTML to it would mean re-verifying every template and audit against a different DOM implementation for a capability nothing but autofix currently needs.

A parse5 + parse5-htmlparser2-tree-adapter + domutils/css-select stack (what cheerio itself uses internally) would give a real, tested selector engine at a fraction of that weight. Its functions are called as domutils.querySelectorAll(selector, [node]), not as methods on the node. Adopting it directly would require rewriting roughly 260 existing DOM call sites across every template, or building a facade class to preserve the current method-call shape. Either way it is still a second parsing and querying stack living alongside happy-dom, for a query capability happy-dom's existing schema-validation machinery already provides correctly today.

What autofix actually lacks is narrower than a new DOM: given an element happy-dom already found and validated, where is it, in bytes, in the specific source file. parse5 alone, parsed with sourceCodeLocationInfo: true and read as a plain tree, answers exactly that. A plain tree means no DOM, no selector matching, since the leaf walk only tests tag membership against BLOCK_TAGS/PROTECTED_TAGS. A spike confirms exact startTag/endTag offsets. Since nothing is ever re-serialized, entities and unusual markup survive untouched with no round-trip risk. happy-dom keeps doing everything it already does, unchanged, everywhere in the project.

This is exported as a small reusable utility rather than inlined into autofix alone. A second real consumer exists: a live editor diagnostic flagging a schema violation (a missing required child, for instance) in an open document. It would reuse the same existing happy-dom-based validation to find the problem, and would need exactly this same capability: position for an already-identified element to place the diagnostic.
