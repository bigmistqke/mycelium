A peer edge runs straight across the gap between two boxes in one row, from one facing side to the other. No elbow and no lane: a row is as tall as its tallest box, so the line between their middles is already level.

The element reads peer-ness off data-at rather than from a new attribute. That is not the inference data-back replaced, which compared measured boxes; this compares two numbers the figure wrote down, and moving a node to another row edits the document.

assignLanes now skips a peer edge, and nothing visible depends on that. Its channel key would be its own row's bottom and top, which no edge leaving that row can match, so it sat alone in a channel and routePeer never read a lane anyway. A test written to catch that passed against both versions, which is how the mistaken claim came out. The guard stays because a lane is a position inside a gap and this edge has no gap.

A labelled peer edge needed one thing no other edge needs. Two neighbours leave about twenty pixels to run in, a chip is wider than that, and centring it the usual way hid the line and its arrowhead — so the picture stopped saying which direction the relation ran. The label lifts clear of the line, and a case pins it.

Two audits cover what the geometry cannot. A peer edge may not span a box in its own row, tested by emptiness rather than adjacency, so columns one and three may join across an empty column two. And a same-row edge may not carry data-back, which names a direction the figure does not travel there.
