Drive browser tests with W3C WebDriver, and let the CLI fetch its own chromedriver 90 active

A preference for web standards over a proprietary protocol decided this, and a probe then showed it costs nothing. The same measurements came back identical over WebDriver and over the devtools protocol, to the last decimal: a grid of 70.5625px 123.109px 123.109px 123.109px 123.109px, thirteen wires, and a back edge at x=60.28.

WebDriver needs no client library. Six fetch calls cover a whole run: POST /session, POST /session/{id}/timeouts, POST /session/{id}/url, POST /session/{id}/execute/async, GET /session/{id}/element/{eid}/screenshot and DELETE /session/{id}. The devtools route wanted a WebSocket and fifteen lines correlating replies to requests, so the standard is also the smaller of the two.

execute/async carries the deadline. The injected script polls and calls back once the page settles, and chromedriver enforces the script timeout, so nothing on the Node side runs a timer of its own.

The driver provisions itself. Chrome for Testing publishes a chromedriver per platform as a plain zip, one per build number that an installed Chrome reports. Chrome 150.0.7871.189 here matched a 150.0.7871.124 driver. Node's fetch writes no com.apple.quarantine attribute, so the binary runs immediately and macOS asks nothing.

Element screenshots clip to the viewport. Chromedriver scrolls an element into view and captures the part that fits, so a figure taller than the window loses its lower rows. A run that wants the whole figure sets POST /session/{id}/window/rect first.

The cost is one binary that npm does not manage, plus a cache directory to keep it in. What it buys, besides the standard itself, is a route to Firefox that the devtools protocol never had.
