Checked what "the document declares the command, never the implementation, which is true of every other family too" actually claims, against the other four families plus explore.command.html. It's false: knowledge.template.html, language.template.html, plan.template.html, spec.template.html, and explore.command.html all implement their real logic inline in their own <script type="mycelium/command">, importing only the CommandContext type and small generic helpers (loadModule, todayDate) from src/. validate.command.html is the only one that imports a working implementation — validate() — from a src/ file and calls it.

The framing offered in conversation to explain the asymmetry — that validate.ts counts as engine, the same tier as run.ts, because it's "protocol-only" rather than family business logic — doesn't hold up either. The actually generic, reused-elsewhere primitives (parseHTML, walkFiles, walkHtmlFiles, resolveTemplateRef, loadCheck, loadGenericValidator, validateInstance) already live in src/utils.ts, shared by both run.ts's authoring commands and validate.ts. What's left in validate.ts — walking the whole corpus, discovering templates/audits/instances, running them, formatting results — is command-level orchestration built on those primitives, the same relationship knowledge.template.html's extractGraph or language.template.html's lint logic has to src/. Nothing about it is more "engine" than what any other family's script does.

Corrected framing: core is run.ts + api.ts + script-hooks.ts + the generic half of utils.ts. Every subcommand, validate included, sits on top of that as ordinary command implementation — none of them get a special tier just because their content happens to be about the protocol's own vocabulary.
