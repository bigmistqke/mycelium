Extend autofix to fix markdown paragraph-level prose 85 active

Extends language autofix to accept .md files. A new markdownParagraphRanges in language-prose.ts walks marked.lexer's own token list with a running cursor to get each top-level paragraph's exact source range — reusing the library this project already adopted for markdown parsing, rather than hand-rolling another paragraph splitter. Only top-level paragraph tokens become candidates; headings, lists, blockquotes, tables, and code blocks are never touched, matching the comment path's own self-contained-block rule.

Each markdown region carries two strings, not one: text (protected elements stripped, the same pipeline lint's file mode already uses) is what a rule checks; markdown (the untouched raw substring) is what the model sees and what gets spliced back. Stripping a <code> element removes its text along with its markup, so checking and splicing from the same stripped string would have silently eaten every backtick span, link, and emphasis marker a rewrite touched. Passing region.node (real for markdown, still undefined for a comment) into rule.check() is the only change needed for the two node-dependent rules (paragraph-length, no-bolded-mini-headlines) to reach markdown at all — they were previously unreachable by autofix. A rewrite is re-parsed and re-stripped the same way before verification, and the single-<p> structural check runs on the POST-strip tree so a blockquote-wrapped rewrite (blockquote is a protected tag) cannot slip past it.

Verified against a fixture covering all six rules plus decoys (a code fence, list item, heading, and blockquote containing the same violations): --diff then apply produced exactly the expected rewrites, left every decoy byte-identical, and lint afterward reported only the decoys as still-violating — never the fixed paragraphs. One violation (a bare #349 reference) failed verification on the first `--diff` run and was correctly reported rather than silently dropped; a second real run fixed it. Dogfooded on its own doc-comments: ran the pre-existing comment-autofix path against both changed files, which fixed 4 of 5 violations automatically; the fifth (a passive-voice instance introduced by the model's own rewrite of a sentence) needed a one-line manual fix, as did a whitespace-precision loss inside a code span describing hard line breaks, where the model normalized "two trailing spaces" down to one inside a backtick example — worth noting as a known failure mode when autofix rewrites prose that is itself describing exact syntax. pnpm validate stays at 795 checked, 0 fail; pnpm typecheck clean.
