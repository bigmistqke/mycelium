House the Xanadu-view generator under docs/commands/, not core and not a family template 75 completed

The Xanadu-view generator is housed under docs/commands/<id>.command.html — not core (src/), not a content family's own *.template.html, and not a bespoke src/ script.

Rejected: core (src/). Everything this tool reads is protocol-only: data-conforms-to, a type's own <template>-declared fields, data-rel and href. But run.ts and validate.ts are both thin dispatch machinery, and this is mostly canvas layout, shadow-DOM panel loading, connector-line math and interaction handling. Generic data sourcing doesn't imply engine-shaped code; core should stay reserved for actual protocol machinery, not become a home for any tool just because its inputs are generic.

Rejected: a command inside any single content family's own *.template.html (the way knowledge generate graph lives in knowledge.template.html). This tool needs the whole tree — knowledge/, specs/, DESIGN.html — and no single family's file is the right scope; generate graph itself deliberately drops edges pointing outside knowledge/ for exactly this reason.

Rejected: repurposing template.template.html as the command host. It explicitly documents itself as not a node type, with no commands of its own today (only a shared validator function) — its stated purpose is schema vocabulary, not content rendering.

Rejected: a bespoke docs/commands.ts script bundling validate alongside the new tool. validate.ts is itself protocol-only and engine-shaped. I grepped it for hardcoded family names, knowledge and specs, and found none, so it correctly belongs in src/ already. Pulling it into a new file would blur that boundary rather than fix anything.

Landed on: a new file under docs/commands/, suffixed .command.html instead of .template.html so its name doesn't falsely imply instances conform to it (a mistake template.template.html already makes once; no reason to repeat it). Dispatched through the existing mycelium run <id> <command> mechanism — walkHtmlFiles already recurses the whole docs/ tree, so the subdirectory needs no engine change. The one real engine change: run.ts's findTemplateFile is currently hardcoded to a single ${id}.template.html pattern and needs to also recognize ${id}.command.html — small and still fully generic, not yet implemented. The singleton's actual <id> (working name "explore") is also still open.
