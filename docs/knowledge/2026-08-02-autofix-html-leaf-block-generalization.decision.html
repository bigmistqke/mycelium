Generalize autofix's HTML region-finding via a block-level leaf test, not a hardcoded <p> 75 active

Autofix could close its corpus-HTML gap narrowly (only <p>) or generically (every block tag extractProse already knows). Neither is right as stated: the developers built BLOCK_TAGS for extractProse's job (concatenate a whole document's text), not for atomic unit that developers can rewrite and splice back. A <li> or <div> can contain further block tags (a list item with two paragraphs, a div wrapping several <p>s). Treating one as a single splice unit risks reprinting nested structure we never asked the model to preserve, the same reason markdownParagraphRanges already skips inside lists.

The chosen rule: any BLOCK_TAGS element with no BLOCK_TAGS descendant is a leaf, computed with one filter over the existing BLOCK_TAGS set. This covers p/dd/td/th/dt/figcaption/headings as atomic candidates unconditionally, and li/div only when they turn out to be leaves themselves, letting their nested <p>s get picked up individually instead.
