Corpus HTML leaf-block autofix works, verified against a fixture and dogfooded on its own nodes 85

Verified against a hand-built fixture. The fixture contained a top-level violating <p> with an inline <code> span and an <a> link. It also contained a two-paragraph <li> whose own nested paragraphs are picked up individually rather than as one unit. Additionally, it contained a passive-voice sentence inside a <blockquote>. --diff then apply fixed exactly the two leaf paragraphs, left the list item's non-violating second paragraph, the code span, the link, and the protected blockquote byte-identical. lint afterward reported nothing left.

Dogfooding against the two new knowledge nodes this work itself produced caught a real bug. The two markup-reading rules (paragraph-length, no-bolded-mini-headlines) call node.querySelectorAll('p'), written for a whole-document node containing the paragraph. Handed a bare leaf <p> directly, querySelectorAll searches only descendants and never matches the node itself, so both rules silently never fired, and autofix reported "no fixable violations" on a file validate had just flagged.

Fixed by re-parsing each leaf as its own <body>-wrapped document via the same cli.parseHTML already used for the whole corpus document and the markdown path, instead of assembling a wrapper element by hand. No tag-specific branching appears anywhere in this path, unlike an earlier considered fix that would have taught the two rules to special-case matching themselves. A leaf has no BLOCK_TAGS descendant of its own by construction, so .textContent already equals what extractProse would produce for the text-only rules, and that call was dropped as redundant.
