Two kinds of staleness, and only one of them is detectable from the code

Drift

The code moved and the claim no longer describes it. Checks fail. Every tool targets this one.

Expiry

The code still matches the claim perfectly and the claim is dead anyway, because the reason evaporated. We cache this because the upstream API rate-limits us, and the limit went away two years ago.

Every check passes. Nothing is wrong with the code, so nothing that reads the code will ever find it.

What follows

A claim needs a premise: what has to stay true in the world for it to be worth having. Some premises are checkable, being a version or a scale number or a config value. The rest are questions asked on a schedule and answered by a person in ten seconds.

That is the half of the design test suite which cannot be automated, and the half that catches the expensive mistakes.

There is an inverse signal too. A check that has passed for two years while the code under it churned is a check nobody needs. Dead rules are as informative as failing ones.

The strongest defence against staleness is not checking at all. It is use. Documents rot because nothing reads them. A claim read before every change gets exercised daily and its errors surface on their own.
