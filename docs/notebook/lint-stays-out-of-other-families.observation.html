Linting is not protocol, so no family calls another family's lint

Wiring lint into knowledge add and spec add would be the first time a family imports another. Nothing here does that. Each family imports ./shared.ts and, in one case, a script in its own file. The only cross-file dependency in the system is the engine reaching for template.template.html#validate-from-template, and that is engine to protocol.

The test that settles it: cli.validate is handed to every command because conformance is protocol and the engine owns it. Language rules are a project's choice of house style. Not protocol. So the engine should not supply lint either, which also closes the workaround where the engine wires it and the families stay ignorant.

What that costs is immediacy, not coverage. An audit extracting corpus prose catches every violation that lands, at validate time, which is before a commit. Wiring it into add would move the error earlier and catch nothing extra.

The coupling belongs in the harness. A skill or a hook already composes commands, so running language lint on a draft before running knowledge add is that job, and it keeps the dependency out of the corpus. Same layering as fixing the read path before the guardrail: context first, blocking second.
