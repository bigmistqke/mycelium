Findings in code travel upward, so a fix has an altitude

The chain is not a pipeline that runs downward. Implementation flows down from axiom to specification to test to code, and findings flow back up.

The consequence is about what a bug means. A problem the chain did not predict is not, by default, faulty code. It is a sign that something above is missing or in conflict: either no behaviour speaks to the case, or two behaviours want different things and the implementation had to pick one. Fixing the code and stopping leaves the hole where it was, and the next escape comes out of it.

So a fix has an altitude, and the question is how far up it goes. There is a test for which is which. If a test citing an existing behaviour catches the problem, the chain worked and the fix stops at the code. If nothing in any specification speaks to it, the specification is incomplete by exactly that much.

This is also what makes the methodology usable on a project that is already running. A codebase carries principles its maintainers never wrote down, and reading them out of the code is the same operation run in the other direction. Doing that across two subsystems is what surfaces a conflict neither one shows on its own: each is internally consistent, neither is a bug, and the disagreement is only visible once someone writes both assumptions out as sentences and sets them side by side.

 the chain runs both ways, so a finding in code is evidence about the layer above it
