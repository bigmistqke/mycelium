A language rule checks a string; an audit checks a corpus

Language rules kept fitting badly into the audit model, and the reason is that they are asking a different kind of question. An audit answers something about a set of documents: is every outcome linked to, is anything an orphan. A language rule answers something about a string.

The rules spec has a dictionary rule carrying <script data-audits> and exporting check(documents), which makes a rule an audit. That is what the spec gets wrong, and it is why the question of how to reach comments in src/ and messages in git looked hard. Under the audit model the checker has to reach out and find text wherever it lives.

Invert it and the problem dissolves. A rule exports check(text), and the text comes to it.

A commit message arrives on stdin. Corpus prose arrives from an audit that extracts it. Nothing has to reach outside docs/, because nothing is reaching at all.

The self-test improves too. language-pass and language-fail are strings and a rule's check takes a string, so running a rule against its own two examples is direct. The audit version needed a fixture document to stand in for a corpus, which is the awkwardness that declaring expected violations had to solve for real audits and which a language rule now avoids entirely.
