Defer attribute constraints in the schema until a second caller wants them

The schema can constrain children and their text and nothing else. For a schema over markup that is a missing dimension rather than a missing feature: it cannot say that an element must carry an attribute at all.

The form it would take is small. Reserve required, pattern and enum as the schema's own words, and treat any other attribute on a placeholder as one the instance must carry, with a value meaning the value must match. Roughly six lines in validateFromTemplate. Its cost is that a misspelt schema word becomes a requirement for an attribute of that name, which fails loudly with a confusing message rather than silently.

Deferred anyway, because there is exactly one caller: an audit's script must carry data-audits, and a one-line audit covers it. Building the general form now would be growing the engine to serve a single case, which is the trade the schema-or-code rule refused for at-least-one-of.

This differs from that refusal in one way worth recording, in case it is the argument that lets the engine grow later for a bad reason. At-least-one-of is a logic operator wanted by one type. Attributes are a category the schema cannot describe at all. The hole is real; only its urgency is not.

The trigger is explicit. When a second thing wants to constrain an attribute, build the reserved-word form and delete the audit that stood in for it. Not "revisit later".
