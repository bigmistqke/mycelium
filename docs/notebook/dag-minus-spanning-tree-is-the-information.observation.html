Subtract a spanning tree from the graph and the remainder is the whole information content

A tree promises that each child has one parent and that siblings are disjoint. Code honours neither, and every place it breaks one is a fact you cannot get elsewhere.

Many intents, one implementation

A sanitise function someone wrote for cross-site scripting. Later a second person leans on it to fix log injection. Later a third relies on it for a database constraint.

One body, three parents, and only the first has a record. Now cleaning it up is an incident.

In-degree here is a number worth having: not lines, not churn, but how many independent reasons rest on this. That is criticality derived from meaning rather than from size.

One intent, many implementations

Tenancy, auth, retries. A tree wants one box; the honest picture is one node with forty children.

It also exposes a bug class structurally, because thirty-eight children can honour the intent and two not. Inconsistent siblings under a shared parent shows up as a shape, without knowing what the rule says.

Diamonds

Two intents converge on one decision which then serves both. Fast reads and an audit trail both led to an append-only log.

This is design carrying two loads on purpose. It breaks when one intent goes away and someone removes the log as the audit thing. A tree cannot hold it. You would copy the node under both parents and the copies would drift.

Lateral edges

Must not know about. Must happen before. Is the inverse of.

Those hold between cousins, and a tree has no word for cousins. Most invariants live here.

Uneven depth

Some intents reach code in one hop and some in six. A layer diagram assumes one depth and is wrong at both ends.

Apparent cycles

An implementation teaches you something and the intent changes. That is a new version of the intent, not a cycle. So a cycle in the derived graph means history got flattened and a revision needs naming.

Why the non-tree part is the content

Trees are what we already have. The directory structure, the org chart, the layer diagram, the module nesting. Anything tree-shaped in the answer is something you could read off the file system.

Take any spanning tree of the graph and subtract it, and what remains is every edge that surprised you.

This also settles how to draw it. Tree layouts are readable and graph layouts are hairballs, so lay out the spanning tree as a skeleton and render the remaining edges on top, highlighted and filterable. The readable part is scaffolding for the part that is news.

Dead alternatives belong on the edges rather than the nodes. Each step down a level is a place where someone chose one implementation over others, so the losers attach to the edge that records the choice.
