Template: canon-axiom, canon-specification

what this project holds true and what it promises: axioms stating a rule that holds now, and specifications whose behaviours each cite the axiom they narrow .mycelium/canon/<subsystem>.canon.html, one document per subsystem, with root.canon.html holding the axioms that govern everything axioms, specifications, and a chain a checker can walk why a behaviour names the axiom it narrows

Why this template exists

This project could say what shape a document takes and whether its prose obeys the rules. It could not say why the system took the shape it has, nor whether the code answers to anything.

These two types close that. An axiom holds the criterion someone appeals to when two designs both work and one of them is right. A specification holds what one subsystem does, as a list of behaviours a test can cite one at a time.

The chain runs axiom, then behaviour, then test, then implementation. The last two get no document of their own: a test cites a behaviour from a comment in real source, the way a commit is a field rather than a re-hosted node.

It runs in both directions, and that is the methodology rather than a property of it. Downward, an axiom settles what a behaviour may claim and a behaviour settles what a test checks. Upward, a problem the chain did not predict means either that no behaviour speaks to the case or that two behaviours want different things, so a fix has an altitude.

Two types in one file

The types only mean anything together, which is the same reason six knowledge types and four plan types each share a file. An axiom no behaviour refines settles nothing, and a behaviour naming no axiom is an assertion nobody can argue with.

No date prefix, like the language family

Both types describe what holds now. An axiom that stops being true gets revised or retired, and a specification that no longer matches the system is a bug in one of the two.

Neither belongs to the exploration that produced it, so neither filename carries a date and add takes no --date flag. Knowledge nodes and spec docs date their instances because each one records a moment; these record a standing claim.

Shape

All three types share canon-title, the way every knowledge-* type shares knowledge-title. Fields carry the family prefix and not the type name, so canon-title rather than canon-axiom-title.

For an axiom the title is the principle itself. For a behaviour it is the claim, in one falsifiable sentence. For a specification it names the subsystem.

What each field is for

An axiom once carried a confidence, meant to tell a principle somebody committed to from one an agent inferred by reading code. That is a question about kind, and a number from 0 to 100 cannot answer it. The eleven values sat between 80 and 95, nothing read them, and not one ever moved.

An axiom carries a required detail, holding the reasoning behind the principle. A title states a principle in one line, and one line compresses hard: the first eleven axioms all reached a reader with their reasoning missing, because a field nobody has to fill is a field nobody fills. A specification carries no detail at all, and that absence is load-bearing rather than an oversight.

Each kind of content that is not a behaviour already has a family here. A criterion is an axiom, something that happened is a knowledge node, a word's meaning is a language term, and the reasoning behind a design is the design document. A detail field on a specification is the hole all four go through, so this template declares none and the closed-field check rejects one.

Two sentences show what that catches. This gate only became real on 2026-07-30; before that it printed failures and exited 0 is an incident, and it belongs in the graph. It exits non-zero rather than warning because a gate people ignore is not a gate glues a behaviour to its criterion, and the halves separate into a behaviour and an axiom.

Every behaviour owes a test

Nothing marks a behaviour as exempt. No keyword vocabulary sorts them and no attribute grades them, because a behaviour is a claim about the system and a claim with no evidence under it is the same failure an axiom reaching nothing already names.

An earlier draft split a behaviour into a requirement, which owed a test, and context, which did not. The argument was that a requirement is a promise holding across refactors while context describes internals a refactor may invalidate. That reasons from the code level, outside the chain, where nothing below may make something above false.

So the question of what counts as a behaviour is not a question about sorting content inside a specification. It asks which family a sentence belongs to, and the corpus answers that already.

An id is an address, not a summary

The id attribute is what a test cites, so it is required and its pattern rejects any segment made only of digits. A number rots the first time someone inserts a behaviour above it, which the project that ran this methodology before learned from its own numbered axioms.

An id is named for the behaviour rather than for its wording, so a copy-edit never touches one. Renaming an id fails every citation to it, which makes a rename deliberate and carries its citations along.

What that leaves open, and no check here closes it: rewording a behaviour in place keeps every citation resolving, so nothing tells the citing tests they now check something the document no longer claims.

A behaviour is one sentence

A test citing a paragraph cites several claims at once, and then does a test exist for this stops having an answer. Where a paragraph seems necessary, the claim inside it is the behaviour and the rest belongs to another family.

The schema does not enforce this. pattern tests trimmed text, so it cannot see block markup, and a rule counting sentence terminators would reject a behaviour naming src/api.ts. This one stays prose until an audit can carry it.

Edges

A behaviour links up to the axiom it refines with depends_on, and an axiom links up to the general one it narrows with the same relation. That edge is the whole composition mechanism, with no region names, no scope attribute and no cascade.

The citation sits on the behaviour and never on the specification holding it. A specification names a subsystem, and a subsystem is a grouping of files rather than a claim, so nothing can contradict one and nothing can derive one from a principle either. The unit that owes an axiom is the unit somebody could later argue with, which is the behaviour.

Hanging the edge one level up hides exactly the failure this family exists to catch. An axiom carrying three specifications reads as load-bearing, and means the opposite: it is general enough to cover anything, so no behaviour underneath ever had to name a principle that actually predicts it.

Stored edges point up only. The downward reach a checker asks about gets computed from them, never authored, because a hand-maintained reverse index rots and a forgotten entry in one looks exactly like an axiom nothing derives from.

A specification also points at the code it answers for, with specifies. It does not name its subsystem, it points at one: the subsystem is whatever that link set covers. This follows link, do not tag, which refused a hand-maintained vocabulary once already.

The relation comes from the closed set every family already shares, rather than a word minted for this one. specifies entered that set for a design document pointing at what it specifies, and a specification pointing at the command it answers for is the same shape one rung lower. The corpus retired its last two unlisted relations rather than widen the list, and a describes here would have reopened exactly that.

Grounding: where a claim came from

A claim names the notebook entries it came from, inside a canon-references child. Nothing marks an entry as promoted and nothing tracks a queue, because promotion needs state somewhere and one link already carries the fact.

The container is what keeps this cheap. No ninth relation joins the vocabulary, since containment already says what the link is, and canon-axiom keeps its depends_on pattern untouched. grounded reads direct children only, so a reference cannot make a claim look load-bearing.

Every claim may carry one, so a behaviour grounds the same way an axiom does. The prefix follows the family rather than the element, which is the naming rule everywhere else here.

Each anchor carries a label, and the schema requires it. A bare href says which entry, and the label says what the claim took from that entry, which is the part a reader cannot reconstruct by opening it. An axiom's reasoning and its source say different things.

Checking comes free. every-link-resolves queries every anchor in the corpus rather than the ones a family declares, so a reference to a missing entry fails validation the day somebody writes it.

Fifteen axioms carried no reference when this landed. That number is a reading rather than a gate, because much of this canon came top-down from the implementation, and demanding grounding now would manufacture entries to satisfy the check.

A test cites a behaviour

A test is a document here, so the bottom rung is a link like every rung above it. A test-case names the behaviour it checks with depends_on, the same relation a specification uses to name the axiom it serves. 

<test-case id="exits-non-zero-on-failure">
  <test-name>validate exits non-zero when an audit fails</test-name>
  <test-status>PENDING</test-status>
  <a data-rel="depends_on" href="../canon/specifications/validate.specification.html#exits-non-zero-on-failure">the behaviour this checks</a>
  <script type="mycelium/test">…</script>
</test-case>

A case carries an id, so a citation has an address at both ends and every-link-resolves checks it like any other link. Renaming a behaviour fails every citation to it, which is what makes a rename deliberate.

A citation gets judged on where it lands, never on what carries it. One resolving to an axiom rather than a behaviour is a finding: the test knows something no specification states.

An earlier design wrote this as @specification in a comment above an it(...) call, which is what a test looks like in frameworks this repository does not use. It failed twice by finding nothing and calling that an answer. Full reasoning: a test cites a behaviour with an edge.

Validator

The generic validator in template.template.html handles this, reading the schema attributes on the three <template> elements above. No hand-written validator lives here.

The closed-field rule does the work that matters. A specification carrying a canon-detail fails, because that field is absent from its template and the allowed set is exactly what the template declares.

The chain checks

Three audits, declared here beside the types they check, the way knowledge.template.html declares its own. Each reads the corpus through AuditFs and none of them names a rung inside src/: the engine learns this chain by reading the declarations above, because a checker that hardcodes its ontology is a checker that can only ever check one project.

All three share one reader, canon-citations.ts, which holds both ends of the joint: which behaviours the corpus states, and which behaviour each test says it checks. Three copies of that reading is how two checks come to disagree about what a citation is.

grounded

Every axiom reaches a behaviour beneath it, and every specification reaches an axiom above it. An axiom with nothing under it is a belief nobody acted on.

The downward reach is computed from the upward edges, never authored. A hand-maintained reverse index rots, and a forgotten entry in one looks exactly like an axiom nothing derives from.

The honest cost, which the design states outright: a broad axiom nobody has read down into a subsystem reaches nothing there, and this check cannot tell that apart from an axiom that does not apply. Writing the reading is the work, and no audit does it for you.

Two more checks used to sit here, and the shape retired both. One asked whether every behaviour had a case citing it, and one asked whether every case cited a behaviour. A behaviour now carries its own check, so a claim with nothing beneath it fails against its own template and a check has nowhere to live except the claim it answers.

Authoring commands

The same type="mycelium/command" convention every other family uses. Nothing here gets hand-authored, so no file content passes through whoever is writing.

There is no del in this pass. Deleting a specification drops every behaviour inside it, and each citation from source pointing at one stays behind in a file this command does not own, which turns a delete into a broken chain nothing warned about.
