Template: lib-doc

reusable code as a real document, so a family importing it gets a schema-checked, tested, documented function instead of a bare file wandering outside the corpus .mycelium/templates/<slug>.lib.html, sitting beside whatever assets its own functions read — no fixed directory of its own yet lib.template.html: reusable code as a real document, not a bare file
Styling: ./lib.template.css, plus the shared ../theme.css

Why this template exists

A family importing another family's own logic has always worked — mycelium/shared and mycelium/utils are real, working imports today. What neither had was a document of its own. A .ts file sits outside the vocabulary this whole corpus otherwise holds to: nothing checks its shape, nothing cites it, and a reader who wants to know what a function promises has to go read the implementation, the same gap a bare command function had before it could export a real verb table.

A .lib.html file closes that gap without inventing new machinery. Addressing a function by path.html#id already works — it is the same mechanism a command script already uses to reach another family's export. What was missing was a shape: somewhere a function's own doc and its own test could sit beside its own code, checked the way everything else here is checked.

Shape

One title for the library as a whole, and one or more functions. Each function carries its own doc as a real sibling field — not a code comment, the same way a family's own purpose sits beside it rather than above it in a comment — its own script, and an optional test. 

<lib-doc>
  <lib-title>…</lib-title>
  <lib-function>
    <lib-function-doc>…</lib-function-doc>
    <script id="someFunction" type="mycelium/lib">
      export function someFunction() { … }
    </script>
    <lib-function-test>
      <script type="mycelium/test">
        export default async function ({ assert }) { … }
      </script>
    </lib-function-test>
  </lib-function>
</lib-doc>

A function's id is what a reader imports by

<lib-function> itself carries no id — only its <script> does, since that is the one element script-hooks.ts's loader actually resolves with document.getElementById. Giving the wrapper a matching id looks harmless and is not: a duplicate id resolves to whichever element the DOM finds first, so #someFunction would hand the loader the wrapper's own mixed doc-and-code text instead of the script's, and the failure reads as a syntax error in code that was never wrong.

A script typed mycelium/lib gets the same TypeScript-stripping every mycelium/* script already gets. Nothing about loading one is new; only the document holding it is.

A test is optional, and lives beside the function it checks

<lib-function-test> wraps a plain mycelium/test case — the same shape a canon behaviour's own node case already has, handed { assert } and nothing else. No sandbox: a library function is a pure function of its own arguments, not a command reading or writing documents, so it needs no throwaway corpus tree to run against.

Authoring commands

test only. A function's body is real code, and no flag fits one the way --title fits a one-line field — the same reason test.template.html's own cases have no add either. Writing a .lib.html file means writing the markup.

Conformance

Conformance is a data-conforms-to attribute on the element making the claim, the same as every other family here. 

<lib-doc data-conforms-to="../templates/lib.template.html#lib-doc">
  …
</lib-doc>
