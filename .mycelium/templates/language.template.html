Why this template exists

Every family here fixes the shape of a document and checks it. Nothing fixes the sentences. The rules for those exist, but they live where the repository cannot see them — a commit-message skill, a personal memory note, prose scattered through CLAUDE.md, and the corpus itself by example — and rules in that state are not followed. The spec has the evidence and the measurements; this file is the shape that follows from it.

The model is ASD-STE100, which is two parts: writing rules, and a dictionary of words with one meaning each. Technical vocabulary is explicitly left for each project to supply. Those two parts are the two types below.

Two types, because a rule and a word are not the same object

A language-rule is a rule about writing, and its load-bearing content is a pair of examples. Every reader reads a rule stated abstractly differently; the example that passes and the example that fails are what pin it down, which is why both are required rather than optional colour.

A language-term is a word, with one meaning. The field that does the real work is language-status: a dictionary that only defines the words you should use documents the vocabulary without preventing anything. What stops drift is recording that scaffolding is rejected and points at harness. That is ASD-STE100's actual mechanism — its dictionary is approved and not-approved pairs, not a list of entries — and it is the half a glossary usually leaves out and then fails to prevent anything.

No date prefix, unlike every other family here

knowledge/ and specs/ both prefix a filename with its date, and that prefix carries real meaning: it records which exploration a node belongs to, which is the argument link, do not tag leans on to show a separate topic vocabulary is unnecessary.

An entry here is not an event and does not belong to an exploration. The word harness is not from July; it is the word this project uses, and dating it would assert something false about it. Entries are also looked up by their word, which a date prefix puts behind a lookup step. So language/terms/harness.term.html, and add has no --date flag and prepends nothing.

Terms and rules sit in separate directories because thirty-five one-line words and fourteen rules interleave alphabetically otherwise, and nobody could read either list. This is a split by type, not by subject: a term goes with terms and a rule with rules, so there is no judgment to make on each entry. A split by subject would be one, which is the cost link, do not tag refused for topic tags.

The type suffix stays on the filename even though the directory repeats it, and it earns its place: every command that takes an existing entry derives the directory from the suffix, so a caller writes harness.term.html and never a path.

Shape

Both types share language-title and an optional free-form language-detail, the way every knowledge-* type shares knowledge-title and knowledge-detail. Fields carry the family prefix and not the type name, so language-title rather than language-term-title — fields belong to the family.

For a term, the title is the word itself. For a rule, the title is the rule stated in one line. 

<language-term>
  <language-title>harness</language-title>
  <language-part-of-speech>noun</language-part-of-speech>
  <language-meaning>… one sentence …</language-meaning>
  <language-avoid>utilize, leverage</language-avoid>
  <language-detail>… optional, free-form …</language-detail>
  <a data-rel="alternative_to" href="./harness.term.html">use this instead</a>
</language-term>
<language-rule data-validates="html markdown">
  <language-title>… the rule, in one line …</language-title>
  <language-pass>… an example that passes …</language-pass>
  <language-fail>… an example that fails …</language-fail>
  <language-detail>… optional, free-form …</language-detail>
  <language-dependency name="retext" version="^9.0.0"></language-dependency>   <!-- repeatable, only if the check imports a real library -->
  <script type="mycelium/rule">export function check(text) { … }</script>
</language-rule>

<language-guide>   <!-- same fields, no script -->
  <language-title>… the guidance, in one line …</language-title>
  <language-pass>…</language-pass>
  <language-fail>…</language-fail>
</language-guide>

What each field is for

language-meaning is one sentence, and language-detail is free-form. This is the same split knowledge-title and knowledge-detail already make, applied here for the same reason: a term needs a line you can scan in a list of forty, and separately it often needs its boundary drawn against a neighbouring term, which does not fit on that line. Putting both in one field produces what a node should carry a claim, not an incident warns against, and what actually happened on 2026-07-27, when eight nodes averaged 415 characters of title because the field for the rest of the thought went unused.

A rule carries a check; a guide does not. That is the entire difference between the two types, and it is why they are two types rather than one with a field saying which. language-rule declares <script required>, so a rule with no check fails its own template, and nobody can write one. Nothing can claim to be enforced and not be.

language-dependency holds a real package a check imports, one element per package, empty like figure-edge because its meaning sits in name and version rather than in text. Seeding installs every one it finds into the consumer's own project, so the check runs there the same way it runs here. See the spec.

A field would have let it. An earlier version of this template had language-checkable, and within two hours it was wrong on one entry: a rule marked as undecidable when the truth was that a machine cannot settle it but can flag every candidate. Eight entries declared themselves checkable while no check existed anywhere. See derive enforceability from the check.

A guide is not a lesser rule. "Lead with the fact, not the setup for the fact" is a claim about what a writer was trying to do, and no pattern decides it. Writing it down as a guide is what keeps the audit from being blamed for missing it.

The guard runs one way only. The schema can require a script on a rule; it cannot forbid one on a guide, because the closed-field check inspects language-* children and a <script> is not one. A guide carrying a check would validate, and the audit below catches that instead.

A rejected term points at its replacement with an ordinary <a data-rel="alternative_to">. That is not enforced here. The schema can require a field, but "a rejected term must link to an approved one" is a property of a pair of documents, which makes it an audit rather than a validator — and audits are the next pass, not this one.

Validator

Validation is handled by the generic validator in template.template.html, using the schema attributes on the two <template> elements above. No hand-written data-validates script: every rule either type needs (required fields, two enums, and the closed field list that rejects a rule's field appearing on a term) is already expressible in that vocabulary, which is the arrangement schema first, validator function optional settled.

Authoring commands

The same type="mycelium/command" convention knowledge.template.html and spec.template.html already use, and each command's own /** … */ comment is its only documentation, so mycelium language --help and the usage shown here can never drift apart.

link and unlink are both here from the start, unlike in spec.template.html, because this family has a real edge to draw: a rejected term points at its replacement. A family that can create an edge and not remove one leaves a wrong edge standing until someone hand-edits a file, which the session that added the command roster ran into directly.

The audit that runs the rules

The audit runs every rule carrying a <script> against the prose of every document. A rule that carries no script is guidance: it is stated and not enforced, and the script's presence, not a separate field that could disagree with it, decides whether a rule is enforced.

A rule's check takes text. That is what lets the same rule apply to a commit message, a comment in a source file, and a field in a document, without any of them being reached for: the engine brings the text to the rule instead. Deciding which text is prose belongs here, to the thing that knows what a document is, rather than to each rule.

Conformance

Conformance is declared as a data-conforms-to attribute on the element making the claim, the same as every other family here, and it names one of the two fragments above: 

<language-term data-conforms-to="../templates/language.template.html#language-term">
  …
</language-term>

What this pass does not do

There is no audit yet. Nothing reads these entries and checks a document against them, nothing derives the edges from a document to the terms it uses, and nothing fails a build. The spec keeps four questions open that all have to be answered before an audit can exist: whether the derived uses live in a rebuildable index or in the documents, whether the audit gates or reports, which text it reads, and whether the six data-rel labels move into this family. This file is the shape entries take, so that there are entries to answer those questions with.
