Architecture report: repl

Subject — @bigmistqke/repl, version 0.2.8, at commit 07b574e
Sources — 20 source files (1,749 lines), 221 commits from 2024-03-26 to 2026-03-03, one README
Method — derived from artefacts only; no design records exist for this project
Written — 2026-08-05

This report answers three questions about a codebase, working from what the codebase and its history contain. What does it consist of now, what principles do those parts rest on, and how did those principles move over the two years the project ran.

A fourth section lists what the artefacts could not settle. That section is the one worth arguing with, because the author of this project is alive and can correct it, which is the whole reason for choosing this subject.

The constituents

repl turns a set of files into object URLs a browser can execute. A caller hands it a readFile function and a map of file extensions to transforms. It hands back get(path), which returns a URL, and keeps that URL current as the file changes. Everything else in the package supports that one move or sits beside it as a standalone utility.

The core is the smallest part. Twelve percent of the source holds the idea the package is named for, and the largest group by far is machinery for an editor the package does not ship.

The type surface is 19 lines. It declares five file types, an extension as { type, transform? }, and a transform as a function from { path, source, fileUrls } to a string. That is the entire protocol a caller has to implement against.

Both forms say the same thing, so the comparison is about what each costs to keep true. The figure names twelve nodes and thirteen edges, and an audit checks that every edge finds both its ends.

Two halves, and they never touch. Nothing outside src/core/ imports the URL system, and the URL system imports nothing from the editor side. Both take a readFile from the caller, so the caller is the only thing joining them.

They do share a floor. PathUtils, createAsync, ReactiveRefCount and getModulePathRanges sit under both, and the diagram leaves those edges out because every box would reach them. Sharing a floor is not the same as connecting.

Three exports appear in neither half. getModuleDependencies walks an import tree and runs outside a browser, with a demo under node/. babelTransform and the frame helpers hang off nothing at all.

The loop in the middle is the mechanism the file list hides. A JavaScript file's transform rewrites each relative import by calling fileUrls.get() for the resolved path, which enters the same system again for that file. An HTML file does the same for every src and href, and hands its inline module scripts to the JavaScript transform.

So one call for an entry file pulls its whole import graph through the pipeline, and Solid's dependency tracking is what makes that a graph rather than a loop. Editing one file invalidates only the URLs that read it.

The principles

Six principles hold in the current code. Each one appears below with what enforces it and where it came from.

The caller supplies the compiler

TypeScript, Babel and Monaco are peer dependencies, and the library never imports them. A caller passes ts in as an argument to createJSExtension, to transformModulePaths, and to getModuleDependencies. The two runtime dependencies are a Solid signal helper and a reactive set.

The reason survives in a commit message from 2024-07-24, which removed TypeScript and Babel from the dependencies. It says that making a chunk for them added about ten seconds to the build time of repl and of every project consuming repl. This is the oldest principle still standing, and the project reaffirmed it in its final substantive commit, dcfdbbf, which stripped the last TypeScript imports out of the core.

Behaviour arrives as data, keyed by file extension

An extension is a plain object with a type and an optional transform. No class, no registration call, no lifecycle. createFileUrlSystem looks the extension up by the string after the last dot and calls its transform, and defaultFileUrlSystem is nothing but a preset map of six such objects with a spread at the end so a caller can override any of them.

The library owns no file system

There is no file store in the package. Every entry point takes a readFile function, and invalidate(path) is how a caller tells the library that something changed. The library holds derived state and nothing else.

This one arrived late and cost the most to reach, and section 3 traces it.

URL lifetime is derived, never managed

Nothing calls URL.revokeObjectURL from a cleanup path a human wrote. The revoke sits inside onCleanup within the memo that created the URL, so Solid's ownership tree decides when it runs. A ReactiveRefCount class tracks how many reactive readers hold a path, and a file's root disposes when the count reaches zero and the file no longer exists.

The escape hatch is explicit rather than hidden. Calling get(path, { cached: false }) returns a fresh URL and moves the revoking onto the caller, and the doc comment says so.

Every part works alone

Eleven of the sixteen exports run without the core. PathUtils, getModulePathRanges, transformModulePaths, getModuleDependencies and the download helpers all take their inputs directly. A demo under node/ runs the dependency walker outside a browser entirely, and the three test files cover only these free-standing pieces.

Two environments, two implementations, one signature

HTML transformation exists twice. One version uses DOMParser and XMLSerializer, the other uses htmlparser2 and domutils for workers with no DOM. Both expose the same TransformHtmlWorkerConfig shape and both return a function producing a string, so the extension that wraps them differs by one import.

The browser version throws a message naming the worker version when the globals are missing, which is the seam documenting itself.

How the principles changed

The project grew for eighteen months and then removed most of itself in a single commit. File count peaked at 55 on 2024-09-24 and line count at 8,397 two days later. Four months on, one commit deleted 15,875 lines and left 17 files holding 1,174 lines. The code has grown slowly since, to 1,749 lines, and has never come close to its old size.

March to September 2024: repl was the REPL

The early package shipped the editor. It held Repl.Frame, Repl.TabBar, a ReplContext root class, a Monaco integration with bundled themes and TextMate grammars, a second editor built on Shiki, and devtools. Four classes carried the state: TypeRegistry, FileSystem, FrameRegistry and Runtime.

A counter-current ran underneath from early on. Five commits on 2024-05-01 refactored Monaco out of the core, and 2024-08-02 refactored Babel and TypeScript out of the runtime. The principle that the caller supplies the heavy tools formed here, while the surrounding library was still growing.

September 2024: all in on custom elements

One commit moved every Solid file into a solid/ directory, the next added custom-element wrappers, and a third removed the Solid entry points with the message let's go all in with custom elements. The package was at its largest during this month.

The same week retired the assumption the early design rested on. Removing FrameRegistry, the message says the registry worked from the assumption that everything was nested inside a <Repl/> component, and that the assumption is not correct anymore. That is the first clear statement that the library should not own the page.

Then the repository went quiet for three and a half months.

January 2025: the big chop

Work resumed with a commit titled big choppa: 77 files changed, 1,399 insertions, 15,875 deletions. Elements, editors, devtools, frames and the tab bar all left. Every remaining class became a function, so FileSystem became createFileSystem and the extension mechanism became createExtension.

Nothing in the history explains this commit. Its message is two words, and the gap before it holds no commits at all.

January to June 2025: the file system leaves too

A commit on 2025-01-31 split createExecutables out of createFileSystem, and it carries the most detailed message in the project. An experiment in a different repository put a flat file system inside an Automerge document, and synchronising a second file system on top of that turned out to be cumbersome. The fix was to expose the URL machinery alone and demote the file system to a wrapper around it.

Four months later, 457fe49 renamed createExecutables to createFileUrlSystem and deleted createFileSystem outright. The wrapper had turned out to be unnecessary once the primitive underneath it existed. The library has held no file state since.

The following day added ReactiveRefCount and moved URL disposal into the reactive graph, which is where the fourth surviving principle starts.

September 2025 onward: hardening

The last stretch added no new ideas. It consolidated scattered helpers into two utility files, added a circular-import check to the lint script, wrote the first real tests, and added getModuleDependencies. The test suite is 1,176 lines against 1,749 lines of source, and every test targets a free-standing utility rather than the core.

What the artefacts could not say

The history explains removals far better than it explains arrivals. Three of the four abandoned principles left without a stated reason, while the one detailed message in the project explains a design that a failure elsewhere forced. These questions are what a reader of the artefacts cannot close.

Why did custom elements fail?

The commit adopting them states an intent. Nothing states why they went away four months later, and the big chop deleted them alongside everything else, so their removal carries no argument of its own. Were they abandoned on their own merits, or swept out with the rest?

What happened during the three-month gap?

The repository stops on 2024-09-26 and restarts on 2025-01-08, and the first substantial commit after it deletes 15,875 lines. A decision that large either formed during the silence or had been forming through the months before it. The commits cannot tell those apart.

Was the file system removed twice for the same reason?

A FileSystem class died in the big chop with no explanation, and createFileSystem died eighteen months later for a reason the history records precisely. Reading backwards makes it tempting to call the first removal an early version of the second. Nothing supports that.

Is the editor tooling still wanted?

Type downloading and Monaco wiring are 28% of the source and serve no part of the URL pipeline. The README says of one of them that you should probably use a different package instead. Kept deliberately, or simply never removed?

Why did testing stop and restart?

A commit in June 2024 removed vitest. Tests reappear in October 2025, sixteen months later, and now nearly match the source in size. The gap covers the entire period when the library was largest and changing fastest.

What was the target the whole time?

Every principle here is a constraint the code obeys. None of them is a goal. The artefacts show a library shedding responsibility for two years without ever saying what it was trying to become, and the convergence only reads as convergence from the end.

Derived without design records, so every claim traces to a file or a commit in the subject and nothing traces to a stated intent. The earlier finding that this kind of reading recovers mechanism and misses intent predicts exactly the shape above: six principles stated with confidence, six questions that only a person can answer.
