The watching graph server exhausts a two gigabyte heap after roughly a dozen rebuilds graph harness

The server behind notebook generate graph --watch ran for about sixteen minutes while a stream of edits to the notebook and its own template landed, each one triggering a redraw. It crashed with JavaScript heap out of memory after climbing past two gigabytes, having rebuilt on roughly a dozen file-change events over that stretch.

Two gigabytes for a dozen redraws of one corpus is not a corpus problem — the whole notebook parses to a few megabytes. Something in the rebuild path holds onto what an earlier build allocated rather than releasing it, so each redraw's cost adds to the last one's instead of replacing it. A user watching the graph for longer than this session did would hit the same crash sooner, on any corpus, given enough edits.

The fix needs the rebuild path read with this shape in mind — what a build() call retains after it returns, and whether the watcher's own closures over touched/kindOf accumulate anything across calls rather than resetting. Restarting the server is the only workaround right now.
