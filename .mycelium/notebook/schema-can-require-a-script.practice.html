The schema can require a non-family child, so an audit's script is declarable after all

I claimed the schema could not require that a template-audit actually contain a check, because the closed-field rule only inspects children whose tag carries the family prefix, and a <script> does not. That was wrong, and it was wrong about code I had read.

The closed-field rule is only the last loop in validateFromTemplate. The required check above it iterates the shape's children by tag name and cares nothing for prefixes. So <script required></script> in a template declaration requires a non-empty script in every instance.

Verified rather than reasoned: a scratch corpus with one instance carrying a script and one without produced 2 checked, 1 fail — missing or empty <script>. The probe was deleted.

What remains undeclarable is narrower than I said. The schema cannot check that the script carries data-audits, because the vocabulary has no attribute checks at all, and it cannot see inside the script to know it exports check. So the residue is one small audit rather than the larger one first sketched.

The general lesson is about where a limit was assumed. The vocabulary was described to me as field-oriented, and I extended that description into a constraint the code does not have. The rule that a check moves into the schema when the vocabulary can say it is only as good as knowing what the vocabulary can say.
