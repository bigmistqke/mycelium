Mycelium installs into another project as a dependency distribution corpus engine i want to start using mycelium in other projects. currently the project has been created without too much thought about how it could be distributed. i don't want to use a package registry, but use pkg.pr.new instead for continuous releases. it can just be the cli as-is. maybe it can just start with some content? maybe the notebook and the commands let's also rename docs to .mycelium in this repo maybe we can add other functionality later to the the base 'mycelium' command -> but one of the things it should do is to check if there is already a .mycelium and create and seed it if it doesn't exist yet.

This project grew as one checkout where the engine and the corpus sit side by side, and nothing about that arrangement was ever a decision. Another project wanting the same tooling needs the engine from node_modules and a corpus of its own, and today neither half can survive the separation.

Three things hold the halves together. The package declares itself private, carries no bin and exports nothing, so nothing installs it. Twenty-one documents reach the engine through ../../src/api.ts, a path that exists only while docs/ is a sibling of src/. The engine then resolves its corpus as ./docs against the working directory, which is the one tie that already works in somebody else's repository.

Releases go through pkg.pr.new rather than a registry, one build per commit. The corpus moves to .mycelium/ in this repository too, so what a consumer gets and what this project runs are the same shape rather than two arrangements to keep in step.

The bare mycelium command grows a job beyond printing the roster: it looks for .mycelium/ and seeds one when nothing is there. Running it a second time finds the directory and leaves it alone. More may attach to that command later, and this is the first thing on it.
