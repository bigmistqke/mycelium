Every family but one keeps its documentation, its tests and its source in one .html file. The exception is reusable library code: graph-page.ts, shared.ts, graph.element.js, and any vendored helper such as nimble-html would join them, all sit outside the document vocabulary as bare .ts/.js files, because nothing today lets a consumer import from inside an .html document except src/script-hooks.ts's own hook — and that hook is scoped to one .template.html's command script importing another's.

The proposal is to close that gap rather than accept it: give library code a real document shape — source and its own tests co-located, addressed the way script-hooks.ts already resolves a path.html#locator specifier under Node — instead of a permanent exception carved out for anything that has to be importable. templateFile()'s plain readFileSync would need to become "pull one <script>'s textContent out of a parsed document" for the client-inlined case, which is close to what script-hooks.ts's own findScript() already does for the Node case.

A browser-side counterpart, so a generated page's own client scripts could import the same way, was the first avenue explored for this — a service worker rewriting module fetches. That avenue turned out mostly closed: it cannot serve a plain, copy-anywhere generate output at all, and even where it would apply it needs a different addressing scheme than the Node hook's #locator. The Node-side extension of the existing hook stays open regardless of how, or whether, a browser counterpart ever gets built.
