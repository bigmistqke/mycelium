walkFiles skips what .gitignore already excludes implemented 2026-08-20

An earlier followup, now done, named the gap: walkFiles in src/utils.ts skips node_modules and any dot-entry by name, but nothing tells it about .gitignore. Running page generate or page index locally writes build output onto disk — under .mycelium/page/, or as .mycelium/index.html — and every family's own fs.list() walks through corpusView, which walks through walkFiles, so the next validate finds that output sitting beside real source documents.

A generated page is not a document anybody wrote, so checking it against prose-follows-the-language or every-link-resolves fails a build over prose nobody authored and links nobody meant to check. The project's own .gitignore already states which paths are build output — .mycelium/page/, .mycelium/index.html, .mycelium/notebook.html, .mycelium/chain.html, and every *.failure.png a browser test case leaves behind — so the walk had an answer sitting beside it the whole time, unread.

walkFiles reads the nearest .gitignore once, and reuses it

walkFiles keeps its own signature, one directory in and a flat file list out, so every existing caller — corpusView, seedPaths, findTemplateFile, the audit walking src/ for prose-follows-the-language — changes nothing about how it calls in. Internally it now looks for the nearest .gitignore above the directory it was handed, walking upward the same way git itself resolves one, and reuses whatever it finds for every entry in that walk. A project with none — this package's own seed, dropped fresh into a consumer with no git history yet — walks exactly as it did before, since a matcher that never gets built ignores nothing.

The lookup is cached per starting directory, in a module-level map that outlives one call. fs.list() runs dozens of times over one validate, each one a fresh call into walkFiles, and re-reading and re-parsing the same .gitignore that many times would cost real time for an answer that cannot have changed since the process started.

The ignore package parses the file; walkFiles only asks it questions

Real .gitignore syntax carries negation, directory-only patterns and glob semantics a naive string match gets wrong at the edges, and this project does not want a second, worse parser for a format git already parses correctly. ignore is a small, widely used package doing exactly this one thing, so walkFiles adds it as a dependency and calls .ignores(path) once per entry rather than reimplementing pattern matching by hand.

Each entry is tested with a path relative to the .gitignore's own directory, since that is the root every pattern inside it names — not relative to whatever directory walkFiles started from, which may sit several levels below. A directory entry is tested with a trailing slash appended, since a pattern like .mycelium/page/ only matches a directory and the package needs that told to it rather than inferred from the entry existing on disk.

  • Nested .gitignore files below the one nearest the walk's own start. This repository carries exactly one, at its root, and git's own support for several stacked ones is not a shape anything here exercises today.
