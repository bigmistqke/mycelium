webdriver.lib.html: a lib file with no assets to sit beside, and the directory that follows from that implemented 2026-08-19

A prior direction names the gap this closes. lib.template.html's own spec proved the *.lib.html shape on one file, graph.lib.html, and deliberately left its directory undecided: graph.lib.html reads graph.template.css and tokens.css through a path computed from its own location, so nothing about that one file could say whether "beside its own template" was a rule or an accident of where the first example happened to sit.

src/webdriver.ts is a second, real, already-used file. canon.template.html imports ELEMENT and withBrowser, and calls both; it also imports chromePath and sleep, and calls neither, so two of its four imports are dead weight. notebook.template.html imports and calls withBrowser alone. None of webdriver.ts's functions read a file relative to their own location; every one takes its inputs as arguments or reads process.env. Porting it into the lib.template.html shape is mechanical, the same worked pattern graph.lib.html already proved. Where the result should live is not.

The convention was already the right shape; only the directory was missing

lib.template.html's own template-files field already said a lib file sits "beside whatever assets its own functions read." That is not a placeholder for a directory decision — it is the decision, stated in terms of asset locality rather than a fixed path. A lib file with no such asset has nothing to sit beside, so it needs its own home: .mycelium/lib/<slug>.lib.html. webdriver.lib.html lands there. graph.lib.html stays in .mycelium/templates/, beside graph.template.css, tokens.css and the three *.element.js files its own namedScripts reads by name — moving it would mean moving all four together, a real migration this spec does not do.

webdriver.lib.html carries four functions; the rest of webdriver.ts is private

ELEMENT, sleep, chromePath and withBrowser each get their own <lib-function>, since each is independently addressable by id, the same reasoning that gives graph.lib.html's templatePath and templateFile their own entries. The port drops the two dead imports canon.template.html carried rather than repointing them at something nothing calls. chromedriver, session, chromeBuild and unpack exist only to make withBrowser work, the same way graph.lib.html's graphPage keeps its own private tokensFile helper rather than promoting it to a fifth lib-function. withBrowser's own script imports sleep and chromePath back from their own ids, the same cross-function reuse graphPage already does for templateFile.

What gets a test, and what does not

sleep and ELEMENT are deterministic and get one each. chromePath reads process.env.CHROME_PATH before it ever touches the filesystem, so setting that variable to a fake path and reading it back tests the function without needing a real Chrome install. withBrowser gets none, carrying the same explanatory comment serveGraph did before it was retired: it spawns a real process and speaks a real protocol to it, so it is exercised by running it rather than by a case that could complete without one.

Both templates repoint their import; the package export goes

canon.template.html and notebook.template.html both change import { … } from "mycelium/webdriver" to one import { … } from "../lib/webdriver.lib.html#…" per function actually called, matching how both already reach graph.lib.html. src/webdriver.ts is deleted once nothing imports it, and package.json's own "./webdriver" export goes with it — the same cleanup the lib-template port already did for graph-page and graph-serve, since a bare subpath with no confirmed external consumer is dead weight rather than compatibility.

  • Moving graph.lib.html into .mycelium/lib/ too. It stays exempted by its own asset reads, as this spec's design section states; migrating it means moving four files together, not one.
  • Seeding .mycelium/lib/ or lib.template.html into a consuming project. Investigating this surfaced a real gap — neither is part of SEED_FAMILIES or seedPaths()'s directory walk today, so a seeded notebook.template.html's own relative imports into graph.lib.html and now webdriver.lib.html resolve inside this repository and are not confirmed to resolve in a fresh consumer. Recorded as its own followup rather than folded into this port, since fixing it well means auditing the whole seed list, not adding one more directory to it by hand.
