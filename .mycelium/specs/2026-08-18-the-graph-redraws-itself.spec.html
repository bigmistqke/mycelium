The graph redraws itself while somebody works implemented 2026-08-18

The notebook drawing is a one-shot. notebook generate graph parses every entry, asks git for the day each one arrived, writes a self-contained page and prints a file:// URL. Somebody who then writes an entry runs the command again and reopens the page, which throws away the selection, the kind filters and the scroll position every time.

That loop costs about three seconds, and about two of them go before the command starts. mycelium --help alone costs roughly the same two, because the engine compiles each family's embedded scripts at load. So a watcher that re-invokes the command line spends two thirds of its bill re-learning what a command is, and a loop that holds one process open does not. The entry starting-the-process-costs-more-than-the-work.practice.html records the measurement.

Two faults hide inside the one-shot, and a redrawing page meets both immediately. An entry nobody has committed has no commit to take a day from, so it opens the drawing in a nameless column at the far left — and that entry is exactly what somebody watching wants to see. Every node address is an absolute filesystem path, because the corpus moved from docs/ to .mycelium/ and two prefix strippers stayed behind. The entries a-new-entry-has-no-day-to-stand-in.practice.html and a-rename-leaves-a-prefix-stripper-behind.practice.html hold both readings.

generate gains --watch. With it the command builds the page as it always did, holds the process open, serves that page over HTTP and redraws it whenever the corpus underneath moves. Without it the command writes a file and exits, exactly as today, which is what deploy-pages.yml keeps calling.

A new file, graph-serve.ts, sits beside graph-page.ts and holds the server, the change channel and the watcher. Both families already import mycelium/graph-page, so canon generate --watch costs one more argument rather than a second copy. Each family hands the module a function that rebuilds its data and the paths worth watching.

Rebuilding needs the data on its own, and today generate reaches the end holding a whole page. So the command splits into a builder returning the nodes, the edges and the arrival dates, and a thin caller that wraps those in graphPage and writes them. The first request serves the page; every change after it sends only the data.

The server roots at the corpus, so a click on a node's where link opens the real document rather than a dead path. That works only once an address goes back to naming a file relative to the corpus, which is why the stale docs/ prefix leaves as part of this rather than after it. The same fix un-breaks the pane link and the permalink hash on the published site.

One route carries changes, as text/event-stream, and what the page does depends on which file moved:

  • a notebook document, or the family's own ranking script (notebook.element.js) — the page swaps the JSON under #notebook, re-evaluates the ranking script in a fresh function scope and mounts the drawing again;
  • graph.template.css — the page replaces the text of its own <style> and redraws the wires, with no remount;
  • graph.element.js — the page reloads, because mountGraph closes over its state inside an IIFE, and the listeners it registers on the grid and the window have no way to unregister themselves before a fresh copy of the same code registers a second set.

Only the shared drawing engine forces a reload. The family's own ranking script registers no listener and holds no closured state of its own — it reads the current data and calls the one mountGraph that exists, so re-running it fresh is exactly what a data change already does. Splitting this from the shared engine landed while building the server: a probe run in a real headless browser showed that re-running a script this way is only unsafe for the piece that attaches listeners once and cannot detach them, and the ranking script has never been that piece.

Mounting twice nearly works already. render clears the cells it rebuilds, and a second mount breaks in three small ways: buildFilters appends chips without clearing them, mount registers the same four page listeners again so a click toggles twice and nets to nothing, and kindOf, addressByHash and relColour keep keys for nodes that have gone. All three take a line each.

The URL holds which kinds a reader has switched off, as ?hide=practice,research, written through history.replaceState and read back on every mount. Selection already lives in the hash, and the page already reads location.search for measure, so a view's settings have somewhere established to sit. This makes a filtered view a link somebody can paste, and it means a remount recovers its state from the address bar instead of inheriting it from a closure that any reload would clear.

An entry git has never seen takes today as its day. The rule that an entry carries no date holds because git answers for every committed file, and this is the one case where git has no answer. The fallback applies to a plain generate over a dirty tree too, which is the same statement: an entry nobody has committed is arriving now.

Nothing new joins the dependencies. node:http and node:fs's own watching cover all of it, the way the earlier explore server design already assumed.

Nothing edits the corpus from the page. A drawing that writes back is a different design with a different failure mode, and the authoring commands already own writing.

The watcher covers one family's own directory and the three template files its page inlines, not the whole corpus. A spec or a canon claim changing moves nothing in the notebook drawing, and watching everything would rebuild on every keystroke somebody spends elsewhere.

A change to a command script inside a template does not reach the running server. The process holds those modules compiled, and swapping them means the kind of module invalidation this project has no reason to build. Restarting is the answer, and the server says so when one of those files moves.

Publishing stays as it is. deploy-pages.yml calls the one-shot generate --out index.html, and nothing about a watch mode changes what CI writes.

How long to wait after a file moves before rebuilding. One authoring command writes one file, so a short window covers it, and a rebase or a branch switch moves hundreds at once and wants a longer one.

Whether the chain drawing needs anything the notebook does not. It ranks by a vocabulary of claims rather than by days and it has no arrival dates to fall back on, so its builder may be the only part that differs.

What happens to a permalink somebody already saved. Corpus-relative addresses change every hash the published site has ever handed out, and nothing redirects an old one.
