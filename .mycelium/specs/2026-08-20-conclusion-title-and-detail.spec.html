notebook-conclusion: a title and a detail, the way an entry has both implemented 2026-08-20

An earlier followup, now done, named the gap: notebook-conclusion held one blob of markup and nothing scannable, so reading a case's conclusions meant opening every one of them in full. An entry's own notebook-title and notebook-detail already solve exactly this for the record as a whole — a one-line summary a reader can scan, and the reasoning underneath it — but a conclusion never got the same split.

The corpus already showed the cost. Four instances existed before this spec, one of them three paragraphs long, and every one of them read as an undifferentiated block: nothing in notebook show's own output, or in the markup itself, let a reader tell what a conclusion claimed without reading all of it.

notebook-conclusion becomes a nested type, the way notebook-case already is

notebook.template.html gains a <template id="notebook-conclusion"> declaring two children: notebook-conclusion-title, required and plain text, and notebook-conclusion-detail, optional markup. Both the case-level field (repeatable, carrying data-on) and the document-level field on notebook-experiment (singular, no data-on) now reference it through conforms-to="#notebook-conclusion" instead of declaring markup directly, the same mechanism notebook-case already uses to nest under notebook-experiment.

Detail stays optional rather than required. A short conclusion can be its own title, and forcing a second field under it would recreate the empty-boilerplate problem --detail already solves for entries by being required only where a title alone says too little.

Both conclude commands take --title and --detail

notebook experiment case conclude <file>#<id> --title "…" [--detail "…" | --detail -] and notebook experiment conclude <file> --title "…" [--detail "…" | --detail -] replace the old single --conclusion flag on both commands. A shared fillConclusion helper writes both children in the right order, backing a fresh case-level conclusion and an in-place update of the document-level one alike.

Document-level conclude keeps its replace-not-accumulate behaviour: an empty --title clears the existing conclusion, the same way an empty --detail clears a field on notebook update. Case-level conclude keeps appending, since a case gathers conclusions over time the way an existing principle already argues several cases should stay apart rather than merge.

show and del print the title, not the whole body

notebook show prints a conclusion's concluded <date> line with its title beside the date, and only prints the detail underneath when one exists. case del and case update print the same title on the line announcing what a deleted case took with it, so the honesty that command already promises now names what it drops, not only when it drops it.

  • Requiring notebook-conclusion-detail. Left optional so a one-line conclusion stays one line, unlike an entry's own notebook-detail, which this spec's problem section explains is required for a different reason: an entry has nothing else to record what happened.
