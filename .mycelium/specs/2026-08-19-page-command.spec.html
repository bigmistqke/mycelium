page.command.html: a shared home for generating and serving a page implemented 2026-08-19

A prior direction names the gap this closes: a generate command is a plain function discovered by naming convention, documented only in prose a person keeps in sync by hand. Nothing states, in a form validate or a reader could check, what a generate command produces or how to reach it.

The three commands that already generate a page also disagree with each other in ways that gap makes easy to miss. notebook generate graph and canon generate chain/measure both call graphPage() (graph-page.ts) for their shell and get --watch for free through graph-serve.ts. explore generate index reimplements its own shell from scratch, including the doctype, style embedding and escaping that have nothing to do with what it draws, and has no watch mode at all. Canon's own watch gap is already recorded as its own followup. Every one of these differences is a fact about how each family's own generate happened to get written, not a decision anyone made on purpose.

Each family also hand-rolls how its own output reaches disk or a browser: an --out flag, a bare stdout write, or a bespoke HTTP server wired into that one family's own script. None of that is shared machinery, so a fourth family wanting a generated page has nothing to reuse and no address to give a reader who wants to open one.

page is a command file, not a template

page.command.html declares no <template id>, so nothing conforms to it — the same shape explore.command.html and comments.command.html already have: a whole-corpus tool with no files of its own. It holds the machinery every page-producing family would otherwise reimplement: writing output to a derived path, and serving it fresh on --watch.

A family's own page export stays a pure function

A family that wants a generated page exports a page table the same way a command table already works: export const page = { index(): string { ... } }, one entry per page it can produce. Each leaf takes the corpus and returns the finished HTML as a string — or a Promise<string>, for something like canon's measure, which drives a headless browser to read a figure's own layout. A leaf knows nothing about paths, flags, or serving; it stays exactly what graphPage()'s callers already are today, a function from corpus state to markup.

page.command.html finds every family's own page table

Its own command walks the corpus the way explore generate index already walks every family looking for a template-host, except it looks for a page export instead. Reaching into another family's script to call that export uses the same mechanism this project already built for one script to import another by path.html#id — a capability that spec named "cross-family command reuse" as one of the things it would unlock, without a caller for it yet.

The output address is derived, not typed in

A page's path is computed from the same verb path the engine's own resolver already builds while walking a nested command table to find the function to call — page/<family-id>/<verb path>.html. No --out flag for the common case: the address a reader opens is the same path the command line used to reach the function that built it.

--watch becomes one generic feature, not one per family

page.command.html owns a single watch server: given a family and a verb, it re-calls that page's own function on every request and serves what it returns, the way graph-serve.ts does today only for notebook and canon. Every family with a page export gets this for free, which closes canon's own watch followup as a consequence of this shape rather than as a separate port of graph-serve.ts.

page.command.html's own dispatch is discovered, not declared

It cannot know ahead of time which families export a page table, so it reads and looks up its own <family> <verb> arguments at runtime, rather than matching them against a static nested object the way experiment's verbs now do. This is not a new gap: it is the same shape mycelium <id> <command> itself already has, discovered by walking files rather than declared as an enum anywhere.

Nothing here changes run.ts

This stays inside the command-script vocabulary the engine already resolves generically. run.ts's own header names its one rule — protocol-only, never what any command actually does — and writing and serving a page is exactly the kind of thing that rule says does not belong there.

  • Migrating notebook's, canon's, and explore's existing generate commands onto this shape. This spec specifies the mechanism a family would use; doing that migration is separate work, not required to land this.
  • Sharing a page's own visual shell across families. Deriving where a page's output goes does not derive what it looks like — graphPage() is still only reused by the two families that already call it, and this spec does not change that.
  • Any change to how run.ts resolves an ordinary command. This spec's whole point is that none is needed.
  1. Does page replace generate as the verb name — a breaking rename across every family that has one today — or sit alongside it? Unresolved.
  2. Does a page's output under page/<family>/... get committed, and if so, what stops a committed one from going stale the way a hand-authored document already has in this project more than once? An audit comparing a tracked page against what regenerating it produces right now is the obvious answer, and is not specified here.
  3. The exact path convention for a verb path more than one level deep — how a nested page.someGroup.someKind(), should a family ever want one, maps into a filesystem path — is not settled beyond the flat case worked through above.
  4. Whether page.command.html writes the corpus-walking, script-hooks-loading pattern it needs fresh, or factors it out of explore.command.html, which already does the same walk for a different purpose. A smaller instance of the still-open question in whether reusable library code belongs inside a document.
