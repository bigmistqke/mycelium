page.command.html grows a real dev server: livereload and static passthrough, retiring notebook's and canon's own generate implemented 2026-08-19

A prior direction names the gap this closes. page.command.html's own spec claimed that its generic --watch would close canon's long-open watch gap, at the time still tracked as its own followup and since deleted by this spec's own work, "as a consequence of this shape rather than as a separate port of graph-serve.ts." That claim was not yet true. serve() re-ran a page's own leaf on every request and nothing else: no file watching, no push to an open tab, and no route for anything but /. Neither notebook's own generate graph --watch nor canon's chain had moved onto it, because moving would have traded away two things graph.lib.html's serveGraph already gives notebook: a reader's tab redrawing itself without a manual reload, and every link the drawing carries back into the corpus actually resolving.

serveGraph solves both, but only for the two families that already call it, with logic tied to graph pages specifically: it names a shared script, a ranking script and a CSS file by path, and pushes one of three kinds of update depending on which changed. Canon cannot reach it today for an unrelated reason: its chain-building code reads through auditFsOver(fs), a wrapper over the engine's own CommandFilesystem, which parses once and never again — the same limit notebook's own graph-building code carried until corpusView() replaced it, recorded in a notebook entry about what a fresh-per-call view was for.

serve() gains a livereload channel, not a graph-shaped one

Every page's own leaf is already a pure function of corpus state with no per-family shape page.command.html can see. So the mechanism it adds cannot discriminate "just the data changed" from "just the styling changed" the way serveGraph does for a graph page's own known DOM. It can only tell that something under the corpus moved. On any such change, debounced the same 250ms serveGraph already uses, serve() now sends a reload message over a /_reload server-sent-events channel to every open tab, and the HTML each request returns carries a small inlined script subscribing to it.

A full reload rather than an in-place patch is a real step down from what an open notebook graph does today: a selected node's pane closes on the next edit instead of staying open through it. Accepted anyway, because every family gets this uniformly, canon included, instead of one family keeping a richer watch nothing else can reach.

What to watch is derived from the corpus fs.list already returns

serveGraph took one explicit watchDir because notebook was its only caller and notebook's own documents sit in one place. page.command.html has no such fixed directory to hand it, and a family's leaf declares no watch paths of its own — the "a leaf knows nothing about paths, flags, or serving" rule page.command.html's own spec already states would have to bend for that. Instead, serve() calls fs.list(".") once at startup, collects the distinct parent directory of every path it returns, and watches each non-recursively with node:fs's own watch, the same primitive serveGraph already uses, aimed at every directory holding a document instead of one.

serve() also answers for the corpus paths a page links to

A drawing's own links point back into the corpus as paths relative to wherever the page itself sits, so a reader can open the entry a node names. serveGraph already carries a serveStatic that maps any request other than / or its own event channel onto a real file under the corpus root, refusing one that climbs above it. serve() gains the same fallback, generalized from graph pages to any page: a family gets working outbound links for free, the same way it gets livereload for free, because both were true of one family's hand-rolled server and neither has anything graph-specific in it.

notebook and canon each export a page leaf building fresh from disk

notebook.template.html's graphData() already reads through a corpusView() rather than the engine's cached filesystem, built for exactly this repeated-rebuild case. Its new page.graph() calls it the same way the deleted --watch branch did: corpusView(corpusRoot, "."), fresh on every call, wrapped in graphPage() with a <base href="../../"> tag, since page.command.html writes it two directories below the corpus root (page/notebook/graph.html) where the old notebook.html sat at the root.

Canon's chain-building logic moves from generate() into a private chainPage(base) function, reading through corpusView(repoRoot, CORPUS_DIR) in place of auditFsOver(fs), the same fresh-per-call substitution notebook already made, closing the followup's own stated blocker rather than working around it. page.chain() calls chainPage('<base href="../../">'); measure, which never follows a link and only counts what a headless browser renders, keeps calling the same function with an empty base and writing the result to its own temp file, since driving Chrome to read a figure's layout is not something a page leaf does.

generate disappears from both families; serveGraph and its hmrClient disappear from the library

notebook.template.html's and canon.template.html's own generate exports go, along with the --out/--base/--watch/--port/--open surface each carried. mycelium page generate notebook graph [--watch] and mycelium page generate canon chain [--watch] replace both. Once neither calls it, graph.lib.html's serveGraph lib-function and its hmrClient helper are dead code and come out, along with the now-unused hmrClient? field on GraphPage — page.command.html injects its own reload script into the returned HTML string directly, so a leaf's own shell never needs a slot for one.

A family's own page links move onto its own card

readCommands already reads export const page = {...} the same way it reads any other exported command table, since nothing about the shape tells it apart. Rather than teach it to, buildIndex() splits a family's own parsed commands by that one property name: an ordinary command stays a pill with a tooltip, and a page verb becomes a real link at page/<family>/<verb>.html under a new "Page" heading on that family's own card. The hardcoded top-level "Drawings" list, naming only notebook and canon by hand, goes with it — any family exporting page now surfaces its own output the same way, with no second place needing to know the two names.

The deploy workflow moves with the address

.github/workflows/deploy-pages.yml's two build steps, mycelium notebook generate graph --out notebook.html and mycelium canon generate chain --out chain.html, become mycelium page generate notebook graph and mycelium page generate canon chain.

  • Restoring serveGraph's partial data/CSS swap in any generic form. Nothing about a page's own leaf tells page.command.html what changed, only that something did, and inventing a protocol for that with one real caller ever having wanted it is exactly the abstraction this project's own rules argue against building ahead of a second need.
  • Watching a family's own code for changes. serve()'s existing doc comment already states this limit — Node's module cache hands back the old version of a leaf's own script regardless — and nothing here changes it; only corpus documents trigger a reload.
  • Any change to page index's own asset handling. The corpus-wide landing page links to theme.css by a relative href already, a pre-existing gap this spec's static passthrough happens to close as a side effect, not something it sets out to fix.
  1. Whether a family wanting a third kind of push — something between "nothing changed" and "reload everything" — ever arrives, and whether that argues for a small opt-in hook on a page's own leaf or stays a one-off the way serveGraph was. Unresolved until a second family actually wants one.
