lib.template.html: reusable code as a real document, not a bare file implemented 2026-08-19

A prior direction named the gap this closes: reusable code such as graph-page.ts and graph-serve.ts sits outside the document vocabulary as a bare file, unlike everything else in the corpus, which lives as an .html document a schema can check and a reader can open through an ordinary link. The same direction scoped a fix to extending script-hooks.ts's existing path.html#id import mechanism, since a browser-side counterpart hit real platform walls — recorded separately as a fetch handler never sees a request's fragment and a file:// page can't register one at all.

graph-page.ts's graphPage() and graph-serve.ts's serveGraph() are a concrete, live pair to prove this shape against: notebook.template.html imports both, canon.template.html imports graphPage alone, and graph-serve.ts itself imports graphPage internally to rebuild the page it serves. Three real call sites, not a toy example.

lib.template.html declares the shape; a *.lib.html file is an instance

A library becomes a real template family the same way notebook or canon is one: lib.template.html declares a <lib-doc> schema, and each library — graph.lib.html, say — conforms to it via data-conforms-to. That alone makes a library validate-checked and corpus-citable, which a bare .ts file never was.

One function, one lib-function element

A library holds one or more <lib-function> elements, each carrying its own doc and its own script: 

<lib-function>
  <lib-function-doc><p>Assembles the graph page's full HTML shell...</p></lib-function-doc>
  <script id="graphPage" type="mycelium/lib">
    export function graphPage(page) { ... }
  </script>
  <lib-function-test>
    <script type="mycelium/test">
      export default async function ({ assert }) { ... }
    </script>
  </lib-function-test>
</lib-function>

<lib-function-doc> sits as its own sibling field rather than a leading code comment, matching how every other description in this corpus already sits beside what it describes — template-purpose beside a family, not commented above its script. The id lives on the <script> itself, never on the wrapping <lib-function>: giving both the same id looked harmless during this port and was not — a duplicate id resolves to whichever element the DOM finds first, so the wrapper's own mixed doc-and-code text reached the loader instead of the script's, and the failure read as a syntax error in code that was never wrong.

Addressing and language reuse existing mechanism, not new engine code

import { graphPage } from "../templates/graph.lib.html#graphPage" resolves today, through the same path.html#id hook built for cross-family command reuse. A script typed mycelium/lib gets the same TypeScript-stripping every other mycelium/* script already gets, from formatFor() in script-hooks.ts. Neither needs a change — true for a specifier written literally with its own fragment, which is how every internal caller reaches a library. It is not true for a bare package subpath resolved indirectly through package.json's own exports map; see the resolution below.

A lib gets its own test command

mycelium lib test [<file>] runs every mycelium/test case attached to a library's own functions, the way canon test runs a behaviour's. It is a new command, not a reuse of canon test's runner — that one is walking canon documents specifically for behaviour citations, a different question from "does this function do what its test expects."

Where a *.lib.html file lives is decided per file, not by a fixed directory

graphPage() reads graph.template.css through a path computed relative to its own file's location. Moving that file into a new top-level directory would silently break that read, since the CSS and the client scripts it inlines are not moving in this pass. graph.lib.html stays in .mycelium/templates/, beside the assets it actually reads, rather than adopting a directory convention this port does not yet need.

graph.lib.html: the first port

graphPage, serveGraph, and the smaller helpers real callers already depend on — namedScripts, templatePath, templateFile — move into one graph.lib.html, since serveGraph already depends on graphPage internally and splitting them across two lib files would only add a cross-lib import with no benefit. notebook.template.html and canon.template.html both repoint to it directly; graph-page.ts and graph-serve.ts are deleted once nothing imports them.

Resolved: the external subpaths turned out not to be needed at all

A bare package subpath like mycelium/graph-page carries no fragment in its own specifier text — Node's exports map only produces one internally, inside its default resolver, after script-hooks.ts's own hook has already deferred to it. Pointing a subpath straight at graph.lib.html#graphPage therefore resolves the path correctly and then fails to load it, confirmed by a notebook experiment that reproduced the failure through the real mycelium CLI, not just a bare Node process.

A small re-exporting .ts shim fixed it — its own literal imports write the fragment, so they resolve the ordinary way. But nothing in this corpus, and no confirmed external consumer, actually imports mycelium/graph-page or mycelium/graph-serve any more: every internal caller already addresses the library directly. The subpaths and the shim were both removed rather than kept for a consumer that does not exist.

  • Porting shared.ts, canon-citations.ts, or any other bare library file. This spec proves the shape on one real, already-used pair of functions; the rest migrate later.
  • The homecooked, nimble-html-inspired string-templating tag function discussed earlier. A real, separate piece of work, and a natural second *.lib.html once this shape exists.
  • Giving canon's own graph drawing a watch mode. serveGraph moves as-is; nothing here changes what it does or who calls it.
  • A directory convention for where *.lib.html files live in general — deferred until there is more than one real example to generalize from.
