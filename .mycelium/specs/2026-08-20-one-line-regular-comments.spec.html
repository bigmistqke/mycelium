This project's own working style leans on long, multi-paragraph // comments throughout src/ and every template's embedded command scripts, each one explaining a rejected alternative, a constraint from outside the file, or a bug a design avoids. That style is itself the problem this spec answers: a comment spanning several lines is exactly the shape a decision recorded in the wrong place takes, and comment-earns-its-place.guide.html already names that failure — a comment naming a rejected alternative is a decision that nothing can query, and moving it beats deleting it — without anything ever checking for the shape that failure takes.

comments check/comments autofix already judge every comment against that guide through a model call, and already skip the model entirely for two shapes that need no judgment: it cuts a WIP-tagged working note outright, and keeps a doc comment on an export outright, because the roster prints it. A multi-line regular comment joins those two. Whether a comment spans one line or several is a fact about its shape, not a question about its content, so it needs no more judgment than the two shapes already decided without asking.

comments check cuts a multi-line regular comment without asking the model

isMultiLineRegular() in comments.command.html reports true for a comment whose raw text carries a newline and does not open with /** — a doc comment stays exempt, since its shape and its multi-paragraph JSDoc tags answer to a different standard entirely, the one isRosterDoc() already protects. judgeAll() checks it alongside the two existing no-model shapes, in the same if/else if chain, cutting the comment and naming why, before it ever reaches toJudge.

This shape carries no promote path. promote exists for a comment the model reads as carrying rationale worth moving rather than losing, and a mechanical shape check makes no such reading — it only knows the comment spans more than one line. Promoting a multi-line comment that carries real rationale needs a person's own hand, the same notebook practice/notebook principle commands this project already has for exactly that, before autofix ever touches the file it sits in.

The guide states the same rule the check now enforces

comment-earns-its-place.guide.html's own detail gains a line saying a comment fits on one line, full stop — the standard a reader of the guide meets is the same one the command now enforces mechanically, rather than a narrower one the guide states and a wider one the code silently adds beside it.
