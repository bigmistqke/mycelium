A corpus index that lists every file and links every generated graph draft 2026-08-18

The published site shows one page: deploy-pages.yml writes the notebook graph straight to index.html via mycelium notebook generate graph --out index.html. A visitor lands on that drawing and nothing else, even though every document under .mycelium/ is already its own static page with resolvable relative links — the corpus has been a website since DESIGN.html said so.

Two generators already exist and only one runs in CI. canon generate chain --out <path> draws the axiom-to-declaration chain the same way notebook generate graph draws the notebook, but nothing in the workflow calls it, so the chain page is unreachable from the published site. Neither generator's output links back to a page listing what else the corpus holds — a reader who does not already know the directory layout has no way to find a spec, a followup, or a canon subsystem from the front page.

A new command, mycelium explore generate index [--out <path>] [--base [<href>]], mirrors the signature notebook generate graph and canon generate chain already use. It writes one page: a list of every file the corpus holds, grouped by the family that governs it, plus links to the two drawings and a short line about the project.

Grouping stays protocol-only, the way the rest of explore.command.html already reads the corpus. explore list already walks every element carrying data-conforms-to, skipping a template's own worked examples via declaresATemplate; generate index reuses that same walk. Each instance's data-conforms-to names a template file and a fragment — stripping the fragment gives the template that instance's document belongs to, and grouping by that template file is grouping by family with no family-specific code anywhere in the command.

Every templates/<family>.template.html and commands/<name>.command.html already carries a <template-host> — <template-purpose> is a required one-line description of what the family is for, and <template-design> holds one or more <a href> to the specs behind it, already checked by every-link-resolves. The section for a family reads both straight off its own template file: the purpose becomes the section's one-line description, and the design links become "read the spec" links beside it. Nothing new gets written to describe a family a second time.

Under that, the section lists every file whose instances grouped into it — one line per file, not per instance, since a canon subsystem or a notebook entry is a file a reader opens, and what conforms inside it is this command's own bookkeeping. The link text is the file's own <title>, which every document already carries for its browser tab. A file with no data-conforms-to element at all and no template[id] of its own — today only DESIGN.html — is not part of any family section; its title and a short quote from it becomes the page's own "about" line, so the index says what the project is without restating DESIGN.html's argument a second time.

Two links sit above the family sections rather than inside one: the notebook graph and the chain graph, each now written to its own file — notebook.html and chain.html — instead of one of them claiming index.html for itself. deploy-pages.yml gains two generate steps alongside the one it already runs, and its existing "Build the index" step becomes explore generate index --out index.html. The workflow already uploads the whole .mycelium/ directory, so no step beyond the three generate calls changes.

All three generated files stay out of git, the way index.html already does — a local --out run is for looking, and the committed corpus holds nothing that resolves a link into them, so every-link-resolves has nothing to check there.

Whether the notebook and chain pages should link back to the index once it exists, the way a <base>-resolved page already links into individual documents. Today neither one carries any navigation back out. Left for whoever builds this to decide once the index page's own layout is in front of them.
