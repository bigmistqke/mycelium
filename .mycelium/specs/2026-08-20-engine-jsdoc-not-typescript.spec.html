The engine's ten node_modules-only files become plain JavaScript with JSDoc implemented 2026-08-20

A real (non-symlinked) install of this package cannot run at all on stock Node 24, confirmed by packing a real tarball and installing it rather than trusting this repository's own symlinked link: dev dependency, which hides the failure entirely. bin/mycelium.js's own import "../src/run.ts" throws ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING: Node refuses to strip types for a .ts file whose real path passes through node_modules, a deliberate, currently permanent restriction with no opt-in flag (nodejs/node issue 57215 tracks the open request and remains unresolved). Isolated testing confirmed the same failure for every one of the package's own mycelium/* exports — shared, extract-graph, language-prose, code-comments, canon-citations — since each resolves to a .ts file through the same restriction.

A prototype confirmed a loader-hook workaround works too: register a custom Node module hook before the failing import, transpiling .ts on the fly with the typescript package already depended on, bypassing Node's native stripping path entirely. This spec drops it anyway. It ties the fix to the exact shape of today's restriction rather than removing the reason it exists, and it means shipping two different strip mechanisms — Node's native one for corpus scripts, a hand-rolled one for the engine's own — for what is, underneath, the same problem.

The restriction only ever reaches nine files, confirmed by tracing where it can bite

Corpus documents never need any of this. Once seeded, notebook.template.html and every other family template live inside a consumer's own project, never inside node_modules, so their own <script type="mycelium/command"> blocks already load through Node's native stripping with no restriction ever applying — confirmed directly, running notebook principle add end to end against a real packed install with only the engine's own bootstrap patched around. The restriction only touches files that permanently live inside node_modules/mycelium/: the five files package.json's own exports map names, and src/run.ts, src/utils.ts, src/retext.ts and src/script-hooks.ts, which those five and the entry point import in turn.

src/api.ts is the tenth file in that same set and needs nothing done to it. Every reference to it anywhere in the corpus or the engine uses import type, which verbatimModuleSyntax guarantees erases the whole import statement rather than leaving a runtime one behind — nothing ever asks Node to load it, so the restriction that only fires on an attempted load never has anything to fire on.

Nine files become plain JavaScript carrying their types as JSDoc

run.ts, utils.ts, retext.ts, script-hooks.ts, shared.ts, extract-graph.ts, language-prose.ts, code-comments.ts and canon-citations.ts become .js, their type annotations rewritten as @param/@returns/@typedef comments rather than dropped. None of the nine uses a generic, a class, an enum or a namespace — checked directly rather than assumed — so every annotation carries over to JSDoc with nothing lost and nothing approximated. Plain JavaScript needs no stripping of any kind, on any Node version, inside node_modules or out, so the restriction stops applying because there is nothing left for it to apply to.

tsconfig.json already runs checkJs globally rather than gating it behind a per-file // @ts-check pragma — a switch made deliberately after three of six *.element.js files carried the pragma and three did not, leaving half of them unchecked with nothing saying so. These nine files join include the same way, so pnpm run typecheck holds them to the same standard it already holds every .ts file to, with no new mechanism and no pragma to remember.

Only the engine's own cross-references change; nothing seeded does

A relative import between two of these nine files needs its extension updated — run.ts importing from "./utils.ts" becomes from "./utils.js" — since a relative specifier names a real file rather than resolving through a lookup. package.json's own exports map repoints its five entries at the new .js files the same way, and bin/mycelium.js's own import becomes ../src/run.js.

Every corpus document importing one of these five stays exactly as it is. A command script writes import { declaredOrder } from "mycelium/shared", a bare specifier that resolves through the exports map rather than naming a file directly, so the map's own target changing from .ts to .js is invisible from the importing side. No template, no command host and no notebook entry's own worked example needs a single edit.

  • Every <script type="mycelium/command">/mycelium/audit/mycelium/lib block across the corpus — canon, notebook, language, template, followup, spec, figure, lib and every command host. None of it needed converting: confirmed directly that a seeded document's own script already loads through Node's native stripping unaffected, since seeding guarantees it never sits inside node_modules. Converting it anyway would be a much larger, unjustified rewrite answering a problem these files do not have.
  • The editor extension's own type-checking of embedded corpus scripts. It checks real TypeScript inside <script type="mycelium/*"> blocks, which this spec leaves untouched, so nothing about how it works needs to change.
