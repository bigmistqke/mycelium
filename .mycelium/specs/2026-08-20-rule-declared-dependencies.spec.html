A seeded rule declares its own package dependency, installed at seed time implemented 2026-08-20

A rule that needs a real library has one working path today: reach it through mycelium/retext, a re-export this package carries so a seeded corpus — which has only mycelium installed — can still resolve retext under either npm or pnpm. It works, but it hides a fact that belongs to the rule behind the engine's own export surface, and it pins every consumer to whichever retext version mycelium itself happens to depend on.

The dependency is the rule's, not the engine's. passive-voice.rule.html is the only file that needs one, and nothing about seeding — a pure filesystem copy today — ever looks at what a seeded document imports from outside the corpus.

A rule declares a dependency on itself, in a second <script> carrying type="mycelium/importmap": plain JSON shaped like a browser's own {"imports": {"retext": "^9.0.0"}}, but not that real type — these values are semver ranges for npm, not resolution targets a browser could act on, and claiming the real type would have a browser that honors import maps try to resolve them as module paths. language-rule's schema in language.template.html declares it optional, alongside the required, untyped script that carries the actual check. mycelium/retext and .mycelium/templates/retext.js go away; passive-voice.rule.html imports retext and retext-passive by their own name, and declares both in its importmap.

Two placeholders sharing one tag name is new: the generic validator in template.template.html matched a field by tag alone, so a second <script> read as a duplicate of the first. walkChildren now groups same-tag placeholders and picks among them by whichever declared attributes discriminate one from another — type here — trying the more specific placeholder before the bare one, which is what keeps "exactly one real check" true without a separate audit: an untyped script can only ever match the check slot.

Reading the importmap is a parse, not an import — JSON.parse on the script's own text. Importing it would run it through the same type-stripping module hook every other mycelium/* script loads through, and that hook refuses a file under node_modules, which is exactly where this package's own corpus sits in a real install. The same reason rules out feeding this script's raw JSON to the editor's own TypeScript checker: an object literal at that position reads as a block statement, so editor/language-plugin.ts now gives a mycelium/importmap block an empty virtual file instead of its real content, the one mycelium/* type that carries data rather than code.

Seeding gathers every mycelium/importmap script across the files it writes and installs the union into the consumer's own project once the copy finishes. package-manager-detector finds which package manager the consumer already used to install mycelium itself — a lockfile is already there by construction — and resolves that manager's own add command, run against the consumer's package.json directly. The package manager writes its own package.json and lockfile; nothing here parses or edits either by hand.

When detection finds nothing, seeding prints the packages a rule needs instead of failing the whole run, the same way a broken audience should not block everything ahead of it. This is the one place seeding leaves the pure-filesystem model it has held until now, and it does so because the alternative — a shim living inside this package for every dependency a future rule might ever want — repeats the exact problem a-seeded-document-imports-only-what-seeded-it.principle.html already named once.

No general dependency mechanism for every template family — only language-rule gets this field, because only one file needs it today. No interactive confirmation before running the install: seeding already writes files without asking, and this is one more write. No version reconciliation between two rules naming the same package with different ranges — nothing does that yet, because nothing needs to.
