mycelium knowledge update, and closing the field-shape gap approved 2026-07-23

CLAUDE.md names a real gap in the authoring commands as shipped: add only sets fields at creation time. Updating a field on an already-existing node — the exact case of adding <knowledge-commit> to an action node once its commit exists, which happens after nearly every piece of real work — still means a hand Read+Edit, the same file-content-through-the-model cost that building add/link removed for creation and linking.

A second, previously unnoticed gap surfaced while designing the fix: every type's check() in knowledge.template.html only checks that its required fields are present. Nothing checks that a node has only the fields its type allows — a stray <knowledge-status> on a knowledge-option would pass pnpm crawl today, silently, from a hand-edit or any future command alike. Fixing the first gap by having update carefully replicate add's per-type field-gating would leave the second gap exactly where it is; closing the second gap generically means the first doesn't need that replication at all.

Closed-schema validators, not just required-field checks

Each type's check(root) already has the list it needs: the required-tag loop (['knowledge-title', 'knowledge-confidence', …]) plus, for action and outcome, the optional-tag loop right below it (['knowledge-commit', 'knowledge-files', 'knowledge-branch']). Union the two into one ALLOWED array per type and add one more check: any element under the root whose tag name starts with knowledge- and isn't in ALLOWED is an error (unexpected <tag> on knowledge-<type>). This runs for every node on every pnpm crawl, against real files — the same "no sample fixtures" discipline the crawler spec already established. It catches a misplaced field regardless of how it got there: hand-edit, add, update, or any command a future template declares.

This is additive to each type's existing check(), not a new audit: it's still "one instance against its own template," the same data-validates contract, just a stricter version of a rule that was already partially there.

update: a fourth command, sibling to add/link

mycelium knowledge update <file> [--title "…"] [--confidence NN]
  [--status pending|active|completed|rejected] [--prompt "…"]
  [--commit HASH] [--files "…"] [--branch NAME]

<file> is an existing knowledge/*.html file, the same convention link's <from-file>/<to-file> already use. Unlike add, there's no <type> positional: update reads the type straight off the file's own root element (doc.querySelector('[data-conforms-to]').tagName), since the file already declares it and re-stating it on the command line would just be one more place a typo could cause a real mismatch.

Per flag, three states — and parseArgs already distinguishes the two that matter (run.ts:42-54: an omitted --flag never sets the key at all; --flag "" sets it to the empty string):

  • flag omitted (args.commit === undefined) — field untouched.
  • flag given a value — upsert: overwrite the existing element's textContent if the tag is already present, append a new element if it isn't. Order never matters, matching every check()'s use of querySelector rather than positional matching.
  • flag given an explicit empty value (args.commit === "") — remove that field element entirely. The documented case this exists for: write-template-series.action.html omits knowledge-commit on purpose because one commit didn't map cleanly to one node; update needs a way to walk a field back if the caller set it by mistake, not just a way to add one.

update does not replicate add's per-type field gating (REQUIRES_STATUS.includes(type), prompt only for goal). It writes whatever field the caller asks for, on whatever type the file turns out to be. The closed-schema check above is what catches a mismatch — on the next pnpm crawl, not immediately in the CLI. This trades immediate feedback for not duplicating the field-shape table in two places; the project's own session-start and pre-commit checklist already runs pnpm crawl before either of those points, so a mistake doesn't survive long unnoticed.

Where this lives

All in experiments/v4/docs/templates/knowledge.template.html: update as a third export in the existing type="mycelium/command" script, the closed-schema check as an addition to each of the six existing data-validates scripts. No changes to src/run.ts's or src/crawl.ts's engine code — both stay protocol-only, as the authoring-commands spec already established; this is entirely new business logic declared inside the template file, not new engine capability.

  • No edge removal. update covers node fields only; removing or editing an existing <a data-rel> edge is a different, unaddressed gap.
  • No immediate CLI-side validation. update (like add) doesn't run the file back through its own validator after writing; catching a mismatch still means running pnpm crawl, same as today.
  • No authoring commands for spec-doc. The second gap CLAUDE.md names — spec docs still needing hand-authoring — is untouched by this spec; this document itself was hand-authored, per that same gap.
  • No interactive prompts or auto-slugging. Same as add/link; every argument comes in on the command line.
