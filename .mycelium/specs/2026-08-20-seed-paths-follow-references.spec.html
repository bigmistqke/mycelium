seedPaths follows what a seeded document actually references implemented 2026-08-20

An earlier followup, now done, named a concrete crash: a freshly seeded consumer's own notebook.template.html imports ../lib/webdriver.lib.html#withBrowser and ./graph.lib.html#graphPage, and neither file reaches a consumer's corpus, because seedPaths() in src/run.ts only ever copied a hand-picked list: each SEED_FAMILIES family's own <family>.template.html/.css pair, plus everything under language/ and commands/. Reproducing it end to end (packing a real tarball rather than this repository's own symlinked dev dependency, which hides the gap) showed the failure is not narrow: the missing import sits at the top of notebook.template.html's command script, so every verb in the family throws, not only page generate notebook graph or a browser case.

The list was never going to stay complete by hand. It already missed two files this spec found, and a lib file a template starts depending on next month would miss the same way, for the same reason: nothing derives the list from what a seeded document actually needs, so nobody notices until a consumer's install throws.

seedPaths starts from the same roots, then follows what they reference

The family template files plus the full walk of language/ and commands/ stay exactly as they are — those are collections a fresh corpus wants wholesale, not something a link graph would ever derive. What changes is what happens next: every file in that starting set gets scanned for the local files it needs to load or run, each newly found file joins the set and gets scanned in turn, until a pass turns up nothing new. A family's own .css no longer needs its own line in the family loop, since the template's own <link> already says it needs one.

Four reference shapes, one parser each, never a pattern over raw text

localReferences() parses a document with the same happy-dom parser parseHTML already uses everywhere else in this file, and reads a <script>'s own source with the TypeScript compiler, the same way shared.ts's readCommands already does. A relative <link href> or <script src> counts, found by querying the parsed document. So does a data-conforms-to: a lib document is an instance of lib.template.html the same way a notebook entry is an instance of notebook.template.html, and validate opens that path too.

The first end-to-end run of this fix caught the gap directly: a freshly seeded graph.lib.html and webdriver.lib.html both failed validate with no template found at .mycelium/templates/lib.template.html#lib-doc before data-conforms-to joined the other shapes. A relative import … from "…" inside an inline <script> counts too, found by walking that script's own AST for ImportDeclaration nodes. <a href> never counts — that is a citation to other content, not something a document needs to run, and following it would pull in most of the corpus.

A third shape rides on the same AST walk: any string or template literal whose text is nothing but a bare filename ending .css, .js or .html. graph.lib.html reads graph.template.css and tokens.css this way, by name, through its own templateFile() helper rather than by href; notebook.template.html names graph.element.js and notebook.element.js the same way, in the array it hands to namedScripts(). Neither shows up as markup anywhere, so only a literal this narrow — never a general string scan — reaches them.

A generated instance's own script tag counts too, found the same way twice

notebook.template.html's add command writes <script src="../templates/experiment.element.js"> into the HTML string it builds for a fresh browser experiment — real markup, but sitting inside a JavaScript template literal rather than in notebook.template.html's own document. The AST walk already visits that literal as an ordinary string node; when its text contains <script or <link, localReferences() parses that text as its own small HTML document and recurses into it with the identical <link>/<script src> query. The same function runs twice, once on the whole document and once on a fragment of it, rather than a second, different mechanism existing for the fragment.

Every relative path resolves against its own directory first, the corpus root second

A real href, src or import specifier resolves against the file that carries it, which is what "relative" already means for all three. Two shapes cannot: a bare literal like "graph.template.css" carries no directory at all, and the string notebook.template.html writes into a future instance — "../templates/experiment.element.js" — is relative to wherever that instance ends up living, not to notebook.template.html's own location. Both fall back to the corpus root, checked by basename alone, which is where every file either shape has ever needed to reach has sat so far. A reference this fallback still cannot resolve is dropped rather than guessed at.
