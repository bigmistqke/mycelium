Command dispatch as nested exported objects, replacing byVerb implemented 2026-08-19

Today the engine resolves exactly one level of a command line. run.ts's main() splits argv into [id, namedCommand, ...rest], finds the family's <script type="mycelium/command"> block, loads it as a module, and picks the export named after namedCommand with a plain property lookup — const run = mod[command] — then calls it with every remaining token packed into args._, unexamined. For mycelium notebook generate graph --watch, the engine never looks at "graph" at all; it hands the whole thing to generate and trusts generate's own body to make sense of it.

That body makes sense of it by calling byVerb(ctx, "type", verbs), a helper that reads ctx.args._[0], looks it up in a verbs object built fresh inside the function on every call, and recurses for a second level of nesting (experiment case add is two byVerb calls deep). byVerb is not shared machinery — it is defined separately, near-identically, in both notebook.template.html and canon.template.html, and the duplication has already produced a real inconsistency: notebook's copy slices _ by one before recursing so a nested call sees its own verb at the front again, canon's copy does not, because canon never needed a second level. Nothing outside the function that calls byVerb — not the engine, not --help, not the corpus-index page — has ever been able to see the verbs table, because it exists only as a local variable built at call time.

Two standing gaps come directly from this. byverb-has-no-help-of-its-own.followup.html notes that --help for a byVerb-dispatched command has nothing to print but the outer function's entire doc comment, because the sub-verb names exist only as prose a person typed into that comment by hand — notebook experiment case add, case del, case conclude are usage lines in a comment, not anything parsed. And generate-commands-are-undeclared.direction.html names the broader shape of the same problem: a document in this corpus declares what it is, in a way validate can check, and a command declares nothing — what a command actually does is a fact only readable by opening its source.

Commands export nested objects, not calls to byVerb

A family's command script exports a plain object wherever it previously called byVerb, with one method per verb and one nested object per level of sub-verbs: 

export const experiment = {
  add(ctx) { ... },
  run(ctx) { ... },
  conclude(ctx) { ... },
  case: {
    add(ctx) { ... },
    del(ctx) { ... },
    conclude(ctx) { ... },
  },
}

The object's own shape is now the dispatch table. Nothing needs to stay in sync between what verbs a command has and what a reader can discover about it — they are the same property names, and whatever asks reads them directly.

The engine resolves every level, not just the first

run.ts's command resolution changes from a single lookup-and-call into a loop: resolve mod[command] as today, then repeatedly examine the result. A function call consumes whatever of rest remains, parsed into args as it is now. A plain object consumes the next token off the front of rest, looks it up as a property, and the loop continues one level deeper. Running out of tokens while holding an object, or finding no matching property, produces the same "takes a verb: X, Y, Z" error byVerb raises today, listing that level's own keys.

This is the one place the token-slicing rule belongs, decided once rather than copied twice with a drift already in it. byVerb and its canon duplicate disappear once no family still calls them.

--help walks the same structure

printHelp currently lists a family's roster with Object.keys(mod).filter(k => typeof mod[k] === "function") and prints each one's entire leading doc comment verbatim. It needs to walk into an object export the same way the engine now does, printing one line per full verb path (generate graph, experiment case add) — and each leaf can carry its own doc comment, read off its own method node with the same ts.getLeadingCommentRanges call this file already has, rather than every sub-verb sharing one comment written for the whole family of them.

readCommands gains the same walk

shared.ts's readCommands — which the corpus-index page's "Commands" badges already depend on — recognizes exactly three export shapes today: a function declaration, an arrow or function-expression const, and an aliased re-export. An object-literal export matches none of them, so readCommands silently drops it. This has to change in the same commit that lands the first object-literal command, or that command disappears from the index the moment it ships, not later. readCommands needs the identical recursive walk printHelp gets, so a nested verb shows up as its own badge under the family's card.

Migration is per-family, not a flag day

The engine supports both shapes at once: a resolved export that is a function still calls immediately, exactly as today; a resolved export that is a plain object, the resolver now walks. A family moves to the nested shape on its own schedule by rewriting its own byVerb calls into object literals — this spec does not require every family using byVerb-shaped dispatch today to move in one change.

  • Rewriting every family's existing dispatch in this change. This spec establishes the mechanism; which family migrates first, and in what order, is a separate decision.
  • Any schema check confirming every leaf of an exported command object is actually a function (as opposed to, say, a stray non-function property). A future audit could add this; nothing here specifies one.
  • Whether the corpus-index page's popover UI should show a nested verb differently from a flat one — a display decision for that page, not this dispatch mechanism.
  • The broader "document-of-documents" homepage question this idea came up alongside. Unrelated to how a command line resolves to a function.
  1. Once a verb is individually addressable, mycelium notebook generate --help could plausibly print just that one verb's own commands instead of the whole family's roster. Worth doing, not specified here.
  2. Should a leaf command's own doc comment become required rather than optional, now that --help can attribute one to each verb individually instead of one comment covering several? Unresolved.
  3. Whether byVerb and its canon duplicate get deleted as soon as notebook and canon both migrate, or stay until every family that uses the pattern has moved — depends on how many other families turn out to use it, which has not been surveyed beyond notebook and canon.
