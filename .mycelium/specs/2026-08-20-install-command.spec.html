An install command re-runs dependency-installing after seeding finishes implemented 2026-08-20

Seeding installs a rule's declared packages, but only once: seedCorpus returns immediately when .mycelium/ already exists, and that gate covers the dependency-install step along with the file-writing it guards. A rule added by hand after that first run, or one an updated mycelium version ships with a dependency the installed version never had, gets copied in — updating the package itself already carries new template files — but its packages never get installed, because nothing ever asks again.

The detect-a-package-manager-and-run-its-add-command step moves out of src/run.js and into src/utils.js as installPackages(dependencies, repoRoot, out), exported through the existing mycelium/utils specifier every corpus command already reaches other engine helpers through. Its own behavior does not change; only where a caller can reach it does.

A new singleton .mycelium/commands/install.command.html gives mycelium install to whoever needs to ask again. It walks language/ for every .rule.html file through fs.list, the same way the prose-follows-the-language audit already finds every rule, reads each one's mycelium/importmap script the same way seedCorpus does, and calls the same installPackages. seedCorpus keeps gathering its own dependencies from the files it is about to write, unchanged, and calls the same function once seeding finishes — one primitive, two places that need it for different reasons.

No automatic re-run on every command invocation — installing is a real write to the consumer's project, so it stays something somebody asks for, the same way seeding itself is. No diff against what is already installed: the package manager's own add command is idempotent, so asking again when nothing changed costs a no-op rather than a wrong state.
