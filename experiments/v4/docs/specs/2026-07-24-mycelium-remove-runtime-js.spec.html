remove runtime.js, move loadModule/loadCheck into utils.ts, inline the browser copy approved 2026-07-24

src/runtime.js exists for exactly one reason: loadModule/loadCheck (a five-line wrapper around a data: URL dynamic import()) is used both under Node (run.ts, validate.ts, fs-helpers.ts) and in exactly one browser-facing live demo (knowledge.template.html's graph-wide-audits section). To share one function across those two contexts without a real ES import (CORS-checked, and file:// has no stable origin to satisfy that check), it's written with no export and attached to globalThis.mycelium, loaded as a classic <script src> in the browser and a side-effect import "./runtime.js" under Node. A sibling runtime.d.ts exists purely to give the Node side real types for that global.

That's a real file, a side-effect import in three Node modules, a <script src> tag, and a .d.ts file — all in service of sharing a five-line function between exactly two call sites, one of which (the browser one) only exists in one place in the whole project. The machinery is bigger than what it's carrying.

Don't share it — write it twice

loadModule/loadCheck move into src/utils.ts (renamed from fs-helpers.ts — see below) as real, typed exports, keeping the exact signatures runtime.d.ts already declared: 

export async function loadModule(scriptSource: string): Promise<Record<string, unknown>> {
  return await import(`data:text/javascript,${encodeURIComponent(scriptSource)}`)
}

export async function loadCheck(scriptSource: string): Promise<(...args: unknown[]) => unknown> {
  const mod = await loadModule(scriptSource)
  return mod.check as (...args: unknown[]) => unknown
}

run.ts and validate.ts pick up loadModule/loadCheck through their existing import { ... } from "./utils.ts" line, same as parseHTML/walkHtmlFiles/validateInstance/readStdin already are. utils.ts's own validateInstance calls the now-local loadCheck directly instead of globalThis.mycelium.loadCheck.

The one browser call site — knowledge.template.html's audits live-demo — gets its own copy, written directly inside the <script type="module"> block that's already there: 

async function loadCheck(scriptSource) {
  const mod = await import(`data:text/javascript,${encodeURIComponent(scriptSource)}`)
  return mod.check
}

Duplicated on purpose, not shared: this is the same trick both sides already independently rely on (import() a data: URL, no real cross-file import, works over file:// with no server) — there's no cross-file loading left to coordinate, so there's nothing left for a shared file to actually do.

runtime.js and runtime.d.ts are deleted, not deprecated

Both files are removed outright. run.ts/validate.ts/utils.ts lose their import "./runtime.js" side-effect imports; knowledge.template.html loses its <script src="../../src/runtime.js"></script> tag. No global type declaration is needed once the Node side is a real, typed import — runtime.d.ts's whole purpose disappears with the global it was describing.

fs-helpers.ts renamed to utils.ts

Follows from the move above, not a separate motivation: once the file holds loadModule/loadCheck alongside parseHTML/walkHtmlFiles/ resolveTemplateRef/validateInstance/readStdin, "filesystem helpers" undersells what's actually in there — none of the newly-added functions touch the filesystem at all. git mv, then update the two import sites (run.ts, validate.ts).

Documentation: keep the still-true part, drop the shared-file framing

knowledge.template.html's live-demo prose and README.md's "Opening the documents directly" section both currently explain the CORS/file:///no-export reasoning in terms of one shared runtime.js file. That reasoning is still entirely true — the data: URL trick is exactly why neither side needs a server — it just needs reframing from "one file, loaded two ways" to "the same trick, written independently on each side." Every frozen spec and knowledge/*.html node that mentions runtime.js stays exactly as written — historical record of what was true when written, same convention this project has followed for every prior rename (see the validate-rename spec, which drew the identical living-vs-historical line).

Knowledge graph: a new decision, not an edit to the old one

reverse-runtime-to-globalthis.decision.html recorded choosing globalThis-sharing over real ES imports, specifically to avoid file:// CORS. This work doesn't reopen that question or reverse that decision — it answers a narrower one that decision never asked: given something needs sharing across Node/browser without real imports, is a whole shared file with its own loading mechanism warranted for a five-line function with exactly two call sites? Per this project's own convention, this work leaves the old node untouched (it's still correct about the question it actually answered) and adds a new knowledge-decision that records this one, linked back with elaborates rather than contradicts.

  • Not revisiting the file:// CORS constraint itself. Raised during brainstorming as a real, separate possibility (reconsidering real ES imports project-wide) but explicitly out of scope here — a bigger question about a constraint that still holds for anything actually needing cross-file sharing, not resolved by this change since nothing here needs that anymore.
  • Not building spec.template.html's authoring commands. Named as the very next piece of work, but sequenced after this one, not part of it.
