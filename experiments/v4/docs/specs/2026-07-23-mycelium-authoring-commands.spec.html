mycelium run: template-declared authoring commands approved 2026-07-23

Every node and edge in knowledge/ tonight was hand-authored: Write a new file with its full boilerplate by hand, or Read an existing node (its entire content, into context) then Edit in one new <a data-rel> line. With deciduous, the same operations were deciduous add goal "…" -c 90 and deciduous link 383 395 -r "…" — one cheap command each, no file content ever passing through the model doing the authoring. The gap is real and measurable: linking two existing nodes now costs a full file read plus an edit, where it used to cost nothing beyond the two IDs.

DESIGN.html's roadmap named this "mycelium run" and deferred it until a real template series existed. The crawler is that series' read side; this is the write side.

No built-in ontology, still

The first draft of this design put edge-insertion logic — find the root element, insert before its closing tag — directly in the engine. That's the same mistake the crawler's first draft made with nodes/edges, just recurring one layer up: "where a valid edge goes" is exactly as template-specific as "what a valid knowledge-goal looks like." Fixed the same way: the engine only ever knows the templating protocol, every authoring operation is declared by the template it belongs to.

Declaration: one script per template file

Not one script per command, and not one per type — knowledge.template.html already holds all six types together because they're one family, and the same reasoning argues for one commands script, not six near-identical fragments of one. A single <script type="mycelium/command">, exporting one named function per command: 

<script type="mycelium/command">
  export function add(fs, args) { … }
  export function link(fs, args) { … }
</script>

type="mycelium/command", not type="module": these scripts never run inside a browser — there's no "click a button on the page" equivalent to data-validates's and data-audits's live demos, they're only ever extracted and run by the CLI, under Node. An unrecognized type value gets a browser to treat the tag as inert data rather than auto-executing it on page load, while keeping <script>'s special raw-text parsing (content is never interpreted as markup, unlike a real custom element would be) — load-bearing here specifically because add's seed HTML, embedded as a template literal in its own source, is full of </> characters. The type value alone is also the discovery selector; no separate marker attribute earns its keep on top of it.

Because these scripts never run in a browser, they don't inherit the crawler spec's file:// constraint either — real import/export is fine here, no globalThis workaround needed. The crawler's own discovery (script[data-validates], script[data-audits]) is unaffected by type="mycelium/command" scripts sitting alongside them in the same file; different attributes, no overlap.

CLI shape

mycelium crawl [dir]                          # existing, unchanged: bulk validate + audit
mycelium run <id> <command> [args…]        # new: run one declared command

<id> always means the template file, uniformly, for every command — it resolves to <id>.template.html, the same way the file-naming convention already reads. Nothing about the shape of an individual command changes what <id> means; that would make the engine's own argument parsing depend on which command was invoked, which is exactly the kind of thing that isn't supposed to live in the engine. 

mycelium run knowledge add goal --title "Build v4" -c 85 -p "…" --file build-v4
mycelium run knowledge link build-v4.goal.html html-as-store.decision.html --rel leads_to "led to deciding …"

add needs an extra positional argument (goal) because a knowledge-* instance's shape genuinely differs per type; link doesn't, because splicing in an edge doesn't. Both commands still share the exact same function signature (below); the CLI just collects whatever arguments each named export happens to read off args, and the extra positional is add's own business, not something the engine's dispatch logic branches on. Engine-side dispatch is the same three steps regardless: resolve <id>.template.html, find its one script[type="mycelium/command"], extract and run it, call mod[command](fs, args).

A filesystem of mutable DOMs, not strings in and out

First draft had commands take a raw content string and return a new one — link would have had to find its insertion point with something like content.replace(/(<\/[a-z-]+>\s*)$/i, …). That's exactly the kind of fragile text-surgery the crawler already avoids by parsing with linkedom instead of pattern-matching HTML as text; writing deserves the same safety reading already has. It was also too narrow a second way: scoping a command to "the one file it was invoked on" rules out anything that reasonably needs to touch more than one, the same reason data-audits scripts get the whole documents array instead of one file at a time.

Revised: every command receives an fs context instead of a content string.

  • fs.get(path) — the existing file's parsed, mutable DOM (the same linkedom document the crawler already builds for reading).
  • fs.create(path, seedHtml) — a new file, parsed from a starting string so add isn't stuck building <!DOCTYPE html> one createElement call at a time for boilerplate that never varies, but still returns a real mutable DOM for the parts that do.
  • fs.delete(path) — marks a file for removal.

Commands mutate those DOM objects directly (root.appendChild(el), el.setAttribute(…)) and return nothing — the mutation happens by reference on objects the runtime already holds. After the command function finishes, the runtime's entire remaining job is genuinely just delete/add/update: serialize and write everything touched via get/create, delete everything marked via delete. Identical three operations no matter which command ran or what it did internally; the runtime never inspects what changed or why. 

export function add(fs, args) {
  const doc = fs.create(`${args.file}.${args.type}.html`, `<!DOCTYPE html>
<html lang="en">
<head>…</head>
<body>
<knowledge-${args.type} data-conforms-to="../templates/knowledge.template.html#knowledge-${args.type}">
</knowledge-${args.type}>
</body>
</html>`)

  const root = doc.querySelector(`knowledge-${args.type}`)
  const field = (tag, text) => {
    const el = doc.createElement(tag)
    el.textContent = text
    root.appendChild(el)
  }
  field('knowledge-title', args.title)
  field('knowledge-confidence', args.confidence ?? 70)
  if (['goal', 'decision', 'action'].includes(args.type)) field('knowledge-status', args.status ?? 'pending')
  if (args.type === 'goal' && args.prompt) field('knowledge-prompt', args.prompt)
}

export function link(fs, args) {
  const doc = fs.get(args.from)
  const root = doc.querySelector('[data-conforms-to]')
  const a = doc.createElement('a')
  a.setAttribute('data-rel', args.rel)
  a.setAttribute('href', args.href)
  a.textContent = args.label
  root.appendChild(a)
}

add's seed string carries the boilerplate that genuinely never varies by content (doctype, stylesheet links) parameterized only by args.type; everything conditional (which fields exist, whether status/prompt apply) happens through DOM calls instead of string concatenation, matching the per-type field table knowledge.template.html's own validators already encode. link never touches raw text at all — args.href is a relative path the runtime computed generically (no template-specific knowledge needed for path math), and the insertion point is "the element with data-conforms-to," found the same structural way the crawler already finds it, not a guess about where a closing tag happens to sit in the text.

No auto-slugging file names from the title — --file stays required, since deriving a good slug (dropping the type-redundant word, as every node written tonight already does by hand) is itself a judgment call worth making explicitly rather than guessing.

One addition worth including, not just an idea: after add writes a new file, immediately run that one file back through the crawler's own existing validator lookup and report PASS/FAIL, the same live-proof instinct every template in this project already leans on. Costs nothing new to build — crawl.ts already has the "resolve data-conforms-to, run the matching data-validates script" logic, this just calls it once instead of over a whole directory.

Where this lives

experiments/v4/src/
  crawl.ts    unchanged
  run.ts      new: `run <id> <command> [args]`, shares path/parse helpers with crawl.ts
  runtime.js  unchanged

No new dependency: argument parsing for a two-command surface this small doesn't earn a library like commander (which @mycelium/v0 uses for a much larger command set) — plain process.argv handling is enough and keeps @mycelium/v4's one-dependency footprint (linkedom) as it is.

  • No commands beyond add and link. A template could declare more later; nothing here enumerates what's possible, only what two things exist today.
  • No auto-slugging. --file is required; see above.
  • No interactive prompts. Every argument comes in on the command line, same as deciduous's own CLI worked.
  • No changes to the crawler itself. crawl.ts's discovery is unaffected by mycelium/command scripts existing alongside data-validates/ data-audits ones.
