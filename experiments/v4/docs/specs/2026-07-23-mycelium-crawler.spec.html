The mycelium crawler: a protocol-only engine for template-conforming HTML implemented 2026-07-23

DESIGN.html's roadmap deferred "build mycelium run" and "build the crawler/index" until a real template series existed to test them against. That's now true — knowledge.template.html and spec.template.html exist, with real instances in knowledge/. The freshly-rewritten CLAUDE.md already names the resulting gap directly: its Session Start Checklist admits ls/grep are "coarser than deciduous nodes/deciduous edges were," and knowledge.template.html's two audits are still only proven against their own sample markup, never the real files. This spec scopes the tool that closes both gaps.

Package

experiments/v4/
  package.json    name: "@mycelium/v4", joins the pnpm workspace, engines.node >=24
  src/
    crawl.ts      the crawler itself
    runtime.js    shared script-execution helper, imported by crawl.ts and one live demo
  docs/           everything that used to sit directly in experiments/v4/ —
                  DESIGN.html, theme.css, templates/, specs/, knowledge/

Run directly as pnpm crawl (node src/crawl.ts) — Node ≥24 strips TypeScript's type syntax natively, no tsx/ts-node, no build step, nothing to keep in sync between a source file and a compiled one. Same "no build step that could drift from the source" argument DESIGN.html already makes about the HTML documents themselves, just applied to the tool that reads them. The docs/ split moves every document out of the package root without changing any of their own relative links — nothing in the tree reached more than one level up, so the whole subtree moved as one unit.

One runtime dependency: linkedom, a lightweight HTML5 (not XML) DOM implementation for Node. An XML parser was ruled out earlier: these files rely on real HTML parsing behavior (unclosed void elements like <meta>, named entities like &mdash;), and a stricter parser would silently diverge from what a browser accepts — exactly the drift DESIGN.html argues the format should never allow.

No built-in ontology

DESIGN.html is explicit: "mycelium ships no notion of 'goal,' 'claim,' or 'test.' It discovers vocabulary by reading whatever template documents a project has actually authored." The first draft of this design violated that without noticing — it planned to have the crawler itself extract "nodes" as {id, type} and "edges" from <a data-rel>, baking in exactly the ontology that's supposed to stay template-owned. Corrected: the crawler only ever knows about the templating protocol, never a domain built on top of it.

Protocol-level (crawler knows this)Domain-level (crawler must not know this)
<template id> + its paired script"nodes" and "edges" as concepts
data-conforms-to="path#id"data-rel meaning "edge"
data-validates="#id", signature check(root)node types like knowledge-goal
data-audits="name", signature check(documents)what "orphans-except-goal" even means

What it does

  1. Walk a directory, parse every .html file with linkedom.
  2. Discover every <template id> across all files, paired with its sibling data-validates/data-audits script.
  3. Discover every instance: any element carrying data-conforms-to="path#id".
  4. For each instance, extract and execute its template's data-validates script (check(root) against the instance's own parsed subtree), report pass/fail.
  5. For each data-audits script found, extract and execute it, passed documents — every parsed file as {path, dom} — not a pre-built graph. The script decides how to read that itself.
  6. Print a summary: templates found, instances validated (pass/fail counts), audits run and their results.

Script execution

Extracted script text (an ES module's source, e.g. export function check(root) { … }) runs via a data:text/javascript dynamic import() — confirmed with a real spike before writing crawl.ts, no temp files needed. This part works identically in Node and in a browser, over file:// included: data: imports aren't subject to the CORS check real module fetches get.

Shared runtime: real modules, accept the server

crawl.ts and the browser-facing live demos both need the exact same loadCheck helper. Extracting it to one file and having both sides import it hit a real wall: browsers CORS-check ES module fetches even for local files, and file:// has no stable origin to satisfy that check — confirmed with a spike (a plain import of a sibling .mjs hangs silently over file://, works immediately once served over http://). A second spike confirmed a workaround: a globalThis-based file with no export statement at all works as both a classic <script src> in a browser and a side-effect import in Node, sidestepping the module-fetch restriction entirely.

Decided against the workaround anyway. It trades real import/export for global-namespace assignment, permanently, to preserve file:// compatibility for one shared file — a worse trade the more code ever ends up in it. src/runtime.js is a real ES module (export async function loadCheck(…)), imported normally by both crawl.ts and the "Graph-wide audits" live demo in knowledge.template.html. That one demo now needs a static server (pnpm serve) to actually run; every other live demo in this project, which never needed to share code across files, stays exactly as self-contained and file://-safe as it always was. Not a project-wide policy change, one documented exception where sharing real code won out.

Signature change this requires

knowledge.template.html's two audits changed from check(nodes, edges) to check(documents), an array of {path, dom}. Node/edge extraction (extractGraph()) moved into each audit script itself, duplicated between the two (matching how every other validator/audit script in this project stays self-contained), reading across every document handed to it instead of one local container. The live demo was updated to match, and separately to import the two audit scripts' real source text and the shared loadCheck, rather than hand-copying either.

Report contract, resolved not left open

The crawler needs some minimal way to know whether an audit passed, without interpreting what it checked. Resolution: reuse the shape data-validates scripts already return — { ok, … }. The crawler reads only ok for pass/fail coloring and exit code; everything else in the returned object is audit-specific and gets printed as-is, uninterpreted. Small, consistent, and not a new invention — both script kinds already agree on this shape.

  • No general query language. Pass/fail plus each audit's raw self-reported result is the whole report surface. Filtering by type/status/confidence, "find orphans" as a standalone command — not this pass.
  • No deciduous migration or bridge. Its ~400 frozen nodes stay exactly where they are, queryable only through the deciduous CLI.
  • No sharing with @mycelium/v0. Different domain (TypeScript code graphs vs. HTML documents), different parser, no code shared.
  • No GitHub Pages export, branch grouping, or multi-user sync. Same gaps CLAUDE.md already names; still waiting on this crawler to exist first, not solved by it.
Built and run for real: pnpm crawl against the actual docs/ corpus reports 24 real instances, all passing their validators, and both audits correctly flagging knowledge.template.html's own deliberately-broken sample markup as real violations — proof the crawler has no special-casing for what's "just a demo," exactly the no-built-in-ontology design this spec argued for.
