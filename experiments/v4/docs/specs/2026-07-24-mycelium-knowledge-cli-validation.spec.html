validate CLI input for add/link/update/list, reusing the existing validators approved 2026-07-24

knowledge list nodes can't filter by status or type — the question that started this ("any pending goals?") had to be answered with grep over the CLI's own output, because the CLI has no way to ask itself. Looking at why turned up the same gap repeated across every command in knowledge.template.html's type="mycelium/command" script: none of add, link, or update check their own required arguments before acting.

Confirmed against the real commands, in a scratch copy of docs/ except where noted:

  • add nonsense --file x --title y silently writes x.nonsense.html for a type that isn't one of the six real ones — no error, just a file pnpm validate will later choke on.
  • add with the <type> positional omitted crashes: a raw TypeError with the entire command script dumped inline as a data: URL in the stack trace.
  • link a b without --rel silently writes data-rel="undefined" to the <from> file — no crash, no warning, wrong data committed to disk. Hit for real against this project's own live graph while investigating this problem (build-v4.goal.html briefly gained a data-rel="undefined" edge before being reverted with git checkout).
  • add goal --commit abc1234 --title "…" --file x writes cleanly — <knowledge-commit> isn't in knowledge-goal's allowed-field list, but nothing in add knows that. Only a later pnpm validate catches it (unexpected <knowledge-commit> on knowledge-goal), by which point the bad file has already been sitting in the graph.

list is the one command that got its own input-checking right (a bad/missing <kind> gets a clean, specific error message) — but even it doesn't set a failing exit code, so the error is easy to miss in a script. The common thread: three of four commands trust their input completely and lean on pnpm validate, run afterward by a human, as the only safety net.

Reuse the six validators, don't invent a second schema

The obvious fix for "add/update don't know what fields a type allows" is to give them a copy of that knowledge. Rejected (see <spec-out-of-scope>): the six data-validates scripts in knowledge.template.html already are that knowledge, each with its own allowed = […] array. A second copy inside the command script would be a second place for the same fact to drift out of sync from the first.

Instead, add and update build or mutate the node exactly as they do today, then run the type's own real validator against the result before anything is written — the same code pnpm validate already runs, just moved earlier. validate.ts's main() already contains this exact operation (resolve data-conforms-to, find the matching data-validates script, load it, run check()), just inlined into its per-instance loop. Two small extractions into src/fs-helpers.ts (already the module shared between run.ts and validate.ts):

  • resolveTemplateRef(instanceFile, conformsTo) — moved verbatim out of validate.ts, pure path math, no behavior change. validate.ts imports it instead of defining its own copy.
  • validateInstance(docsDir, instancePath, element) — new. Given an element and the path of the file it lives in, resolves its data-conforms-to, reads that one template file fresh, finds the matching data-validates script, loads and runs it. Returns { ok, errors } uniformly and never throws — "no template found for this type" is a reported failure, not an exception, mirroring how validate.ts already treats that case.

validate.ts keeps its own batched, whole-corpus discovery machinery untouched: it reads every template file once up front, shared across 50+ instances, which is a genuinely different job from "check the one node a command just built." Forcing both call sites through one implementation would either cost validate.ts a real file read per instance (a perf regression for no reason) or force the new single-node helper to accept a pre-built templates map it doesn't need. Sharing only the pure path-math piece gets the duplication that actually matters without entangling two different jobs.

run.ts's main() builds a validate(root, instancePath) closure over docsDir, backed by the new helper, and passes it as a third argument to every command: 

const run = mod[command] as (fs: Filesystem, args: ParsedArgs, validate: Validate) => void | Promise<void>
await run(fs, args, validate)
fs.commit()

add and update call it after building/mutating their node; on !ok they throw an Error listing the validator's own messages. This also catches a bad <type> on add for free: constructing <knowledge-nonsense data-conforms-to="…#knowledge-nonsense"> and validating it hits the exact same "no template found" path a genuine broken reference would, with no special-case type-checking code needed anywhere.

Abort-on-invalid costs nothing extra

Filesystem.commit() (in run.ts) only ever runs after await run(fs, args, validate) returns successfully — that sequencing already exists today. A command that throws never reaches commit(), so nothing it touched gets written: no rollback logic, no partial-write cleanup, no new mechanism. This is also why the design in the previous section doesn't need to special-case "write nothing on failure" — the architecture already guarantees it as a side effect of a plain throw.

Required-argument checks, only where a validator can't cover it

A small local requireArgs(args, names) guard, defined once at the top of knowledge.template.html's mycelium/command script (not in the generic engine — each template family's command script owns its own argument conventions, the way this file already works), throws a plain, clean Error naming what's missing. Used only for what validateInstance genuinely can't catch, since anything a type's own validator already checks (a missing title, a missing confidence) doesn't need a second, duplicate check in requireArgs:

  • add: --file only — needed to know what filename to write before any validation is even possible.
  • link: <from>, <to>, and --rel. There's no validator for edges to lean on — the --rel vocabulary is deliberately open (per knowledge.template.html's own docs), so only presence can be checked, not the value. This directly fixes the data-rel="undefined" bug from <spec-problem>.
  • update: the target <file> positional only.
  • list: its existing <kind> check (must be nodes/edges) is kept as-is in shape, just switched from console.error(…); return to a thrown Error, so it fails the same way every other command now does.

link additionally calls fs.get(`knowledge/${to}`) (result discarded) before making any change, purely to confirm <to> exists — reusing the exact existence-check <from> already gets for free from its own fs.get() call, rather than adding a separate existsSync-style mechanism. fs is already the command's first argument, so this costs nothing beyond the one extra call.

list: filters and a failing exit code

list nodes/list edges accept two new optional flags, --status and --type, applied as a plain filter over the lines the command already builds — no new abstraction, no change to fs.list('knowledge') itself. 

mycelium run knowledge list nodes --status pending
mycelium run knowledge list nodes --type goal

One clean error path for every command

run.ts's main() wraps await run(fs, args, validate) in a single try/catch: on any thrown error — a requireArgs failure, a validateInstance rejection, or a plain filesystem error like "file not found" — it prints err.message alone (no stack, no data: URL dump) to stderr and exits 1. One change, and every command's failure mode becomes equally clean, including failure modes this spec doesn't add any new code for (e.g. update on a file that doesn't exist).

  • No new schema table. Considered and rejected in <spec-design>'s first section: it would be a second place "what fields does a goal allow" is defined, guaranteed to drift from the six validators that already define it.
  • Not fixing --help's positional-only quirk. mycelium run knowledge list nodes --help today silently runs list nodes instead of printing help, because --help is only special-cased when typed immediately after the family id, before any command name. Real, but a separate problem from commands trusting their own required input — not touched here.
