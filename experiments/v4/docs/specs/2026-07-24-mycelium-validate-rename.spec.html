rename crawl to validate, quiet colorized output, exclude template fixtures from audits approved 2026-07-24

Every pnpm crawl run this session has printed the same two audit failures (orphans-except-goal on sample-observation, dangling-outcome on sample-outcome), alongside a PASS line for every single instance checked (50+ and growing). Both are noise, for different reasons:

  • The per-instance PASS lines are never interesting once the mechanism is trusted — a routine sanity check only needs to know "did anything fail," not which 50 things didn't.
  • The two audit failures aren't real problems at all: they're knowledge.template.html's own live-demo self-test fixtures, deliberately wired to violate the two audits so the audit logic can be shown catching something real. But crawl.ts feeds every .html file under docs/ — including the template's own sample instances — into the same check(documents) call as the real graph, so the fixture's deliberate violation and a genuine graph problem would look identical in the output. Every run reads as "failing" even when the real graph is perfectly healthy.

Two designs for reconciling the fixture violations against reality were considered and rejected before landing on the fix below (see <spec-out-of-scope>): a data-audits-expect attribute carrying the expected violation IDs, and a per-audit data-expects="FAIL" declaration. Both add a way to tolerate the fixture's noise; neither addresses that the noise shouldn't be produced in the first place.

Separately, pnpm crawl is a memorable command for what the tool does internally (walk the tree) but not for what a user is actually asking when they type it (validate the graph).

Audits exclude docs/templates/, full stop

No new attribute, no per-violation reconciliation, no declared expectations. crawl.ts (renamed validate.ts, below) computes templatesDir = resolvePath(dir, "templates") once, and for every data-audits script, filters the documents array to exclude anything whose path falls under it before calling check(documents): 

const templatesDir = resolvePath(dir, "templates") + sep
const auditDocuments = documents.filter((d) => !d.path.startsWith(templatesDir))
// ...
const result = (await check(auditDocuments)) as CheckResult

Per-instance validation (data-validates) is untouched and keeps including everything, samples included — that's what proves each type's validator works for real, and it's harmless since it's isolated per-instance; nothing about "is this one sample-goal shaped correctly" depends on what else is in the graph. Audits are different in kind: they're inherently about the whole real corpus's connectivity, and a documentation fixture sitting in that same pool corrupts the answer to "is my real graph healthy" in a way a per-instance check can't be corrupted by its neighbors.

The browser-side live demo is untouched — it already scopes itself to just the six sample instances (documents = [{ path: 'sample', dom: sample-instances }]) to prove the audits are live, and stays the one and only place these fixtures get exercised. Net effect: a pnpm validate run against a healthy real graph now reports a genuine 0 fail, not two explained-away ones.

docs/templates/ is not new business knowledge for this engine to carry: run.ts's findTemplateFile already assumes exactly this directory convention to resolve <id>.template.html. This is the same convention, applied on the read side.

Quiet by default, one unified summary, colorized

Drop the per-instance PASS lines and the separate validators: N pass, M fail line entirely — no flag to bring them back; nobody has asked "which specific 50 things passed" all session, only "did anything fail." Replace both with one line combining validator and audit counts: 

50 checked, 0 fail

in green when fail === 0, red otherwise, via node:util's built-in styleText (stable on Node ≥24, no new dependency). Any real failure still prints in full below the summary, restructured — a label line, then indented violation text — instead of a raw JSON.stringify(result) dump: 

FAIL  knowledge/some-node.option.html
      unexpected <knowledge-status> on knowledge-option

Audit failures (now only ever real ones, per the fix above) print the same way, one indented line per violation instead of a JSON array literal.

Rename: crawl.ts → validate.ts, pnpm crawl → pnpm validate

Full rename, not an alias: git mv experiments/v4/src/crawl.ts experiments/v4/src/validate.ts, package.json's script becomes "validate": "node src/validate.ts". The tool's own self-description ("the mycelium v4 crawler," in its own header comment) is prose about what it conceptually does — walk the tree — and doesn't need to match the artifact name; it stays.

Blast radius, split the same way this project has split every rename/change so far this session — living documentation gets updated, historical record doesn't:

  • Update: README.md (layout diagram, usage section), CLAUDE.md (three pnpm crawl mentions), and the two other live source files that name crawl.ts in prose describing current behavior — run.ts's header comment ("same discipline as crawl.ts") and knowledge.template.html's live-demo section ("the same runtime.js the crawler uses under Node").
  • Leave alone: every crawl.ts/pnpm crawl reference inside the existing frozen spec docs (four of them), the two prior implementation plans, and every knowledge/*.html action/outcome/decision node. These describe what was literally true when they were written, the same convention CLAUDE.md's own "add only sets fields at creation time" gap-narrowing left every one of its own past specs unedited.
  • No data-audits-expect attribute. Considered: a JSON-array-valued attribute on the audit script declaring which violations are expected from self-test fixtures, diffed by validate.ts against actual violations. Rejected on two grounds: a serialized array in an attribute string doesn't match this project's own convention that real data lives as element content, not stringified into attributes; and more fundamentally, it treats a structural problem (mixing fixture and real data in one check) as a bookkeeping problem (reconciling two lists), which just adds a second place expectations could drift from what the browser demo already hardcodes.
  • No per-audit data-expects="FAIL" declaration. Considered as a coarser alternative: declare that a given audit's self-test run is expected to come back FAIL overall. Rejected: it can only compare the boolean ok result, not which specific violations occurred, so a real new orphan appearing alongside the already-known fixture violation would still read as "still just FAIL, as expected" — silently masking the exact class of problem pnpm validate exists to catch.
  • No type="mycelium/validate" script type. Considered as a way to unify data-validates/data-audits under the same declared-command pattern type="mycelium/command" already uses. Rejected immediately: an unrecognized type value is exactly what makes mycelium/command scripts inert in a browser (deliberately, since they must never run there) — the opposite of what audits and validators need, since running live in-browser as part of the demo is the entire point.
  • No --verbose flag or any other mode switch. Quiet-by-default is the only mode; nothing in this session has asked for the full per-instance listing back.
