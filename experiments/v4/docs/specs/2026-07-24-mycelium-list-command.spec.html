mycelium knowledge list, a shared fs-helpers module, and a Filesystem safety fix approved 2026-07-24

CLAUDE.md names a real capability gap versus deciduous: "pnpm crawl now answers most of what deciduous nodes/deciduous edges did — it validates every instance against its own template and runs both graph-wide audits against the real files … What it still doesn't do: print a clean list of nodes/edges the way deciduous nodes/ deciduous edges did (it reports pass/fail, not an enumeration)." There is no way today to ask "what's in the graph?" without reading crawl's PASS/FAIL output and mentally filtering it, or opening files by hand.

Two other real gaps surfaced while designing the fix, not from the graph itself but from the codebase backing it:

  • parseHTML and walkHtmlFiles are duplicated verbatim between src/crawl.ts and src/run.ts — each file independently defines its own copy. Any command that needs to read many files at once (which list does) would be a third copy if left as-is.
  • Filesystem.commit() unconditionally rewrites every file it touched, whether or not a command actually mutated it. get(path) exists to let a command read a file it's about to edit — nothing currently distinguishes "read and left alone" from "read and changed." A command that reads many files just to report on them (again, list) would, under the current implementation, cause every file it read to be reserialized and rewritten to disk on every invocation — a real risk of spurious whole-graph diffs from a command that's supposed to be read-only.

Where list doesn't live, and why

Two alternatives were considered and rejected before landing on the design below:

  • Generic in crawl.ts, deriving titles from the family-prefix convention (tagName.split('-')[0] + '-title', per spec.template.html's own naming rule that every root type is <family>-<type>). Rejected: this bakes a new piece of ontology knowledge into the engine that crawl.ts's own header comment says it deliberately avoids ("nothing about what any project builds on top of" the four protocol primitives). It would also require deciding whether to include the six sample instances live inside knowledge.template.html itself and any spec-doc instances — both of which are real [data-conforms-to] instances crawl.ts already discovers generically today, but neither of which is what "list the knowledge graph" means.
  • A data-lists script, audit-style, discovered by crawl.ts the same generic way it discovers data-audits, reusing the extractGraph() logic the two existing audits already duplicate. This was the initial recommendation and is architecturally the closest analog to the read side's existing pattern. Set aside in favor of the option below once it became clear the real blocker to putting list in run.ts's mycelium/command world (see next section) was fixable rather than fundamental.

A shared src/fs-helpers.ts module

parseHTML(html) and walkHtmlFiles(dir) move out of both crawl.ts and run.ts into a new src/fs-helpers.ts, imported by both. No behavior change — this only removes the existing duplication, and is what makes it reasonable for run.ts's Filesystem to grow a directory-walking method without copying crawl.ts's logic a third time.

Filesystem: mutation-aware commit(), plus list(dir)

get(path) and create(path, seedHtml) both snapshot doc.documentElement.outerHTML immediately after parsing, alongside the Document they already store. commit() re-serializes at write time and compares against that snapshot; if they're identical, it skips the write for that file entirely. Both snapshots go through the same happy-dom serialization path, so parse/reserialize normalization noise cancels out on both sides of the comparison — the only way the two can differ is a real mutation between get() and commit(). create() stores "" as its snapshot (a freshly created document's real content never serializes to the empty string), so a created file is always written, matching today's behavior.

list(dir) is new: it walks every .html file under dir (via the shared walkHtmlFiles) and calls this.get() on each, returning { path, doc }[]. It needs no new tracking of its own — every file it reads goes through the same get() path as any other read, and the commit() fix above is what makes calling it safe: reading dozens of files to report on them no longer risks rewriting all of them. 

class Filesystem {
  #touched = new Map() // path -> { doc, original } | { deleted: true }

  get(path) {
    ...
    if (!entry) {
      const { document } = parseHTML(html)
      entry = { doc: document, original: document.documentElement.outerHTML }
      this.#touched.set(full, entry)
    }
    return entry.doc
  }

  create(path, seedHtml) {
    const { document } = parseHTML(seedHtml)
    this.#touched.set(full, { doc: document, original: '' })
    return document
  }

  list(dir) {
    return walkHtmlFiles(resolvePath(this.#root, dir)).map(file => ({
      path: relativePath(this.#root, file),
      doc: this.get(relativePath(this.#root, file)),
    }))
  }

  commit() {
    for (const [full, entry] of this.#touched) {
      if ('deleted' in entry) { unlinkSync(full); continue }
      const html = entry.doc.documentElement.outerHTML
      if (html === entry.original) continue // unchanged — skip the write
      writeFileSync(full, ...)
    }
  }
}

list: a fourth mycelium/command, sibling to add/link/update

mycelium knowledge list nodes   # one line per node: file, type, status, title
mycelium knowledge list edges   # one line per edge: from --rel--> to

Scoped to knowledge/*.html only, via fs.list('knowledge') — not templates' sample instances, not spec-doc files. This is the one piece of knowledge-specific business logic in an otherwise-generic method: list (the command) knows the real graph lives under knowledge/; Filesystem.list(dir) (the primitive) doesn't know or care what's in the directory it's given.

For list nodes: for each document, find the root [data-conforms-to] element, read its type directly off its own tag name (el.tagName.toLowerCase(), e.g. knowledge-action) rather than checking against a hardcoded list of the six known types — a seventh type added to knowledge.template.html later would show up in list automatically, unlike the two audits' TYPES array. Status is read via the family prefix (knowledge-status) if present, blank for types that don't have one (option/outcome/observation).

For list edges: for each document, every a[data-rel] found anywhere inside the root element, printing the source file, the data-rel value, and the link's href (resolved relative to knowledge/, matching how the files themselves reference each other) and label text. This is deliberately simpler than the two audits' extractGraph(), which builds a combined node+edge graph for cross-checking orphans and dangling outcomes; list edges only ever needs edges, so it doesn't build node objects it won't use.
