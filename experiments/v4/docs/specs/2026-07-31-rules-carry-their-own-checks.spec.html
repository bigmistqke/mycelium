A rule carries its own check, and its examples are that check's tests draft 2026-07-31

The dictionary family holds fourteen rules. Eight of them declare dictionary-checkable as yes. No check exists for any of them. Nothing reads a rule, nothing enforces one, and a rule marked yes produces exactly the same result as a rule marked no.

That is not a gap waiting to be filled by the obvious next commit. It is the same shape as validate reported failures and exited zero: a mechanism that reads as enforcement while enforcing nothing. The field states an intention in the grammar of a capability.

The declared value was also wrong within two hours of being written. say-harness-when-you-mean-harness was marked no, when the truth is that a machine cannot decide it but can flag every candidate. The repair proposed at the time was a third value, gate|flag|none, which keeps the shape that failed: still written by hand, still a claim about a capability rather than the capability, still able to disagree with what exists.

What the ruleset should be

Limited, and ours. An external style guide has more rules than this project will ever write by hand, but importing three hundred of them produces a hand-maintained copy of somebody else's list, which is precisely the failure a hand-copied command list is read as the whole tool records. A small ruleset authored here has no upstream and therefore cannot drift from one.

That argument does not extend to implementations. If a published library already detects passive voice, writing a worse detector by hand is not ownership, it is duplication. So the design has to let a rule reach a library without making every rule depend on one.

Delete dictionary-checkable. A dictionary-rule may instead carry a <script data-audits="<rule-slug>"> that exports check(documents). A rule with a script is enforced. A rule without one is guidance. Enforceability stops being described and becomes observable, so it cannot be wrong.

The mechanism already exists, and was measured before this was designed

validate.ts collects script[data-audits] from every document under docs/, excludes only the templates/ directory, loads each through the virtual-module hook described in virtual module script imports, and calls check(documents) with the corpus. A falsy ok fails the run.

A probe document placed in dictionary/ confirmed all of it: the script was discovered, received 364 documents, and failed the run with exit code 1. A second probe imported acorn by bare specifier from inside that script and it resolved. So no new runner is needed, and reaching a library is a decision each rule makes for itself rather than one the project makes once.

This is the family's own primitive doing the work. A rule is a document, its enforcement is a script inside that document, and the thing that runs it is the same validator that already runs every other audit.

The two examples become the check's tests

dictionary-pass and dictionary-fail are already required on every rule, and they were required for a human reason: a rule stated abstractly is read differently by every reader. They are also exactly what a check should be tested against.

So one audit, written once and living beside the template, runs every rule's check against that rule's own two examples. A check that does not flag its own failing example is broken. A check that flags its own passing example is broken. Neither can reach the corpus without being caught, and no separate test fixtures have to be invented or kept in step with the prose.

This also gives the pass and fail fields a second job that makes them harder to write carelessly, which is worth having: an example that was decoration now has to be a case the check can actually decide.

Protected text is a shared concern, not each check's problem

No check may read a code block, the boilerplate quoting a plan's environment, a rule's own failing example, or a knowledge-prompt. That last is a record of what somebody typed, and editing one to satisfy a style rule would make the record false. Cleaning the corpus established this: of 59 occurrences found, 27 were in protected contexts and 2 of those were inside recorded user messages.

The selector for that is written and tested. It belongs in templates/shared.ts, imported by every check, rather than reimplemented per rule. A rule that gets it wrong would otherwise report a violation against text nobody may change.

Sentence length is the one number this spec does not fix. A cap of 25 words, which is what ASD-STE100 uses, flags 519 sentences, a quarter of the corpus. At 40 words it flags 168 and at 50 it flags 68. The standard's number was chosen for aircraft maintenance procedures read by non-native speakers, and this corpus is expository prose about software. The number is a judgment about how much rewriting is worth it, and it is left open below.

Porting all fourteen rules. This specifies the mechanism. Which rules get checks, and in what order, follows from the counts above.

The migration pass over the existing corpus. 464 em-dash asides will not be fixed by the commit that makes them detectable, and most of them were written today by the same author writing this.

Adopting an external style guide wholesale. Rejected in the problem section. A single rule importing a single library is not that.

Deriving term-use edges. Still open from the dictionary family spec and untouched here.

  1. Severity. The runner is binary: a check either fails the run or is silent. Flagging candidates for a person to look at, which is what say-harness-when-you-mean-harness needs, has no place to go. Either a check prints its own advisories and returns ok, which needs no change and hides advisories from any summary, or the runner grows a third outcome. The first is honest and cheap; the second is right if advisories turn out to be common.
  2. What a check receives. Raw documents, as the runner passes them today, means every check repeats the work of selecting prose. Pre-extracted prose means changing the runner for one family's benefit. A shared helper imported by each check is the middle option and costs an import line per rule.
  3. The sentence cap. 40 words flags 168 sentences, 50 flags 68. Not a technical question.
  4. Whether a rule without a check needs any marking at all. Absence is already the signal, and adding a field to say so would reintroduce what this spec deletes. But a reader scanning a list cannot see absence, so list may need to show it even though the document does not store it.
  5. Rules whose check needs configuration. A length cap has a number in it. If the number lives in the script, changing it is a code edit to a document; if it lives in a field, the field can disagree with the script. The same problem this spec solves for enforceability, one level down.
