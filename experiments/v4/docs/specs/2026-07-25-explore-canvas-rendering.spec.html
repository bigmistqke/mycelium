Panel and connector rendering for the docs/ explorer approved 2026-07-25

explore list (added to docs/commands/explore.command.html alongside the engine's new <id>.command.html lookup) proves the whole-tree, family-agnostic discovery this tool needs, but it only ever prints a flat text index. The actual goal recorded in the root goal and the transpointing-windows decision was a canvas of real document panels connected by visible lines, not a list and not a precomputed diagram (that's what knowledge generate graph already is, and deliberately isn't this). Nothing renders that yet.

A real constraint surfaced while starting this design: the shadow-DOM isolation decision assumed a panel loads its content by fetching the real document when it's opened, but every other generated page in this project (generate graph's output) is opened as a bare file:// page, and browsers generally block fetch() of local files from file:// with no server behind it. Resolved by having the command itself start a local HTTP server rooted at docs/, so every panel's fetch() is a same-origin request against a real server rather than a blocked local-file read.

Command and server

A new command, mycelium run explore serve [--port <n>], added to explore.command.html alongside list. It starts a plain node:http server (no framework — nothing else in this project pulls one in either) rooted at docs/: any request path maps directly to a file under docs/ and is served as static content, except GET /, which serves a generated shell page. The shell page comes from a renderExplorePage() template-string function, the same shape generate graph's own renderGraphPage() already uses. The command prints the server's URL and leaves opening a browser to the person running it, matching generate graph's existing behavior rather than adding OS-specific "open a browser" logic. It runs until interrupted; nothing it does needs cleanup on exit.

Sidebar

Computed server-side on each request to /: walk docs/ into a nested file/directory tree and inline it as JSON into the shell page, the same inlining pattern generate graph uses for its own graph payload. Rendered client-side as a collapsible tree in a fixed left-hand panel. Clicking a file entry opens it as a panel — the same function used when a link inside an already-open panel is clicked.

Panel lifecycle

Opening a path: if a panel for that path is already open, focus it instead of opening a duplicate — without this, two different documents linking to the same target would each spawn their own copy. Otherwise: fetch the path, parse the response with DOMParser, take .body.innerHTML and the resolved href of every <link rel=stylesheet> in its <head> (resolved against the fetch response's own URL, so ../theme.css-style relative paths still work no matter where the panel sits on the page). Build a panel: an absolutely-positioned <div> with a shadow root, a small header outside the shadow root (title from the fetched <title>, a close button) so panel chrome stays consistent regardless of what a document's own stylesheet does, and inject the resolved stylesheet <link> tags plus the body content inside the shadow root. New panels spawn with a simple fixed-offset cascade from whichever panel or sidebar entry opened them — no auto-layout algorithm, since dragging is always available to fix placement and this project already has an actual layout-solver precedent (cytoscape.js in generate graph) it's deliberately not reaching for here.

Link interception

Any <a href> click inside a panel's shadow root is caught by a listener on the shadow root — composed events still bubble out of shadow boundaries — and opens the target as a new panel with a connector instead of navigating the page. No special-casing data-rel versus a plain link: anything with an href behaves the same way, matching this tool's existing "no per-family, no per-attribute special knowledge" discipline from list.

Connector layer

One full-canvas <svg> sits under the panels, holding one <line> per connection. On open, a connector is drawn from the clicking anchor's position to the new panel. Endpoints are recomputed from getBoundingClientRect() on drag and on window resize, for every connector attached to the panel that moved.

Backlinks

Each panel's header shows a count of documents that link to it, computed from the same whole-tree [data-conforms-to]/[data-rel] walk list already does, with a toggle that opens every one of them at once, connectors included, using the exact same open-a-panel path as clicking a forward link. This is the part of the original discussion that made the project worth doing at all — the ordinary web only shows outbound links; this makes inbound ones just as visible — so it belongs in the first version, not a later one.

Error handling

A fetch that comes back 404 (a stale link, a deleted file) renders as a small inline error state in place of the panel's content rather than failing silently or breaking the rest of the canvas. A port already in use fails the command immediately, before any server state exists, with a message naming the port.

  • No transclusion. Quoting a passage from one document by reference inside another's panel was named early in the original discussion as a further Xanadu idea, but it's a distinct feature from making links visible and bidirectional — not needed for this version.
  • No persisted canvas layout. Reloading the page starts from an empty canvas plus the sidebar every time; nothing about which panels were open or where they were dragged is saved.
  • No zoom or minimap. At the scale this project's docs/ tree is actually at (roughly 130 instances), plain scrolling and dragging is enough; revisit if that stops being true.
  • No search. The sidebar tree plus backlinks are the two ways to find something; a dedicated search box is a reasonable later addition, not a blocker for a first version.
  • No auto-layout algorithm for panel placement. Considered and rejected in favor of simple cascade-from-parent placement plus manual dragging — see "Panel lifecycle" above.
