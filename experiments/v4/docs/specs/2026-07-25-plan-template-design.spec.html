plan.template.html: a runnable-step plan family for v4 draft 2026-07-25

knowledge.template.html and spec.template.html gave v4 a way to log decisions and design docs as hypermedia nodes instead of a SQLite table (deciduous) or Markdown (the superpowers:brainstorming skill's default). The third leg of that pipeline, superpowers:writing-plans, still only writes plain Markdown to docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md: a header (Goal/Architecture/Tech Stack/Global Constraints) followed by Task N blocks, each with a Files/Interfaces block and a numbered list of tiny Steps, each step a - [ ] checkbox, some of them literally "run this command, expect this result." None of that is queryable, linkable, or runnable the way a knowledge or spec node is — a step's own verification command is prose a human has to read and execute by hand, and progress tracking is whatever checkboxes happen to say in a file nobody else's tooling can see.

This spec designs plan.template.html: the same override spec.template.html already made for brainstorming's spec output, made for writing-plans' plan output instead, project-wide — not just for v4-internal work.

Tag family & file shape

New family plan-*, root type plan-doc, one file per plan at docs/plans/<date>-<topic>.plan.html — a new plans/ directory, sibling to knowledge/ and specs/. Four conforming types share this one file, nested three deep, each independently addressable via its own data-conforms-to — the same pattern spec.template.html's own "Conformance" section already documents ("a document can have exactly one typed root and any number of typed elements nested inside it, each independently addressable"). plan-doc contains plan-tasks, each conforming to #plan-task; plan-task contains plan-steps, each conforming to #plan-step; plan-step contains at most one plan-check, conforming to #plan-check. A parent's own <template> only ever declares a nested child tag as "may be present" — it can't and doesn't reach into that child's own internal shape; that's the independently-conforming child's own job, which is also why each of the three nested types needs its own data-conforms-to in the first place: the crawler behind pnpm validate finds every validatable instance purely by scanning for [data-conforms-to] anywhere in the tree, so without one, a plan-task's (or plan-step's, or plan-check's) own required-field rules would never be checked at all. 

<plan-doc>
  <plan-title>…</plan-title>
  <plan-status>pending | active | completed | rejected</plan-status>
  <plan-date>YYYY-MM-DD</plan-date>
  <plan-goal>… one sentence …</plan-goal>
  <plan-architecture>… 2-3 sentences …</plan-architecture>
  <plan-tech-stack>… optional …</plan-tech-stack>
  <plan-global-constraints>… optional …</plan-global-constraints>
  <plan-task id="task-1" data-conforms-to="../templates/plan.template.html#plan-task">
    <plan-title>…</plan-title>
    <plan-status>pending | active | completed | rejected</plan-status>
    <plan-files>… Create/Modify/Test …</plan-files>
    <plan-interfaces>… optional: Consumes/Produces …</plan-interfaces>
    <plan-step id="task-1-step-1" data-conforms-to="../templates/plan.template.html#plan-step">
      <plan-title>Write the failing test</plan-title>
      <plan-status>pending | completed</plan-status>
      <plan-detail>… optional: code, exact commands …</plan-detail>
      <plan-check data-conforms-to="../templates/plan.template.html#plan-check">
        <plan-check-command>pytest tests/foo.py::test_bar -v</plan-check-command>
        <plan-check-success>false</plan-check-success>
        <plan-check-output>function not defined</plan-check-output>
      </plan-check>
    </plan-step>
  </plan-task>
</plan-doc>

plan-title/plan-status exist at all three levels of the doc/task/step nesting, which is deliberate — fields belong to the family, not to one type within it, the same rule spec.template.html already documents for why spec-title isn't spec-doc-title. It does mean the shared generic validator (template.template.html's validateFromTemplate) must look up a field among only the element's own direct children, not anywhere in its subtree — otherwise checking, say, a plan-task's own plan-title could accidentally match a nested plan-step's title instead. This is a real, separate fix needed in shared infrastructure (also used by knowledge-*/spec-doc, though a no-op for both today, since neither has nested same-name fields) — see "Prerequisite fix" below.

plan-doc and plan-task both use the full four-value status enum (pending|active|completed|rejected) — reusing knowledge-status's exact vocabulary rather than inventing a new one, since a plan's and a task's lifecycle both genuinely span all four states. plan-step gets its own narrower two-value enum, pending|completed: a single step is only ever done or not — no "active" mid-step, no "rejected" for one isolated step — the same reasoning that already justifies knowledge-option/knowledge-outcome/knowledge-observation omitting status entirely rather than forcing an enum with values that never apply.

Required fields: plan-title/plan-status/plan-date/plan-goal/plan-architecture on plan-doc; plan-title/plan-status/plan-files on plan-task; plan-title/plan-status on plan-step; plan-check-command on plan-check. plan-tech-stack/plan-global-constraints (doc), plan-interfaces (task), plan-detail/plan-check (step), and plan-check-success/plan-check-output (check) are all optional.

Prerequisite fix: direct-child field scoping in the shared validator

template.template.html's validateFromTemplate currently locates a declared field's value with a deep el.querySelector(tag) — it searches the instance's entire subtree, not just its direct children. Its separate "unexpected field" check already does this correctly (Array.from(el.children), direct children only); only the required/pattern/enum lookup doesn't. This has never mattered before: no existing knowledge-* or spec-doc instance nests a same-named field inside itself.

plan-* is the first family where it does (plan-title/plan-status at three nesting levels), so the fix — scoping that lookup to direct children, matching the unexpected-field check's existing behavior — has to land before building plan.template.html can proceed correctly. Backward-compatible: identical behavior for every existing single-level instance, since a direct-children scan and a subtree scan return the same first match whenever there's no nested same-tag element in the first place. The same direct-children-only lookup discipline also applies to plan.template.html's own command code whenever it reads or upserts a field on a plan-task/plan-step (which may itself contain nested same-named fields) — not just to the shared validator.

plan-check: a fourth conforming type, not a field

A shell command a step can be verified against: 

<plan-check data-conforms-to="../templates/plan.template.html#plan-check">
  <plan-check-command>pytest tests/foo.py::test_bar -v</plan-check-command>
  <plan-check-success>true | false</plan-check-success>
  <plan-check-output>function not defined</plan-check-output>
</plan-check>
  • plan-check-command (required) — a shell command, run via a plain node:child_process call from the check command below. The runtime is confirmed unsandboxed real Node (command scripts load as genuine ES modules via a file: URL import(), no VM sandbox, no permission flag) with no existing cli.exec convenience — plan check is the first command in this project to shell out, and does so directly rather than waiting on a convenience that doesn't exist yet.
  • plan-check-success (optional, enum true|false, code default "true" when absent) — "true" requires exit code 0, "false" requires nonzero. Exists specifically for the TDD red/green cycle: writing-plans' own Step 2 ("run it, make sure it fails") is exactly plan-check-success = false.
  • plan-check-output (optional) — a plain substring match against combined stdout+stderr, not a full regex (YAGNI; extend later if real plans need more).

At most one plan-check per plan-step — plan-step's own <template> declares it as a single optional field (checked via one direct-child lookup, matching only the first), so a step wanting two independent checks would need splitting into two steps instead. Because plan-check is its own conforming type rather than a plain field, creating or editing one takes two cli.validate() calls in the owning command — one for the plan-step itself, one for the nested plan-check — not one.

mycelium run plan check <file> [<step-id>] runs the check(s) it finds (one named step, or every plan-step with a plan-check in the doc if the caller names no step), reports pass/fail per step, and only on pass flips that step's plan-status to completed. A failing check leaves status untouched rather than marking it rejected — a red step mid-TDD-cycle isn't abandoned, just not done yet. Steps with no plan-check are never touched by check; they can only be completed by hand, via update below.

Cross-linking

plan-doc links to the spec-doc it implements with a newly minted data-rel="implements" edge — the open vocabulary CLAUDE.md already invites minting into when a project genuinely needs a label neither of the original six nor specifies/elaborates already covers. Once a plan-step is actually executed, CLAUDE.md's existing knowledge-logging rules are unchanged: a step doesn't replace knowledge add action/outcome, it's linked to the resulting knowledge-action/knowledge-outcome node the same way any two nodes link today — a plain <a data-rel="leads_to" href="…#task-1-step-2"> in either direction, no new field required.

CLI commands

Four mycelium/command exports in plan.template.html: add, update, check, list. add and update each take a kind (doc|task|step) as their own first positional argument and dispatch internally — the exact convention knowledge add <type> already established in this project, reused here rather than inventing four separate hyphenated command names (add-task, add-step, …), which JavaScript can't export as plain identifiers and which this project's own --help doc-comment matcher (keyed off a plain export function/export const declaration) wouldn't recognize either.

  • add doc — mycelium run plan add doc --title "…" --file <topic> --goal "…" --architecture "…" [--status …] [--tech-stack "…"] [--global-constraints "…"]. Creates plans/<today>-<topic>.plan.html with header fields only, no tasks yet — the same way knowledge add goal creates a bare node.
  • add task — mycelium run plan add task <file> --title "…" --files "…" [--interfaces "…"] [--status …]. Appends one <plan-task id="task-N"> (N = current task count + 1) to the doc's plan-doc root, prints the new task id.
  • add step — mycelium run plan add step <file> <task-id> --title "…" [--detail "…" | --detail -] [--check-command "…" [--expected-success true|false] [--expected-output "…"]]. Appends one <plan-step id="<task-id>-step-M"> (status pending) inside the named task, with a nested plan-check when the caller supplies --check-command; prints the new step id.
  • update doc — mycelium run plan update doc <file> [--title] [--status] [--goal] [--architecture] [--tech-stack] [--global-constraints]. Scoped to the doc's own header fields.
  • update task — mycelium run plan update task <file> <task-id> [--title] [--status] [--files] [--interfaces]. Scoped to one existing task's own fields; omitted flags leave the field untouched, an explicit empty value clears an optional field, same convention as every other update.
  • update step — mycelium run plan update step <file> <step-id> [--title] [--status pending|completed] [--detail] [--check-command] [--expected-success] [--expected-output]. Scoped to one existing step; covers both the common case (flip --status after finishing a step by hand) and creating/editing/clearing its nested plan-check after the fact (e.g. fixing a flaky test command) — --check-command "" removes the whole plan-check, a non-empty value upserts plan-check-command (creating the plan-check wrapper first if none exists yet), and --expected-success/--expected-output upsert their own fields within it.
  • check — mycelium run plan check <file> [<step-id>]. The mechanics above.
  • list — mycelium run plan list <file>. One line per step: task title, step title, status, [has-check] marker — a flat progress view in the same spirit as knowledge list nodes. Doesn't re-run checks, just reports the current plan-status already on disk.

IDs are sequential and doc-scoped (task-1, task-1-step-1, task-2-step-3), generated at append time from the current sibling count — the same style already used for the sample-goal/sample-decision ids in knowledge.template.html's own live demo. A step/task is addressed for update/check purely by its id attribute via getElementById, not by tag name or position, so id collisions across a single plan file are the only thing that could misdirect a lookup — sequential per-parent generation already rules that out.

  • Wiring writing-plans/executing-plans/subagent-driven-development themselves to actually target this template instead of Markdown — this spec only designs the shape plan-doc takes and the commands that operate on it, the same way spec.template.html's own spec didn't rewrite brainstorming's skill file in the same pass.
  • Automatically generating a plan-doc's tasks/steps from a spec-doc's spec-design content (e.g. a plan add --from-spec) — parked as an open question below, not designed here.
  • A task-level status that's automatically derived by rolling up its children steps' statuses — plan-task's own status stays independently settable via plan update/hand-editing for now, same as knowledge-action never auto-derives from anything either.
  • Full regex or multi-assertion checks in plan-check — expected-output is a plain substring match only.
  • Should a follow-up spec design plan add --from-spec <spec-file>, scaffolding plan-task/plan-step skeletons out of a spec's own spec-design content? Flagged as a stretch goal during brainstorming, deliberately not committed to here.
  • Is a plan next <file> command (print the first plan-step with status="pending" in document order) worth adding alongside list, mirroring how executing-plans/subagent-driven-development already ask "what's the next task" during real execution? Deferred rather than designed, the same way spec.template.html deferred its own list command.
  • expected-output's substring match is case-sensitive and literal (no wildcard/regex) — revisit if a real plan's steps need more than that.
