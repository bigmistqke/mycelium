knowledge-detail: a free-form elaboration field for knowledge-* nodes, and the shared CLI-input helper it needs approved 2026-07-24

Every knowledge-* type has a title and nothing longer — no field for the reasoning, caveats, or supporting detail behind a claim. When that detail is genuinely worth keeping, it has nowhere to go except the title itself, which flattens it: a real example from this session's own graph is an observation node whose title grew into a multi-clause run-on sentence trying to carry an entire argument, useful for overview but lossy compared to what was actually said. spec-doc already solved this shape for design documents — spec-title stays short and scannable, spec-problem/spec-design hold as much real content as a design needs — but knowledge-* nodes never got the equivalent.

Adding the field alone doesn't fully solve it, though. add/update exist specifically so nodes get authored through the CLI instead of hand-edited (per CLAUDE.md's "use the CLI to log, don't hand-author" rule), and every existing field is a single-line value passed as --flag "value" — parsed by the shell before the command ever runs. That already causes friction for a short title with an apostrophe in it; a multi-paragraph value with embedded quotes, angle brackets, and markup would be substantially worse. A field that can only practically be filled in by hand-editing the file defeats the reason add/update were built.

The field: knowledge-detail, optional on all six types

knowledge-detail joins the existing field list, optional on every type — knowledge-goal through knowledge-observation — the same way title/confidence are universal but, unlike those two, never required. Field order in both the <template> entries and add's field-writing sequence places it after the short header-like fields (title, confidence, status, prompt) and before the trailing provenance fields (commit, files, branch) — header, then body, then metadata.

Content model: free-form, no tag or markup restriction, validated only for "present and non-empty if present" — identical to how spec-design/spec-problem are already validated today (spec.template.html's own check never inspects what's inside those sections, only that they're non-empty when the tag exists). This was a real design fork during brainstorming: an earlier draft proposed a validator-level allowlist of permitted tags, until checking revealed spec-design already has zero tag-level restriction and this project has never needed one — matching that existing precedent is more consistent than inventing a stricter rule for a sixth family that the fifth family never got. See <spec-out-of-scope> for what the allowlist draft would have looked like and why it was dropped.

Every one of the six data-validates scripts' closed-schema allowed arrays gains 'knowledge-detail' — six small, identical edits, not a new mechanism.

Insertion mechanism matters here and is easy to get wrong by default: every existing field's field() helper in add/update sets el.textContent = text, which is exactly right for a single-line value but would silently flatten real markup right back down to escaped text, defeating the whole point. knowledge-detail needs its own insertion path — parse the resolved string as an HTML fragment (reusing parseHTML, already in this project's toolchain via happy-dom) and move the resulting child nodes into the <knowledge-detail> element, the same shape spec-design's own content already takes. field() itself is untouched; this is a second, separate helper used only for this one field.

Script tags are a feature, not a hole to patch

knowledge-detail permits <script> content, deliberately. This isn't "no allowlist" applied carelessly — it's the same pattern this project already uses for its own validators and audits: every data-validates/data-audits script ships next to a live-demo section that runs the check against a sample instance, right there in the browser, so the claim "this validator catches X" is proven, not just asserted. A knowledge-observation making an empirical claim can now do the same thing for itself — embed a small script that reproduces the behavior it's describing and prints the result, instead of asking a reader to trust prose. This is a direct application of this session's own observation that this project's documents already fuse data and presentation into one file (xml-html-data-presentation-fusion.observation.html); letting an instance node carry a provable demo, not just a template, is that fusion reaching one level further down.

One constraint carries over unchanged from existing precedent, not newly invented here: a demo script that should work when the file is opened via plain double-click over file:// needs to follow the same rule runtime.js already follows — a classic <script> using globalThis, or type="module" via the data: URL import trick loadModule already uses, never a real cross-file ES import, which is CORS-blocked with no origin over file://. See the decision that established this for the full reasoning.

CLI: two flags, not one with a sentinel

add/update gain two new flags: 

--detail "short inline text"          # literal value, same as --title today
--detail-file <path>                  # read the value from a file
--detail-file -                        # read the value from stdin

Two flags rather than one flag with a value-prefix sentinel (the way curl -d @file uses @ to mean "read this from a file instead of treating it literally"). Every existing flag in this project's commands (--title, --commit, --files, --branch) is a plain, single-purpose name with no special value syntax; a sentinel would make --detail the one flag in the whole CLI whose behavior depends on the first character of its value, discoverable only by reading source, not from --help. -F taking a real filename or a literal - for stdin is a well-worn Unix convention (also tar, cp, plenty of others) — reused here for the value of --detail-file specifically, not as a reason to collapse it back into one flag with --detail.

This also gives every author a proportionate tool: a one-sentence clarification stays a plain --detail "…", no heredoc ceremony required; anything with real paragraphs, code blocks, or a demo script goes through --detail-file, where shell quoting never touches the content at all.

Both flags given at once is rejected with a clear error, not silently resolved by precedence — consistent with this project's existing preference (established in the previous plan) for a command that catches a contradiction in its own input rather than guessing which one the author meant.

Shared input-resolution helper, not knowledge-specific code

The logic that turns --detail/--detail-file into an actual markup string (read the literal value, or read a file, or read stdin when the value is -) is a new export in src/fs-helpers.ts, alongside resolveTemplateRef/validateInstance — not written inline inside knowledge.template.html's command script. This matters because spec.template.html doesn't have a type="mycelium/command" script yet (a known, already-tracked gap), but when it does, its own add/update will need the identical mechanism for spec-problem/spec-design. Building it as a shared, generic helper now — one real call site today, a known second call site coming — follows the same reasoning validateInstance was already extracted under during the previous plan: write the shared piece once, where both consumers can reach it, rather than duplicating it when the second consumer arrives.

list nodes gets a marker

list nodes' one-line-per-node output gains a fifth tab-separated column, always present (even when empty, so the output stays a fixed-width, awk-friendly shape): [+detail] when the node's knowledge-detail is present and non-empty, an empty field otherwise. 

knowledge/some-node.observation.html	knowledge-observation		A short title	[+detail]
knowledge/other-node.goal.html	knowledge-goal	completed	Another title
  • No validator-level tag allowlist. An earlier draft of this design proposed rejecting any tag inside knowledge-detail outside a fixed set (p, h2, pre, code, a, etc.), enforced via a shared check all six validators would call. Dropped once it became clear spec-design/spec-problem already accept arbitrary markup today with zero tag-level restriction — adding a stricter rule for a sixth family the fifth family never needed would be inconsistent, not safer in any way this project has actually needed.
  • No special guard against data-conforms-to/data-validates/data-audits/data-touches appearing inside knowledge-detail content. validate.ts's instance/audit discovery is unscoped (document.querySelectorAll('[data-conforms-to]') across the whole parsed document), so a stray one of these attributes buried in free-form content could in principle confuse it. This isn't a new risk knowledge-detail introduces — the identical risk already exists, unaddressed, for spec-design's content today. Documented here as an accepted, already-latent risk rather than engineered around.
  • No javascript:-URI rejection on <a href>. Considered as a narrow defense-in-depth check even under an otherwise unrestricted content model. Dropped: the decision to allow <script> content outright already accepts a much larger surface than one URI scheme on one attribute would meaningfully close off.
  • No change to runtime.js's avoidance of real ES imports. This design's demo-script guidance assumes that constraint as it exists today (reverse-runtime-to-globalthis.decision.html). Revisiting that decision was raised during brainstorming as a real possibility, but explicitly as a follow-up, not part of this scope — if it changes later, this spec's file://-safety guidance would need revisiting, not the field design itself.
  • No type="mycelium/command" script for spec.template.html. Referenced here as the reason the input-resolution helper is built shared rather than inline, but actually building spec's authoring commands is separate, already-tracked, unstarted work.
