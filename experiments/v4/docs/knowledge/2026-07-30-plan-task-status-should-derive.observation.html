plan-task status is declared, and went stale after one task 85

plan check flips a step to completed automatically when its check passes, and plan list renders the progress view. Neither derives the task or doc status. Those are declared fields that someone has to remember to update.

It went stale immediately. After task-1 ran, all three of its steps read completed while the task containing them still read pending. One task in, and the plan already misreported itself. It took a hand-run plan update task … --status completed to correct, which is the same "remember to X" the harness work has been removing everywhere else.

A task's status is fully determined by its steps. All steps completed means completed; some means active; none means pending. Storing it separately creates two sources of truth that can disagree, and one of them is maintained by memory. Same for a doc over its tasks.

This project already knows the answer. Deciduous #310/#311 reached it — status should be computed from the layer below, not stored. #364 generalized it: derive the graph, do not curate it, because every hand-maintained thing here has decayed. The evidence is on both sides of the comparison: 361 of deciduous's 400 nodes sit at pending because nobody went back, and this plan managed the same failure inside a single task.

Scope note. Fixing this means plan list and plan check computing task and doc status from steps rather than reading a stored field — plausibly with the stored field removed from the template entirely, since a derived value that is also writable is just a slower way to disagree with yourself. That is outside the current plan and should not be smuggled into it.
