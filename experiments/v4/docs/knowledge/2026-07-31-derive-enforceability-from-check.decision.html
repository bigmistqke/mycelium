Derive whether a rule is enforceable from the check it carries, rather than declaring it 90 completed

language-checkable is a declared field, and it claims something the corpus does not have. Fourteen rules exist.

Eight declare themselves machine-checkable. Zero checks exist. A rule marked yes and a rule marked no currently produce exactly the same result, which is nothing, so the field records an intention and reads as a capability.

It was also wrong within two hours of being written. say-harness-when-you-mean-harness was marked no, when the real answer was that it cannot be decided but can be flagged. A boolean has no room for that, and the fix proposed at the time was a third value, which would have been a second declared field with the same failure mode.

Derive it instead. A rule carries a <script data-audits> or it does not; a rule with one gates, a rule without one is guidance. Nothing to keep in step, and the answer cannot be wrong because it is the mechanism rather than a description of it. This is the argument derived status, not declared makes, and the one link, do not tag leans on: a derived value can be recomputed, so it cannot rot.

Verified before deciding, not after. A probe document placed in language/ with a data-audits script was discovered by the existing validator, received all 364 corpus documents, and failed the run with a non-zero exit. A second probe resolved a bare npm specifier from inside that script. So the mechanism needs no new runner, and reaching a library is a per-rule choice rather than a project-wide one.
