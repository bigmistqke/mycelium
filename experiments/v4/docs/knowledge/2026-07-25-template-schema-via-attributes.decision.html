Schema lives as attributes on existing template field placeholders, not new wrapper elements 70 completed

Schema lives as required/pattern/enum attributes directly on each type's existing <template id> field placeholders, not new <template-type>/<template-field> wrapper elements — e.g. <knowledge-title required>, <knowledge-confidence required pattern="^\d+$">, <knowledge-status required enum="pending active completed rejected">. No field name is written twice.

Verified against happy-dom (the DOM engine this project already runs on): a <template>'s children live in .content, a separate DocumentFragment, so the generic validator (hosted in template.template.html) must read via tpl.content.querySelector(...), and required is a boolean attribute so it needs hasAttribute, not a truthy getAttribute check.

No data-conforms-to is needed on the <template> definitions themselves — unlike the docs/knowledge/*.html instance corpus, there are only ever a handful of *.template.html files, so the filename convention alone is enough signal; nothing needs to be crawler-enforced there.

 the same required/pattern/enum attributes the generic validator reads can be surfaced in the overview command's field-level detail, not locked inside validator-function internals resolves full-replace-vs-fallback: all seven current validators turn out to be fully expressible in the schema, so they're deleted
