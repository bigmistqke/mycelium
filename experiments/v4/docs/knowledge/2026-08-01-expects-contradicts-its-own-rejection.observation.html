The expectations attribute built today was rejected by name a week ago, and one objection still stands 88

The validate rename spec puts No data-audits-expect attribute in its out-of-scope section and rejects it on two grounds. Today that attribute was built as data-expects, and neither the decision nor the commit knew the rejection existed.

The second objection is answered. It held that declaring expectations treats a structural problem (mixing fixture and real data in one check) as a bookkeeping problem (reconciling two lists). It does the opposite in practice: the declaration turned each fixture into an assertion, and the first thing it caught was a fixture that had stopped violating the audit it existed to demonstrate. A filter cannot catch that, because a filter looks away.

The first objection stands. It held that a serialized array in an attribute string doesn't match this project's own convention that real data lives as element content, not stringified into attributes. That is exactly what data-expects="sample-observation" is. The convention it names is real: fields are elements everywhere else here, and this is a whitespace-separated list in an attribute.

Two things follow. The convention has a real exception now, and it should be written down as one rather than left as an inconsistency nobody mentions. And the decision that rejected the filter should say so against the spec that rejected the attribute, because a graph where two documents disagree silently is worse than one where they contradict each other in the open.
