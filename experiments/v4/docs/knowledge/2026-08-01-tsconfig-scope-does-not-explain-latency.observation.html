Narrowing the TS project's root-file count did not speed up per-edit checks 80

Tested rather than assumed. tsconfig.json's include pulls in all 407 files under docs/, but 333 of them live under knowledge/, 19 under specs/, and 11 under plans/ — pure data instances that never carry a <script> tag, by the templates' own design. Only templates/, commands/, a few language/ rule files, and DESIGN.html do. That looked like a plausible lever: shrink the TypeScript project from 407 root files to about 44 and per-request work should drop.

Measured with @volar/kit's checker directly, timing checker construction, the first check (which builds the Program), and a check after a one-byte edit (standing in for a keystroke), once with the broad include and once with the narrow one. Checker construction was about 2.7 seconds in both — flat, not sensitive to root-file count — and post-edit checks landed at 13–25 ms in both, no meaningful gap. Narrowing include is not a lever here; whoever looks at this next should not re-try it expecting a win.

The real cost is that flat ~2.7 second construction, paid once per language server process, not per keystroke. It is closer to what "Volar things feel slow to warm up" usually means than to per-edit lag.
