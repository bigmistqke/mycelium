v4: A Knowledge Graph as Hypermedia

Status: design, self-hosted. This document is the first node.
Format: this package's specs, docs, and knowledge graph are HTML, not Markdown + deciduous
Supersedes: nothing directly; complements VISION.md and PRIOR_ART.md

The problem

Intent gets encoded into code once, and everyone downstream has to decode it back out by inference: code, then inferred design, then reconstructed intent. A teammate months later, the same person a year on, an LLM with no memory of the session that wrote the code: each of them repeats that decode from scratch, and each decode loses something. It's a xerox of a xerox. The reasoning behind a decision fades a little more every time it gets reconstructed instead of read.

The knowledge isn't missing, it's scattered. Commit messages, issues, design specs and ADRs, documentation, tests: each of these already exists to capture some piece of intent, and none of them stay connected to the code or to each other. A commit references an issue by number, in prose nothing resolves. An ADR sits in a folder nobody links back to the lines it constrains. A test has no structural tie to the claim it verifies, usually just a filename convention if you're lucky. The record exists, but it's spread across half a dozen silos and formats, held together only by whoever happens to remember writing all of them.

That loss compounds over a project's life. The same bug shows up again in a different shape, because the insight that would have prevented it got spent once on a fix instead of being kept somewhere the next pass could find and recognize as the same problem again. packages/v3/DESIGN.md measured a narrow instance of this: of five hand-written tests for a two-line max function, mutation testing showed two were load-bearing and three were noise. The tests that looked responsible weren't, and nothing queryable recorded which mutation each one actually guarded against.

A database on top (deciduous's SQLite store, mycelium's earlier graph-data.json exports) gives back some queryability, but becomes a sixth silo: one more thing that can drift from what it's supposed to describe. It fixes fragmentation by adding another fragment.

Core thesis

A single self-contained HTML document can hold a claim, its implementation, and the thing that verifies it, with boundaries between the three that blur however much a given piece of work needs them to. The document isn't a view onto some other canonical store, it is the canonical store. Any index, cache, or queryable graph built on top of a folder of these documents is a derived, rebuildable artifact, never the source of truth.

This package (packages/v4) tests that thesis by building this way instead of describing it: every spec, design note, and knowledge-graph node from here on is an HTML file, not a Markdown file plus a database row.

Substrate: one document, one node

A node is one .html file. Open it directly in a browser and the prose renders, the diagrams render, and any code inside a <script> tag runs, showing its own result inline. Hand the same file to a thin CLI (mycelium run node.html) and it extracts that same <script> content and runs it under Node. Nothing is transformed between the two, it's the same bytes read two different ways. There is no build step that could drift from the source, because there is no separate build output.

Document anatomy: no imposed shape

Nothing about the format requires a document to separate "spec," "test," and "implementation" into fixed slots. A node can be almost pure prose with one inline assertion, or almost pure code with a one-line comment above it, whatever that unit of thought actually needs. The only hard requirement is that it's valid HTML, and that runnable code lives inside a <script> tag so tooling can find it.

Structure without dogma: open-vocabulary links

Where a document does want to assert a relationship to another node, it does so with a plain link and an open-ended label, not one drawn from an enum the tool defines: 

<a data-rel="verifies" href="./claim-1.html">the test above verifies this claim</a>

verifies, supersedes, benchmarks, contradicts: the vocabulary gets minted by the project as it needs it, the same way HTML's own rel attribute, microformats, and schema.org all resolved this same tension for the web at large. A document that asserts nothing contributes nothing queryable, and that's the honest default rather than a degraded case. Most of the web has no schema.org markup either, and it's still hypertext.

Templates: structure, authored per-project

Structure that is checked, not just asserted, comes from templates. A template is a node like any other, not something the tool ships. It pairs a native, inert <template> element (a shape, never rendered or executed on its own) with a sibling <script> that validates instances against it: 

<template id="claim">
  <div data-claim></div>
</template>

<script type="module" data-validates="#claim">
  export function check(instance) {
    return !!instance.querySelector('[data-claim]')
  }
</script>

Because the validator is real code, not a declarative schema language, it isn't limited to checking one instance's local shape. It can receive the full set of nodes and edges the CLI has collected and assert something about the graph around an instance, not just the instance itself. That's also how a graph-wide audit ("every outcome links back to what caused it") gets expressed: as a script attached to a template, not as a separate constraint language.

Conformance is by reference, not by name

A document doesn't declare "I am a claim" as an abstract, global type. It links to one specific template, addressed the same way HTML has always addressed a piece of a document: a path and a fragment. 

<link rel="conforms-to" href="./templates/decision-nodes.html#outcome">

Two different documents can each declare a <template id="outcome"> with different shapes and never conflict, because nothing ties them together except a coincidental label, the same way two sites can both use schema.org/Person a little differently. There is no global type registry to keep consistent, because there was never a global namespace to begin with. A document is checked against the one template it specifically points at, nothing more.

This also answers how a single document can hold templates for several related types without duplicating anyone else's shape: a cross-template validator doesn't redeclare goal or outcome, it links to the existing template documents for both and runs a script that checks the relationship between them.

The CLI has no built-in ontology

mycelium ships no notion of "goal," "claim," or "test." It discovers vocabulary by reading whatever template documents a project has actually authored, then answers questions that only become askable once a template made them meaningful. "Which outcome instances have no incoming leads_to edge" only parses once some template declared that outcome and leads_to exist. Any index it builds to answer these questions fast (a cache of what templates exist, what conforms to what, what links to what) is exactly that: a cache, rebuildable by re-crawling the documents, never the record of truth.

Proof case: deciduous as a template series

deciduous already has a fully specified, battle-tested schema: six node types (goal, decision, option, action, outcome, observation) and six edge types (depends_on, blocks, supports, contradicts, alternative_to, leads_to). Reimplementing it as a template series is a sharper test than inventing a toy example, because the answer is already known.

It's also a schema that already exposed the exact problem templates solve. deciduous's git-native cousin, hive, discovered mid-build that status only makes sense for goal/decision/action, not for option/outcome/observation, and had to bolt on a nodeTypeSupportsStatus() helper to fake per-type shape onto one flat SQL table. With templates, heterogeneous shape per node type isn't a workaround: a goal template declares a status field, an observation template simply doesn't.

What this is not

  • Not live transclusion. Embedding another node's content by reference so edits propagate live is a real Xanadu idea and a real future direction, just not built here. Links point, they don't inline.
  • Not swappable implementations behind a shared interface. Conforming to the same template is what would make two documents interchangeable, but v4 doesn't build the swap mechanism, only the conformance it would rest on.
  • Not a global type system. There is no registry of node kinds, no schema the tool enforces, no naming authority. Conformance is always to one specific, linked template.
  • Not a replacement for git. Versioning, history, and diffing stay exactly what git already does well; this is about what a single snapshot of a node contains and how nodes relate, not how changes over time are stored.

What's next

  1. Write the deciduous template series (six type templates, six relationship labels, the orphan-goal and dangling-outcome audits as cross-template validator scripts).
  2. Build mycelium run: extract and execute a document's <script> content under Node.
  3. Build the crawler/index: walk a folder of documents, resolve conforms-to links, run validators, answer queries. This is the rebuildable cache described above.
  4. Only then: revisit transclusion and interface-swapping, once there's a real corpus to test them against.
