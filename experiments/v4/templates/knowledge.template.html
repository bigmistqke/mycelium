Templates: knowledge-*

Node types: knowledge-goal, knowledge-decision, knowledge-option, knowledge-action, knowledge-outcome, knowledge-observation — six templates, one file, per the family-file convention
File naming: this file is knowledge.template.html, named after the knowledge-* family it defines, the same way spec.template.html names the spec-* family
Purpose: deciduous's node schema, reimplemented as templates instead of one flat SQL table — the proof case DESIGN.html proposed
Sibling of: spec.template.html, the spec-* family
Styling: ./knowledge.template.css, this family's own rendering rules, plus the shared ../theme.css every document links

Why six templates, not one flat schema

deciduous's git-native cousin hive discovered mid-build that status only makes sense for goal/decision/action, not for option/outcome/observation, and had to bolt on a nodeTypeSupportsStatus() helper to fake per-type shape onto one flat SQL table. Here that isn't a workaround: knowledge-goal declares a knowledge-status field, knowledge-observation simply doesn't. Six separate <template> entries in one knowledge-*-named file, exactly as DESIGN.html's own worked example already showed for this same schema.

Shared field vocabulary

Every type shares only the family prefix on its fields, not its own type name (knowledge-title, not knowledge-goal-title) — see the design spec's naming section. Two fields need more than "present and non-empty":

  • knowledge-confidence — an integer 0–100, matching deciduous's own -c/--confidence flag.
  • knowledge-status — one of pending, active, completed, rejected. This resolves the open question the design spec left: deciduous's own CLI (deciduous status --help) defines exactly these four, not the draft/approved/implemented enum spec-doc uses for an unrelated reason (that one tracks the brainstorming skill's lifecycle, not deciduous's).

knowledge-prompt is optional even on knowledge-goal: CLAUDE.md's own rule is that a verbatim prompt belongs on root goals and major direction changes, not on every downstream node, so a knowledge-goal without one is valid, not incomplete.

The six types

knowledge-goal

What the user asked for. Fields: title, confidence, status, optional prompt (the verbatim request, for root goals and major direction changes).

<knowledge-goal data-conforms-to="./knowledge.template.html#knowledge-goal">
  <knowledge-title>Build v4: knowledge graph as hypermedia</knowledge-title>
  <knowledge-confidence>85</knowledge-confidence>
  <knowledge-status>active</knowledge-status>
  <knowledge-prompt>we are playing around with mycelium…</knowledge-prompt>
</knowledge-goal>

knowledge-decision

A choice made between approaches. Fields: title, confidence, status.

<knowledge-decision data-conforms-to="./knowledge.template.html#knowledge-decision">
  <knowledge-title>HTML documents as canonical store, not DB + Markdown</knowledge-title>
  <knowledge-confidence>80</knowledge-confidence>
  <knowledge-status>active</knowledge-status>
</knowledge-decision>

knowledge-option

One alternative considered within a decision. No status — the option was or wasn't chosen, that's what an edge to its parent decision says, not a lifecycle of its own. Linked to its parent with <a data-rel="depends_on">, the closest of the six edge labels. Fields: title, confidence.

<knowledge-option data-conforms-to="./knowledge.template.html#knowledge-option">
  <knowledge-title>Keep the six-file split (one template file per type)</knowledge-title>
  <knowledge-confidence>40</knowledge-confidence>
  <a data-rel="depends_on" href="./knowledge.template.html">considered for this file, rejected in favor of one bundled file</a>
</knowledge-option>

knowledge-action

About to write or edit code. Fields: title, confidence, status, optional commit/files/branch once it's tied to real work.

<knowledge-action data-conforms-to="./knowledge.template.html#knowledge-action">
  <knowledge-title>Write DESIGN.html</knowledge-title>
  <knowledge-confidence>90</knowledge-confidence>
  <knowledge-status>completed</knowledge-status>
  <knowledge-commit>9794442</knowledge-commit>
  <knowledge-branch>main</knowledge-branch>
</knowledge-action>

knowledge-outcome

Something worked or failed. No status — an outcome is the record of what happened, not a thing that has a lifecycle itself. Fields: title, confidence, optional commit/files/branch.

<knowledge-outcome data-conforms-to="./knowledge.template.html#knowledge-outcome">
  <knowledge-title>DESIGN.html written and committed</knowledge-title>
  <knowledge-confidence>92</knowledge-confidence>
  <knowledge-commit>9794442</knowledge-commit>
</knowledge-outcome>

knowledge-observation

Something noticed along the way, not yet a decision. Fields: title, confidence.

<knowledge-observation data-conforms-to="./knowledge.template.html#knowledge-observation">
  <knowledge-title>Removing the <style> block made every document read like structured data</knowledge-title>
  <knowledge-confidence>70</knowledge-confidence>
</knowledge-observation>

Edges

The six data-rel labels deciduous already uses: depends_on, blocks, supports, contradicts, alternative_to, leads_to, written the same way DESIGN.html's own example shows: <a data-rel="leads_to" href="./outcome-x.html">…</a>. This project's own chain tonight used leads_to for its forward narrative (goal → decision → action → outcome → action) and depends_on for knowledge-option → parent knowledge-decision, the closest existing label for that relationship.
