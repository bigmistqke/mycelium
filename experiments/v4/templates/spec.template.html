Template: spec-doc

Node type: spec-doc
File naming: this file is spec.template.html, named after the spec-* family it defines, not the single spec-doc type — the same file can hold more spec-* template entries later without being renamed. Documents that conform to spec-doc are named <date>-<topic>.spec.html
Purpose: the shape a design/brainstorming document takes when written as a v4 node instead of Markdown
Sibling of: graph.template.html, one file holding all six deciduous node-type templates (graph-goal through graph-observation)

Why this template exists

The superpowers:brainstorming skill's default is to write an approved design to docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md, with an explicit carve-out: "user preferences for spec location override this default." v4's preference is that a spec is a node like any other — HTML, not Markdown, and conforming to a template like any other instance in this graph. This template is that override, made concrete.

Naming: hyphenated, family-prefixed, and the file names the family

Every tag this project invents is hyphenated. Two reasons: the actual Custom Elements API (customElements.define(name, Class)) throws on an unhyphenated name, so a bare <spec> could never later be given real behavior without a breaking rename; and it's the same guarantee HTML itself relies on to add new elements safely — no future standard tag will ever contain a hyphen. This isn't hypothetical for this project specifically: an earlier, unhyphenated version of this very template used <title>, a real element with its own parsing rules, and the as-yet-unbuilt deciduous types include option, which collides even harder (real, heavily special-cased, expected inside <select>).

The prefix isn't a decorative brand mark (not v4-title), it names the family a tag belongs to: spec-* for design-document types, graph-* for the six deciduous node types that participate in the decision graph — mirroring the project's own existing graph/ directory. A root type is <family>-<type> (spec-doc); its fields share just the family prefix, not the full type name (spec-title, not spec-doc-title), because fields belong to the family, not to one specific type within it — every spec-* type would share spec-title, the same way every graph-* type will share graph-title.

The template file is named after the family, not the one type it happens to define today: spec.template.html, not spec-doc.template.html. That's what lets one file hold several related <template> entries under a shared prefix, addressed by fragment, the way DESIGN.html's own worked example already does for the six deciduous types in one file — the family prefix is what keeps that safe now, not physically splitting every type into its own file.

Shape

A first version of this template had a three-field header (title, status, date) and left everything else as untagged prose, on the theory that "no imposed shape" meant the body should stay free-form. That confused two different things: a template isn't a metadata header bolted onto a separate free-form document, it's a set of named containers, and a container can hold freeform content and still be queryable as a section, by tag name, even though what's inside it isn't atomized into fields. What actually determines whether something can be found later isn't "structured vs. prose," it's "inside a named tag vs. bare in the document." A three-field template left everything past its header outside any tag at all — invisible to any query, no matter how load-bearing the content was.

So the template grew section containers, each free to hold rich content (headings, tables, code, whatever a given design needs) while still being addressable by tag name across every spec in the corpus: 

<spec-doc>
  <spec-title>…</spec-title>
  <spec-status>draft | approved | implemented</spec-status>
  <spec-date>YYYY-MM-DD</spec-date>
  <spec-problem>… what motivates this design …</spec-problem>
  <spec-design>… the approved design itself, any content …</spec-design>
  <spec-out-of-scope>… optional …</spec-out-of-scope>
  <spec-open-questions>… optional …</spec-open-questions>
</spec-doc>

spec-title, spec-status, spec-date, spec-problem, and spec-design are required — every spec has an identity, a motivation, and a decided approach. spec-out-of-scope and spec-open-questions are optional: a spec that has nothing to exclude or nothing left open simply omits the tag, rather than including it empty. Related nodes, wherever they're mentioned inside any of these sections, are reached the usual way: <a data-rel="…">.

spec-status tracks the brainstorming skill's own lifecycle: draft while under discussion, approved once the user signs off on the design, implemented once the plan it led to has shipped.

Conformance

Conformance is declared as a data-conforms-to attribute on the element making the claim, not as a <link rel="conforms-to"> in <head>. A head link can only assert one thing about the document as a whole; it can't sit next to a <graph-decision> nested three levels into a <spec-design> section, declaring conformance for just that one element. An attribute on the element itself composes: a document can have exactly one typed root and any number of typed elements nested inside it, each independently addressable via document.querySelectorAll('[data-conforms-to]'), instead of only ever answering "what is this document" once from <head>. 

<spec-doc data-conforms-to="../templates/spec.template.html#spec-doc">

</spec-doc>
