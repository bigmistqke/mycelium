Deciduous as an HTML template series, plus v4's first dogfooded graph nodes approved 2026-07-23

DESIGN.html proposed reimplementing deciduous's six node types and six edge labels as a template series, then building real graph nodes from v4's own history on top of it, as the proof case for the whole document-as-canonical-store thesis (see DESIGN.html's "What's next" item 1). This spec fixes the shape of that template series and scopes the first real instances. The crawler, mycelium run, and any cross-file validation stay explicitly out of scope, per DESIGN.html's own roadmap ordering — everything here is provable by opening a single document in a browser, nothing requires fetching across files.

File naming convention going forward: template documents end in .template.html, spec documents end in .spec.html. Graph instance nodes (graph/*.html) and audit documents (audits/*.html) aren't covered by a suffix convention yet — introduce one if and when it earns its keep, not speculatively.

Template shape: real tags, not data-* soup

Each node type is a real element, not a <div data-node="goal">. Fields are child elements, not data-field attributes. Templates are exactly where this project's vocabulary gets invented, so the vocabulary should read as itself: 

<template id="goal">
  <goal>
    <title></title>
    <confidence></confidence>
    <status></status>
    <prompt></prompt>
  </goal>
</template>

Instance:

<goal>
  <title>Build v4: knowledge graph as hypermedia</title>
  <confidence>85</confidence>
  <status>pending</status>
  <prompt>we are playing around with mycelium…</prompt>
</goal>

Known wrinkle, accepted: <title> is a real HTML element with its own parsing rules (only unambiguously valid in <head>, or in <body> with scripting disabled). Kept anyway, because it's the right word and a CSS reset (spec > title { display: block; … }, applied to this very document's own header above) handles the presentational side. If it ever causes real parser trouble in a target browser, that's a fix to the reset or the tag choice, not a reason to fall back to data-field.

Validators query by tag instead of attribute: root.querySelector('title'), root.querySelector('confidence'), and so on, the same pure-check(root) shape DESIGN.html's live demo already established.

Per-type fields

Deciduous's flat schema bolted status onto every node type and then had to fake its absence for option/outcome/observation with a nodeTypeSupportsStatus() helper — the exact problem DESIGN.html names as the reason templates exist. Here, a type simply doesn't declare a field it doesn't need.

typefields
goaltitle, confidence, status, prompt
decisiontitle, confidence, status
optiontitle, confidence
actiontitle, confidence, status, commit, files, branch
outcometitle, confidence, commit, files, branch
observationtitle, confidence

Edges

The six data-rel labels carry over unchanged: depends_on, blocks, supports, contradicts, alternative_to, leads_to, used exactly as DESIGN.html's <a data-rel="verifies" href="…"> example already shows. option → parent decision uses depends_on, the closest existing label; the dogfood chain below uses leads_to for its forward narrative. New labels get minted the same way DESIGN.html describes: as a project needs them, not from a fixed enum — this document mints specifies for the spec → action link below, and elaborates for the link to DESIGN.html above.

Audits: proven against a fixture, not the real files

audits/graph-integrity.html implements the two audits DESIGN.html names:

  • orphans-except-goal — every non-goal node must have at least one edge (CLAUDE.md: "Root goal nodes are the ONLY valid orphans").
  • dangling-outcome — every outcome must have an edge back to what it resolves (CLAUDE.md: "does every outcome link back to what caused it?").

Both are pure functions over {nodes: [{id, type, status}], edges: [{from, to, rel}]} — deliberately the shape a future crawler would emit by parsing graph/*.html. This round proves them the way DESIGN.html's own live demo proves the claim template: against a literal embedded sample array, PASS/FAIL rendered inline in the browser. They are not run against the real graph/ files — that needs fetching across documents, which is the crawler/mycelium run work this spec explicitly defers. The five real instance docs get conforms-to links and hand-verified-correct structure, not yet mechanically checked.

Spec docs are graph nodes too

This document is the concrete answer to a meta-question the brainstorming skill leaves open for every project: where does an approved design go? v4's answer is templates/spec.template.html, a template with a required identity (title, status, date) plus required problem and design sections, and optional out-of-scope / open-questions sections — each free to hold whatever content the design needs, but addressable by tag name across every spec in the corpus. status tracks the skill's own lifecycle: draft while under discussion, approved at the point this document reached (sign-off, before writing code), implemented once this design has shipped.

  • No mycelium run. Deferred by DESIGN.html's own roadmap.
  • No crawler/index. Same deferral; nothing here fetches across documents.
  • No live validation of the real instance docs. The five dogfood nodes and the audits are correct by hand-inspection and by the embedded-fixture proof respectively, not mechanically checked against each other. That mechanical check is exactly what the crawler gives later.
  • What are the actual valid status values for goal/decision/ action instances? Every node inspected in the existing deciduous graph so far shows pending; resolve by checking deciduous's own source before writing decision-nodes.template.html's validators, rather than guessing an enum.
  • Once decision-nodes.template.html exists, should specific claims inside a spec's <design> (like the two callouts above) be marked up as inline <decision>/<observation> instances, rather than plain paragraphs? Left open rather than done here, since it can't properly conform to a template that doesn't exist yet.
