Deciduous as an HTML template series, plus v4's first dogfooded graph nodes approved 2026-07-23

DESIGN.html proposed reimplementing deciduous's six node types and six edge labels as a template series, then building real graph nodes from v4's own history on top of it, as the proof case for the whole document-as-canonical-store thesis (see DESIGN.html's "What's next" item 1). This spec fixes the shape of that template series and scopes the first real instances. The crawler, mycelium run, and any cross-file validation stay explicitly out of scope, per DESIGN.html's own roadmap ordering — everything here is provable by opening a single document in a browser, nothing requires fetching across files.

File naming convention: a template file is named after the tag family it defines (spec.template.html for the spec-* family, graph.template.html for the graph-* family), not after any single type within it — the same file can hold several related <template> entries, addressed by fragment, the way DESIGN.html's own worked example already does. Documents that conform to spec-doc end in .spec.html. Graph instance nodes (graph/*.html) and audit documents (audits/*.html) aren't covered by a suffix convention yet — introduce one if and when it earns its keep, not speculatively.

Tag vocabulary: hyphenated, family-prefixed

Each node type is a real element, not a <div data-node="goal">, and fields are child elements, not data-field attributes — templates are exactly where this project's vocabulary gets invented, so it should read as itself. Every invented tag is hyphenated, though: the Custom Elements API rejects unhyphenated names outright, and an earlier, unhyphenated version of this vocabulary already collided twice — once for real (<title>, a real element with its own parsing rules, worked around with a CSS reset before this fix) and once waiting to happen (option, one of the six deciduous types, is a real, heavily special-cased HTML element).

The hyphen prefix names a family, not a brand (not v4-title): spec-* for design-document types, graph-* for the six deciduous node types, mirroring the project's own graph/ directory. A root type is <family>-<type>; its fields share only the family prefix, since fields belong to the family, not to one type within it — every graph-* type shares graph-title, the same way every spec-* type shares spec-title: 

<template id="graph-goal">
  <graph-goal>
    <graph-title></graph-title>
    <graph-confidence></graph-confidence>
    <graph-status></graph-status>
    <graph-prompt></graph-prompt>
  </graph-goal>
</template>

Instance:

<graph-goal data-conforms-to="../templates/graph.template.html#graph-goal">
  <graph-title>Build v4: knowledge graph as hypermedia</graph-title>
  <graph-confidence>85</graph-confidence>
  <graph-status>pending</graph-status>
  <graph-prompt>we are playing around with mycelium…</graph-prompt>
</graph-goal>

Validators query by tag instead of attribute: root.querySelector('graph-title'), root.querySelector('graph-confidence'), and so on, the same pure-check(root) shape DESIGN.html's live demo already established.

Per-type fields

Deciduous's flat schema bolted status onto every node type and then had to fake its absence for option/outcome/observation with a nodeTypeSupportsStatus() helper — the exact problem DESIGN.html names as the reason templates exist. Here, a type simply doesn't declare a field it doesn't need. (Table shows field names without the graph- prefix for brevity; every field below is graph-<name> in practice.)

typefields
graph-goaltitle, confidence, status, prompt
graph-decisiontitle, confidence, status
graph-optiontitle, confidence
graph-actiontitle, confidence, status, commit, files, branch
graph-outcometitle, confidence, commit, files, branch
graph-observationtitle, confidence

Conformance: on the element, not the document

DESIGN.html's own example declares conformance with a <link rel="conforms-to"> in <head> — a claim about the document as a whole, one slot, exactly one type. That doesn't compose: it can't sit next to a <graph-decision> nested inside this very document's <spec-design> section, declaring conformance for just that one embedded element (see the open question below about inline <graph-decision>/ <graph-observation> instances). So this document (and spec.template.html) instead declare conformance as a data-conforms-to attribute directly on the element making the claim — this document's own <spec-doc> tag carries it. A document can then have exactly one typed root and any number of typed elements nested inside it, each independently found via document.querySelectorAll('[data-conforms-to]').

Edges

The six data-rel labels carry over unchanged: depends_on, blocks, supports, contradicts, alternative_to, leads_to, used exactly as DESIGN.html's <a data-rel="verifies" href="…"> example already shows. graph-option → parent graph-decision uses depends_on, the closest existing label; the dogfood chain below uses leads_to for its forward narrative. New labels get minted the same way DESIGN.html describes: as a project needs them, not from a fixed enum — this document mints specifies for the spec → action link below, and elaborates for the link to DESIGN.html above.

Audits: proven against a fixture, not the real files

audits/graph-integrity.html implements the two audits DESIGN.html names:

  • orphans-except-goal — every non-graph-goal node must have at least one edge (CLAUDE.md: "Root goal nodes are the ONLY valid orphans").
  • dangling-outcome — every graph-outcome must have an edge back to what it resolves (CLAUDE.md: "does every outcome link back to what caused it?").

Both are pure functions over {nodes: [{id, type, status}], edges: [{from, to, rel}]} — deliberately the shape a future crawler would emit by parsing graph/*.html. This round proves them the way DESIGN.html's own live demo proves the claim template: against a literal embedded sample array, PASS/FAIL rendered inline in the browser. They are not run against the real graph/ files — that needs fetching across documents, which is the crawler/mycelium run work this spec explicitly defers. The five real instance docs get conforms-to links and hand-verified-correct structure, not yet mechanically checked.

The five dogfood nodes

v4's own decision trail so far, as graph nodes instead of deciduous rows:

  1. goal-build-v4.html — a graph-goal, "Build v4: knowledge graph as hypermedia," with graph-prompt set to the verbatim message that opened this session.
  2. decision-html-as-store.html — a graph-decision, "HTML documents as canonical store, not DB + Markdown," summarizing DESIGN.html's core thesis.
  3. action-write-design-html.html — a graph-action, writing DESIGN.html.
  4. outcome-design-html-committed.html — a graph-outcome, committed as 9794442, with graph-commit set accordingly.
  5. action-write-template-series.html — a graph-action, this task: the template series plus this spec. Its graph-outcome node is added after the implementation actually lands, per CLAUDE.md's before/after logging rule, not written speculatively now.

Chained graph-goal →leads_to→ graph-decision →leads_to→ graph-action →leads_to→ graph-outcome →leads_to→ graph-action. This document's specifies edge below points at node 5 once it exists: action-write-template-series.html.

Spec docs are graph nodes too

This document is the concrete answer to a meta-question the brainstorming skill leaves open for every project: where does an approved design go? v4's answer is templates/spec.template.html's spec-doc type: a required identity (spec-title, spec-status, spec-date) plus required spec-problem and spec-design sections, and optional spec-out-of-scope / spec-open-questions sections — each free to hold whatever content the design needs, but addressable by tag name across every spec in the corpus. spec-status tracks the skill's own lifecycle: draft while under discussion, approved at the point this document reached (sign-off, before writing code), implemented once this design has shipped.

  • No mycelium run. Deferred by DESIGN.html's own roadmap.
  • No crawler/index. Same deferral; nothing here fetches across documents.
  • No live validation of the real instance docs. The five dogfood nodes and the audits are correct by hand-inspection and by the embedded-fixture proof respectively, not mechanically checked against each other. That mechanical check is exactly what the crawler gives later.
  • What are the actual valid graph-status values for graph-goal/ graph-decision/graph-action instances? Every node inspected in the existing deciduous graph so far shows pending; resolve by checking deciduous's own source before writing graph.template.html's validators, rather than guessing an enum.
  • Once graph.template.html exists, should specific claims inside a spec's <spec-design> (like the two callouts above) be marked up as inline <graph-decision>/<graph-observation> instances, rather than plain paragraphs? Left open rather than done here, since it can't properly conform to a template that doesn't exist yet.
