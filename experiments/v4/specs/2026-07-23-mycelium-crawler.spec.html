The mycelium crawler: a protocol-only engine for template-conforming HTML approved 2026-07-23

DESIGN.html's roadmap deferred "build mycelium run" and "build the crawler/index" until a real template series existed to test them against. That's now true — knowledge.template.html and spec.template.html exist, with real instances in knowledge/. The freshly-rewritten CLAUDE.md already names the resulting gap directly: its Session Start Checklist admits ls/grep are "coarser than deciduous nodes/deciduous edges were," and knowledge.template.html's two audits are still only proven against their own sample markup, never the real files. This spec scopes the tool that closes both gaps.

Package

experiments/v4/package.json    name: "@mycelium/v4", joins the pnpm workspace, engines.node >=24
experiments/v4/crawl.ts        the crawler itself

Run directly as node crawl.ts — Node ≥24 strips TypeScript's type syntax natively, no tsx/ts-node, no build step, nothing to keep in sync between a source file and a compiled one. Same "no build step that could drift from the source" argument DESIGN.html already makes about the HTML documents themselves, just applied to the tool that reads them.

One runtime dependency: linkedom, a lightweight HTML5 (not XML) DOM implementation for Node. An XML parser was ruled out earlier: these files rely on real HTML parsing behavior (unclosed void elements like <meta>, named entities like &mdash;), and a stricter parser would silently diverge from what a browser accepts — exactly the drift DESIGN.html argues the format should never allow.

No built-in ontology

DESIGN.html is explicit: "mycelium ships no notion of 'goal,' 'claim,' or 'test.' It discovers vocabulary by reading whatever template documents a project has actually authored." The first draft of this design violated that without noticing — it planned to have the crawler itself extract "nodes" as {id, type} and "edges" from <a data-rel>, baking in exactly the ontology that's supposed to stay template-owned. Corrected: the crawler only ever knows about the templating protocol, never a domain built on top of it.

Protocol-level (crawler knows this)Domain-level (crawler must not know this)
<template id> + its paired script"nodes" and "edges" as concepts
data-conforms-to="path#id"data-rel meaning "edge"
data-validates="#id", signature check(root)node types like knowledge-goal
data-audits="name", signature check(documents)what "orphans-except-goal" even means

What it does

  1. Walk a directory, parse every .html file with linkedom.
  2. Discover every <template id> across all files, paired with its sibling data-validates/data-audits script.
  3. Discover every instance: any element carrying data-conforms-to="path#id".
  4. For each instance, extract and execute its template's data-validates script (check(root) against the instance's own parsed subtree), report pass/fail.
  5. For each data-audits script found, extract and execute it, passed documents — every parsed file as {path, dom} — not a pre-built graph. The script decides how to read that itself.
  6. Print a summary: templates found, instances validated (pass/fail counts), audits run and their results.

Script execution

Extracted script text (an ES module's source, e.g. export function check(root) { … }) runs via a data:text/javascript dynamic import() — no temp files, if that holds up under a quick spike before this is built for real. Falls back to a temp .mjs file if it doesn't.

Signature change this requires

knowledge.template.html's two audits currently export check(nodes, edges), with node/edge extraction (extractGraph()) living in the live-demo script, run once against local sample markup. They move to check(documents), with the same extractGraph-shaped logic moving into the audit script itself, now reading across every file the crawler found instead of one local container. The live demo keeps working unchanged — it already has real markup and real edges sitting in the DOM, it just calls extractGraph(documents) with a one-file documents array standing in for a real crawl.

Report contract, resolved not left open

The crawler needs some minimal way to know whether an audit passed, without interpreting what it checked. Resolution: reuse the shape data-validates scripts already return — { ok, … }. The crawler reads only ok for pass/fail coloring and exit code; everything else in the returned object is audit-specific and gets printed as-is, uninterpreted. Small, consistent, and not a new invention — both script kinds already agree on this shape.

  • No general query language. Pass/fail plus each audit's raw self-reported result is the whole report surface. Filtering by type/status/confidence, "find orphans" as a standalone command — not this pass.
  • No deciduous migration or bridge. Its ~400 frozen nodes stay exactly where they are, queryable only through the deciduous CLI.
  • No sharing with @mycelium/v0. Different domain (TypeScript code graphs vs. HTML documents), different parser, no code shared.
  • No GitHub Pages export, branch grouping, or multi-user sync. Same gaps CLAUDE.md already names; still waiting on this crawler to exist first, not solved by it.
  • Does data:text/javascript dynamic import() actually work reliably in the target Node version for this repo, including for scripts that themselves have no imports of their own (these don't)? Unverified until the spike.
